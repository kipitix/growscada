# Code Review: client-event-protocol vs path

Дата: 2026-09-16

Ревью diff между ветками `client-event-protocol` и `path` (плюс незакоммиченное изменение `internal/interface/ui/eventlog/render.go`). Сборка (`go build ./...`), `go vet ./...` и тесты (`internal/domain/event`, `TestEventsHandlers_*`) — чистые.

## Замечания

### 1. Неизвестные типы событий молча пропадают из лога
- **Файл:** `internal/interface/ui/eventlog/event_types.go:28`
- **Проблема:** `defaultFilters()` и `allCategories` не содержат записи для `categoryOther` (`""`).
- **Сценарий отказа:** Приходит SSE-событие с типом, отсутствующим среди 14 захардкоженных строк в `eventTypeInfoByType` (например, новый `EventType`, добавленный на сервере без соответствующего обновления клиента). В `render.go:124` `b.filters[entry.Category]` обращается по пустому ключу, которого нет в map — Go возвращает `false` по умолчанию, и запись навсегда пропадает из лога без переключателя фильтра, которым пользователь мог бы её включить.

### 2. Лишняя сериализация событий при отсутствии SSE-клиентов
- **Файл:** `internal/interface/restapi/event_hub.go:67`
- **Проблема:** `eventHub.broadcast` безусловно маршалит каждое доменное событие в JSON до проверки, есть ли подключённые клиенты.
- **Сценарий отказа:** При нуле открытых вкладок браузера (`h.clients` пуст) каждое `TagUpdatedEvent` от частых записей значений тегов всё равно проходит через `json.Marshal` + `time.Format` синхронно в горутине публикации (внутри пути REST-запроса). При высокой частоте обновления тегов это лишняя нагрузка CPU/аллокаций ради функции, которую никто не наблюдает. Исправление — проверять `len(h.clients) == 0` (под мьютексом или через атомарный счётчик) перед маршалингом.

### 3. Нет лимита на число одновременных SSE-подключений
- **Файл:** `internal/interface/restapi/events.go:42`
- **Проблема:** `GET /api/v1/events` принимает неограниченное число одновременных SSE-соединений, каждое с буферизованным каналом на 64 слота.
- **Сценарий отказа:** Клиент (злонамеренный или просто с багом в retry-логике) открывает множество `EventSource`-соединений, не закрывая их; каждое добавляется в `eventHub.clients` и живёт до отмены контекста. Нигде в роутере или хендлере нет ограничения, поэтому память/горутины сервера растут неограниченно, а `broadcast()` вынужден перебирать растущий набор клиентов под одним мьютексом при каждом доменном событии.

### 4. `eventHub.Close()` никогда не вызывается
- **Файл:** `internal/interface/restapi/event_hub.go:46`
- **Проблема:** `eventHub.Close()` отписывает hub от `EventBus`, но нигде не подключён к `gracedownManager` в `main.go`, в отличие от закрытия БД и API-сервера.
- **Сценарий отказа:** При graceful shutdown `sqlDB.Close()` и `apiServer.Shutdown()` явно зарегистрированы в `gracedownManager`, а `eventHub`, созданный внутри `NewEventsHandler(eventBus)`, никогда не получает `Close()` — его 15 подписок на `EventBus` просто утекают до завершения процесса. Сейчас безвредно только потому, что процесс всё равно завершается, но это мёртвый код относительно собственного назначения и нарушает симметрию shutdown-логики остальной части `main.go`.

### 5. Поле `onError` объявлено, но никогда не присваивается
- **Файл:** `internal/interface/ui/eventlog/bar.go:47`
- **Проблема:** Поле `Bar.onError` объявлено и защитно освобождается в `OnDismount`, но вызова `es.Set("onerror", ...)` нигде нет, поэтому оно всегда `nil`.
- **Сценарий отказа:** Это вестигиальное состояние: поле предполагает, что обработка ошибок планировалась (по аналогии с `onMessage`), но не была реализована, поэтому любая ошибка на уровне `EventSource` невидима для приложения (нет записи в лог, нет индикации в UI) кроме тихого автопереподключения браузера; проверка `if b.onError != nil` в `OnDismount` — недостижимый код.

## Приоритет

Наиболее актуально — пункт 1 (тихая потеря событий неизвестного типа): проявится сразу, как только на сервере появится новый тип события без соответствующего обновления клиента.
