## P3 — остальное

Задачи 44–70 остаются в прежнем порядке (по номеру) и не блокируют P1. Исключения — `74`, `76`, `77` и `78` выше: они стали P1 как находки ревью `73`, лежащие на только что переделанной странице выбора.

## Почему так

- Цепочка 85 идёт первой, потому что меняет саму модель публикации: Release уходит, Deploy и импорт Library работают с сохранённым состоянием, а лейблы становятся единственным способом отфильтровать сохранения в двух новых окнах. Пока это не сделано, любая работа с Release/пинами/деплоем будет переделкой. 85_1 вынесена вперёд как отдельный быстрый дефект экрана выбора.
- Внутри 85 сначала лейблы (85_2–85_3), потом носитель Deploy (85_4), затем окна (85_5–85_6), затем удаление Release (85_7) и документы (85_8): каждая часть оставляет сборку и тесты зелёными, а Release удаляется только когда им уже никто не пользуется.
- Правки по ревью задачи 73 (74, 76, 77, 78) шли первыми: страница выбора — свежий код, дефекты и дубли дешевле закрыть, пока контекст задачи 73 ещё свеж. Все четыре закрыты 2026-11-10.
- Задача 73 — страницы выбора Library/Project — шла первой из старой очереди: это следующий UI-шаг после 72_6/72_7.
- Сначала убрали неочевидный замок (72_1) — это самостоятельный видимый результат.
- Параллельно переименовываем Runtime Revision в Deployment (72_9), чтобы модель была Commit → Release → Deployment, без четвёртого неоднозначного термина.
- Затем Save/Commit (72_2), потому что Release и Deploy строятся на нём.
- Release (72_3/72_5) и Deploy (72_4) разделены: Project Release деплоится, Library Release только закрепляется.
- Защита Library (71) идёт сразу после Project Release: она не даёт истории сохранений оборвать Release.
- UI идёт после серверных частей, чтобы не переделывать экраны дважды.
- Миграции/инструменты/документы — в конце, когда форма API и модели стабилизировалась.
