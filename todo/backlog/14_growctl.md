# growctl

Утилита для декларативного управления сущностями через YAML-манифесты, по аналогии с `kubectl apply`. Нужна для быстрого поднятия тестовых окружений без goose-миграций. Её использует симулятор нижнего уровня (задача 15), чтобы сидировать тестовые теги.

## Изменения сервера

- Имя тега уникально (ADR 0002): миграция с `UNIQUE` на `tags.name`; репозиторий отображает нарушение уникальности в доменную ошибку `ErrTagNameTaken`; `POST /api/v1/tags` отвечает на неё `409 Conflict` (Problem Details).
- Существующие дубли имён миграция не чистит и не переименовывает: на базе с дублями она падает на нарушении `UNIQUE`, дубли разбираются вручную. Рабочих баз до 1.0 нет, это отмечено в CHANGELOG как BREAKING.
- `GET /api/v1/tags?name=<имя>` фильтрует по имени. Форма ответа та же, `{tags:[...]}`, и в ней 0 или 1 элемент.
- Обновить Bruno-коллекцию: фильтр `?name=` и 409 при дубле имени.

## growctl

- `cmd/growctl/` в этом же модуле, CLI на `spf13/cobra`. Собирается в `make build` → `bin/growctl/`.
- Работает только через REST API. Адрес задаётся `--server` или `GROWCTL_SERVER`, по умолчанию `http://localhost:9090`.
- Поддерживается только `kind: Tag`. Другие kind-ы — отдельные задачи.
- Манифест в стиле kubectl, многодокументный YAML. Разбирается `gopkg.in/yaml.v3` с `KnownFields`: неизвестные поля, `kind` и `apiVersion` — ошибка. Все поля `spec` обязательны.

  ```yaml
  apiVersion: growscada/v1
  kind: Tag
  metadata:
    name: pump1.running
  spec:
    type: boolean
    initialValue: "false"
    initialQuality: good
  ```

- Тег сопоставляется с сервером по `metadata.name`.
- Команды:
  - `apply -f <файл|каталог|->`: создаёт недостающие теги. `initialValue`/`initialQuality` применяются только при создании, значение существующего тега не трогается. С `--prune` удаляет теги сервера, которых нет в манифесте.
  - `diff -f` показывает план без изменений и учитывает `--prune`. Код выхода 0 — нет изменений, 1 — есть изменения, >1 — ошибка.
  - `delete -f` удаляет теги из манифеста по имени, `spec` игнорирует. Если тега нет, выводит «not found», код выхода 0.
- Сначала строится план, потом он выполняется. Ошибки валидации манифеста и расхождение `type` у существующего тега обнаруживаются до первого изменения: growctl выводит ошибку и ничего не меняет. Если при выполнении падает REST-запрос, growctl останавливается сразу и выходит с ненулевым кодом. apply идемпотентен, повторный запуск доводит дело до конца.
- Шаблоны имён: `--pattern` (`*` — любая последовательность, `?` — один символ, совпадение со всем именем) или `--regex` (Go RE2, совпадение в любом месте), одновременно — только один; семантика как у `GET /tags?name_pattern=` / `?name_regex=`, клиент дополнительно фильтрует ответ сам (защита от сервера без поддержки фильтров).
  - `apply`/`diff --prune --pattern|--regex` — prune только среди тегов, подходящих под шаблон («зона ответственности» манифеста); без `--prune` — ошибка использования.
  - `delete --pattern|--regex` — удалить подходящие теги без манифеста; показывает список и спрашивает подтверждение (`--yes`/`-y` — без вопроса); вместе с `-f` — ошибка использования.
  - `get tags [--pattern|--regex] [-o table|yaml]` — список тегов по имени; `-o yaml` выводит манифест (текущие значение и качество → `initialValue`/`initialQuality`), пригодный для `apply -f`.
- Ошибки использования (флаги, аргументы, невалидный шаблон) — код выхода 2.
- Прочие ошибки (невалидный манифест, расхождение `type`, сбой REST): `apply`, `delete`, `get` — код выхода 1; `diff` — 2, потому что его код 1 означает «есть изменения».
- Вывод `apply`/`delete` — по строке на объект: `tag/<имя> created|unchanged|pruned|deleted|not found`. У `diff` свой формат превью, только изменения: `+ tag/<имя> (<type>)` — будет создан, `- tag/<имя>` — будет удалён (`--prune`); неизменённые теги не выводятся.
- goose-сид не меняется. Добавить пример манифеста `tests/manifests/example_tags.yaml`.

- Сквозные тесты growctl: `httptest` с настоящим restapi-роутером и Postgres в testcontainers. Запускаются в `make test`.
