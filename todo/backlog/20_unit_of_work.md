# Агрегат и его события в одной транзакции (outbox)
Status: ready-for-agent

Появилось в архитектурном ревью 2026-10-05, решения — grilling 2026-10-06 и ADR 0008. Мутирующие методы трёх сервисов application повторяют один шаблон, события публикуют сами сервисы, а то, что событие уходит после commit, ничем не гарантировано.

## Что не так сейчас

- 9 мутирующих методов в `tag_application_service.go`, `scene_application_service.go` и `widget_type_application_service.go` повторяют одни шаги: разбор ID → `FindByID` и сверка Version → разбор входа → `repo.Save` → `eventBus.Publish` → `appdto.NewX`.
- Три Postgres-реализации `Save` зеркальны: `version.Initial` → INSERT, иначе UPDATE `WHERE version = $n` → `classifyUpdateConflict`.
- Сверка ожидаемой Version у Tag и WidgetType живёт в сервисах, а не в агрегатах (у Scene — уже в агрегате, задача 19).
- `EventBus.Publish` синхронный. Событие уходит после commit только потому, что репозиторий сам закрыл свою транзакцию.
- События ставит сервис вручную, и их забывают: `UpdateWidgetType` не публикует события согласованных Scene (задача 21).
- `domain/event` импортирует пакеты агрегатов, поэтому агрегаты не могут сами записывать события.

## Принцип (ADR 0008)

- Одна транзакция — один агрегат. Межагрегатное — идемпотентные политики по событиям (eventual consistency). Многоагрегатной единицы работы нет.
- События записывает агрегат; `Save`/`Delete` репозитория пишет состояние и события в `outbox` в одной транзакции; диспетчер доставляет после commit.
- Конфликт правки (ожидаемая Version) ловит агрегат, гонку записи — CAS при сохранении.

## Что сделать

Одна ветка, четыре шага; после каждого `make build` и `make test` проходят.

1. **Домен.**
   - События — в пакетах своих агрегатов (`tag`, `scene`, `library`); `domain/event` остаётся базой (Event, EventType, EventTimestamp, EventBus, события Client/System) и не импортирует агрегаты.
   - Агрегаты копят новые события (pending); сохранённый агрегат их не несёт.
   - `Create…` записывает Created, `Reconstitute…` (для репозиториев) — ничего.
   - `Delete()` агрегата записывает Deleted; Scene — ещё WidgetDeleted по каждому Widget.
   - Сверка ожидаемой Version у Tag (`SetValue`) и WidgetType (обновление) — в агрегате, как у Scene.
   - Сервисы на этом шаге ещё публикуют сами.
2. **Outbox.**
   - Миграция: таблица `outbox (seq bigserial, type, payload jsonb, created_at)`.
   - Внутренний кодек событий в infrastructure (не контракт ADR 0005); тест: каждое событие переживает кодирование туда и обратно.
   - Общий шаблон `Save`/`Delete` в Postgres: CAS по загруженной Version, классификация NotFound/Conflict, запись pending-событий в outbox — одна транзакция. Собственные `BeginTx` в `sceneRepository` уходят в шаблон.
   - `DeleteByID` → `Delete(ctx, agg)` с CAS.
3. **Диспетчер.**
   - Один процесс на БД. Сигнал из `Save` после commit + опрос ~1 с.
   - Порядок `seq`; для каждой строки: политики (возвращают error; при ошибке строка остаётся и повторяется с паузой) → `EventBus.Publish` (SSE) → DELETE. At-least-once.
   - Реестр политик (в этой задаче пуст; первая — задача 21).
   - Запуск в `main.go`; при остановке — дочистка outbox с таймаутом (стыкуется с задачей 26).
   - `DrainOnce(ctx)` для детерминированных тестов.
4. **Сервисы.**
   - Сервисы: разбор входа → загрузить → метод агрегата → `Save`/`Delete` → `appdto`; ручные `Publish` уходят, сервисы больше не держат `EventBus`.
   - `retryOnRace` в application: операции без ожидаемой Version (удаление) при гонке записи перечитывают и повторяют (3 попытки, затем конфликт агрегата → 409).
   - Согласование в `UpdateWidgetType` пока остаётся синхронным, но каждый `Save` Scene сам кладёт свои события в outbox. Превращение в политику — задача 21.

## Ограничения

- ADR 0002: только таблицы состояния + Journal, без event sourcing. Outbox — не Journal: Journal (задача 42) будет ещё одной записью в той же транзакции `Save` для Runtime-агрегатов.
- Атомарность DraftChange над несколькими агрегатами — не здесь (задача 38, Draft как агрегат).
- In-memory-репозиториев не делаем: тесты application остаются на testcontainers.
- Область Project (ADR 0006) — в задаче 31.

## Приёмка

- Поведение REST API не меняется, кроме одного: удаление, проигравшее гонку записи 3 раза подряд, отвечает 409.
- Тест: если `Save` откатился, в outbox ничего нет и ни одно событие не доставлено.
- Тест: удаление Scene, пока в неё добавляют Widget, доставляет WidgetDeleted и для добавленного Widget.
- Тест: событие, на котором упала политика, доставляется повторно; SSE-подписчик получает события в порядке commit.
- Тест: после `UpdateWidgetType` с удалённым InputPort в outbox есть события каждой изменённой Scene.
- `make build` и `make test` проходят; `CHANGELOG.md`.
