# Типизированный конфиг протокола `simulation`

Status: ready-for-agent

Домен принимает `Device.Config` как любой JSON-объект (`domain/device/device_config.go`), хотя спека задачи 34 (часть A, «Сущности») требует: «`config` — JSON под протокол (для `simulation` валидируется типизированно)». Из-за этого в Draft сохраняется конфиг, который Gateway не сможет исполнить, а `Device.Update` меняет протокол, не перепроверяя конфиг.

## Что сделать

### Домен (`internal/server/domain/device`)

- Новый VO `SimulationConfig` — полная схема протокола `simulation`: список тегов `{tag, interval?, pattern}`; паттерны — те же пять kind'ов, что в `internal/devicesim/pattern.go` (`constant`, `ramp`, `sine`, `random_walk`, `step`) с их обязательными/необязательными полями и инвариантами (`min ≤ max`, `period > 0` и т. п.).
- `quality` в конфиг **не входит**: качество значений — настройка Gateway'а, а не свойство протокола (и `tag.TagQuality` дал бы цикл импортов `tag → device → tag`).
- `Device` хранит `protocol` и типизированный `Config` рядом; конструкторы и `Update` сверяют, что конфиг принадлежит протоколу, иначе новый сентинел `ErrConfigOfAnotherProtocol`. `Device.Config()` отдаёт типизированный вариант, не сырой JSON.
- `Update`, меняющий протокол, валидирует конфиг заново (закрывает замечание ревью).
- Сырой JSON-тип (`DeviceConfig`) остаётся только на границе — разбор входа в типизированный конфиг по протоколу и обратная сериализация; в агрегате его нет.
- Форма JSON на границе (уедет в контракт части 4 и в `devicesim` части 5):
  `{"tags":[{"tag":"sim.pump1.speed","interval":"500ms","pattern":{"kind":"sine","offset":1500,"amplitude":300,"period":"20s"}}]}`
  — как в YAML симулятора, без `server`/`project`/`control`/`autostart`.

### Application (часть 3/4)

- Совместимость «паттерн ↔ тип Tag'а» (в `devicesim` — матрица `kinds[].types`, `sine/ramp/random_walk` только для integer) проверяется **не** в `domain/device` (нет доступа к `tag`), а в сервисе Device при создании/изменении: теги читаются через область проекта, отказ — как `scene.ErrTagTypesOfAnotherProject`.

### Симулятор (часть 5)

- `devicesim` продолжает жить на своей модели (`PatternSpec`), паритет проверяется фикстурным тестом: один JSON-файл в `testdata`, разбираемый обеими сторонами. Расхождение моделей — осознанная цена ADR 0004 (device side зависит только от контракта).

## Проверка

- `make build` и `make test` проходят.
- Домен: валидный конфиг создаётся; неизвестный kind, отсутствующее обязательное поле, нарушенный инвариант, конфиг чужого протокола — ошибка; `Update` со сменой протокола без валидного конфига — ошибка.
- Application: паттерн, несовместимый с типом Tag'а, отклоняется при создании и изменении Device.
- Фикстура разбирается и доменом, и `devicesim` без расхождений.

## Вне объёма

- Смена протокола как отдельная операция API — часть 4.
- Quality в конфиге — остаётся настройкой Gateway'а.
- Типизация `EnvironmentDeviceParams` по протоколу: сейчас это общий JSON-объект (тонкая обёртка над `newJSONObject`), как и `DeviceConfig` на границе; типизировать его нечем до первого сетевого протокола (у `simulation` параметров связи нет).
