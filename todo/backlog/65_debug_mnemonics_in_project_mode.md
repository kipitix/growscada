# Отладка мнемосхем в Project-режиме на живых данных
Status: needs-info
Blocked by: 34_4

Слой E. Термины — `CONTEXT.md` (Draft Tag state, Tag state).

Задача выделена из задачи 34 (Device, Device Gateway, Device Token, Environment) 2026-11-01: там согласована часть A (устройства, токены, окружения, запись в Runtime), а эта — про отладку мнемосхем в Project-режиме на живых данных. **Спецификация не готова**: инженер поработает в приложении и сформулирует её здесь.

## Задача

Инженер в режиме Project (черновик) хочет видеть живые данные от внешнего источника (симулятора или реального устройства), **не делая Deploy**, и при этом иметь возможность изменить одно значение Tag'а, оставив остальные от внешнего источника.

Два сценария, которые инженер описал:

1. «Увидеть индикацию в режиме Operation, потом вернуться в режим Project и сказать: покажи мне в Project то, что я вижу в Operation» — то же самое состояние, показанное в другом режиме.
2. «Подключиться к симулятору или реальному устройству и отлаживать мнемосхему на живых данных, а потом изменить какое-то одно значение тега, остальное оставив от внешнего источника».

## Что установлено при разборе (факты, не решения)

- `tag_updated` **уже** публикуется Runtime-нодой (ADR 0011: at-most-once, через `eventbus.AsyncPublisher`) и **уже** доходит до режима Project по общему SSE `/events?project=<id>` — `tag_updated` это `project.ContentEvent`, а `eventHub` направляет ContentEvent в поток проекта (`eventStreamOf`).
- `GET /api/v0/projects/{id}/tags` **уже** отдаёт боевые состояния в любом режиме: `TagService.withStates` → `RuntimeNode.FindTagStates` → Runtime-узел; Tag без состояния показывает начальное (нулевое значение, Quality `bad`).
- Значит сценарий 1 **технически возможен уже сегодня** — не хватает только отображения значений в режиме Project.
- UI режима Project (`internal/server/interface/ui/project/`) показывает только определения Tag'ов (имя, тип); состояния показывает только Operation (`internal/server/interface/ui/tagstate/`).

## Требование, которое уже сформулировано

- У Tag'а должно быть указано, **выставлено его значение пользователем или нет**. Если не выставлено — значение может быть установлено из живого потока Runtime.
- Открепление (вернуть Tag к потоку) означает «пусть поток снова ведёт»: значение заменится следующей записью потока.

## Что осталось решить

- Где и как хранить закреплённые ручные значения. Предварительно: `engineering.tag_states` с признаком закрепления — состояние, а не конфигурация (ADR 0011: «a value is state, never configuration»), рядом с определением Tag'а, **не переносится в ревизию** (при Deploy Tag получает обычное начальное состояние). Требует подтверждения.
- Как UI смешивает живое и закреплённое: один набор значений с перекрытием или два показываемых рядом.
- Отдельный эндпоинт под черновиковые значения или оба значения в одном ответе `GET /tags`.
- Что показывает режим Project по умолчанию: живые значения, закреплённые, или те и другие помеченные.
- Нужен ли переключатель («показывать живые»), и где его состояние.
- Что показывает режим Project для Tag'а, которого нет в Runtime (новый Tag в черновике) — начальное значение, как сегодня.
- Записывает ли ручная правка значение только в черновик или также в Runtime (по правилу «у Tag не больше одного поставщика» — в Runtime писать может только поставщик, значит только в черновик).
