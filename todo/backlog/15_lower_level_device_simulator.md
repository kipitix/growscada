# Симулятор устройства нижнего уровня

`Device` (агрегат) в реализации не требуется — симулятор пишет значения тегов через уже существующий `PATCH /tags/{id}/value`, без токенной авторизации на этом этапе. Когда агрегат `Device` и авторизация появятся, симулятор станет первым клиентом, который начнёт использовать токены.

- Имитируется не протокол (Modbus/OPC-UA/MQTT), а сам факт поставки данных нижним уровнем: значения генерируются по паттернам — константа, линейный рост, синусоида, случайное блуждание, ступенька.
- Архитектурно интерфейс симулятора к SCADA-серверу (REST API) фиксируется как референс для будущих протокольных адаптеров — они должны реализовывать тот же контракт (пишут значения тегов тем же способом, что и симулятор).
- Отдельный Go-бинарник `cmd/device_simulator/` в этом репозитории со своим `make`-таргетом; не участвует в `make build` основного сервера.
- Управление гибридное:
  - YAML-конфиг при старте — список тегов, паттерн и параметры генерации для каждого.
  - Собственный REST control-API для рантайм-управления: `POST /control/start`, `POST /control/stop`, `POST /control/tags/{name}/pattern` (смена паттерна/параметров на лету), `POST /control/tags/{name}/quality` (принудительная установка `Good`/`Bad`/`Uncertain`).
- Ссылается на теги по ID или по имени (имя резолвится в ID через `GET /tags` при старте); теги сам не создаёт и не удаляет — это ответственность основного приложения / `growctl`.
- Один процесс = одно виртуальное устройство (для прототипа); несколько устройств в тестовом сценарии — несколько экземпляров процесса.
- Зависимость: сидирование тестовых тегов для интеграционных тестов делается через `growctl apply` (см. отдельный пункт `growctl`).
- Интеграционные автотесты — Bruno-коллекция (не testcontainers: они зарезервированы за unit-тестами инфраструктурного слоя). Сценарий: `growctl apply` сидирует теги → поднимается сервер + симулятор → проверяется изменение значений и версии тегов по паттерну, включая конфликт версий (409).
