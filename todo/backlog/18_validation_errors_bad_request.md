# Ошибки валидации ввода → 400 Bad Request

Сейчас REST API отвечает 400 только на невалидный JSON или UUID в пути. Любая ошибка разбора/валидации доменных значений (имя тега, значение, `TagType`, `TagQuality`, `ScriptLanguage`, `PortTypeHint`, размеры и т. п.) уходит в 500 — это прямо зафиксировано тестом `TestPostTags_InvalidType_Returns500WithProblemDetails`.

- Ввести в application-слое общий способ пометить ошибку как «невалидный ввод» (sentinel или тип ошибки), оборачивать им ошибки разбора и валидации в сервисах.
- Во всех хендлерах маппить такие ошибки в 400 (`NewBadRequest`), остальные — по-прежнему в 500.
- Обновить тесты, ожидающие 500 на невалидный ввод, и `CHANGELOG.md`.
- Проверить Bruno-коллекции (ожидаемые статусы, если где-то указаны).
- Появилось в ходе задачи 13: `"quality": "simulated"` и `"type_hint": "unknown"` сейчас отклоняются с 500.
- Появилось в ходе задачи 14: `GET /api/v0/tags?name=` (`getTagsByName` в `restapi/tags.go`) отвечает 500 на любую ошибку, кроме `ErrTagNotFound`. Пока `tag.NewTagName` ничего не проверяет (TODO в `tag_name.go`), это недостижимо; когда проверка появится, невалидное имя должно давать 400.

## Comments

### Решения (grilling, 2026-10-04)

- **Везде 400.** Любой невалидный ввод — `400` `NewBadRequest`. Сцены переводятся с `422` на `400`; `NewValidationError` и `TypeValidation` удаляются как неиспользуемые. `404` — только для ресурса из URL, `409` — конфликт версии/имени.
- **Один маркер в application-слое: `application.ErrInvalidInput`** (sentinel). Сервисы оборачивают им ошибки разбора строк из входных `appdto`: имя, `TagType`, `Quality`, значение (в т. ч. несовместимое с типом существующего тега), `ScriptLanguage`, `PortTypeHint`, размеры, origin, версия, имя порта, matcher.
  - Заменяет `scene.ErrSceneValidation` и `widget.ErrWidgetInvalidInput` (удаляются).
  - Доменные sentinel'ы со смыслом (`tag.ErrInvalidTagNameMatcher`, `widget.ErrDuplicateInputPortName`) остаются; сервис дополнительно оборачивает их маркером.
  - Почему не в domain: те же доменные парсеры вызываются при восстановлении из БД — битая строка в БД должна давать `500`, а не `400`. Только сервис знает, что значение пришло от вызывающего.
- **Ссылка из тела запроса на несуществующую сущность → 400** (например, неизвестный `type_id` у Widget): сервис оборачивает not-found в `ErrInvalidInput`.
- **Маппинг — общий хелпер в `restapi`** (`writeAppError(w, r, err)` или аналог): хендлер сначала проверяет свои `404`/`409`, затем хелпер: `ErrInvalidInput` → `400` с `err.Error()` в `detail`, остальное → `500`.
- **Клиенты не меняются**: sentinel для `400` в `apiclient` не добавляем (потребителей нет). Побочный эффект: devicelink/devicesim перестают бесконечно ретраить невалидный ввод (`IsTransient` считает временными только `5xx`).
- **SchemaVersion не поднимается**: статус-коды не входят в схемы `contract/`.
- **Тесты**: `TestPostTags_InvalidType_Returns500WithProblemDetails` → `400`; `400`-тесты по каждому эндпоинту; на уровне сервисов — `errors.Is(err, application.ErrInvalidInput)`; защитный тест: ошибка восстановления из репозитория не помечается маркером (→ `500`).
- UI и Bruno-коллекции от статусов не зависят — менять нечего (проверить при реализации).

### Дополнение: тип виджета (2026-10-04)

- Без port bindings Widget с несуществующим `type_id` создавался (`201`): тип проверялся только при привязках, внешнего ключа не было, а удаление WidgetType оставляло его Widgets с висячим `type_id`.
- **Тип проверяется всегда** при создании и обновлении Widget: неизвестный — `400`.
- **Используемый WidgetType удалить нельзя** — `409 Conflict` (`widget.ErrWidgetTypeInUse`). Гарантия — внешний ключ `fk_widgets_type_id ON DELETE RESTRICT`, без гонки «проверили → удалили»; при гонке на создании/обновлении Widget репозиторий отдаёт `ErrWidgetTypeNotFound` → `400`.
- Миграция удаляет уже осиротевшие Widgets (до 1.0 допустимо, они и так рисовались заглушкой). Очистка привязок при удалении типа больше не нужна.

### Дополнение: UI (2026-10-04)

- Проверка в браузере показала, что `saveSceneProperties` и `saveWidgetGeometry` сами подменяли ввод (размер ≤ 0 → значения по умолчанию, origin обрезался до 0–1, нечисловое → 0), так что `400` сервера до пользователя не доходил, а поле показывало не то, что сохранено.
- Решение: числа отправляются как введены — `400` → toast + откат поля к значению сервера; нечисловое/пустое поле — toast «Client Error», без запроса, поля возвращаются к текущему значению.
