# Согласование Widget с изменённым WidgetType — политика по событию
Status: ready-for-agent

Появилось в архитектурном ревью 2026-10-05; переписано после grilling задачи 20 (2026-10-06, ADR 0008) и grilling этой задачи (2026-10-09, решения внесены в ADR 0008): одна транзакция — один агрегат, межагрегатное — идемпотентные политики, сводящие состояние к текущему, через задания политик. «Всё или ничего» больше не цель.

## Что не так сейчас

- `UpdateWidgetType` (`application/widget_type_application_service.go`) после `Save(type)` синхронно согласует каждую Scene (`FindByWidgetTypeID` → `ReconcileWith(wt)` → `Save`, до 3 попыток при `ErrSceneConflict`, удалённая Scene пропускается, задача 19).
- Ошибка посреди цикла (не конфликт, например отказ БД): клиент получает 500, WidgetType уже сохранён, часть Scene согласована, остальные сохраняют привязки к исчезнувшим портам навсегда — повтора нет.
- Гонка: `AddWidget`/`UpdateWidget` прочитал WidgetType со старым портом P, параллельно `UpdateWidgetType` удалил P и согласовал Scene, затем commit Widget с привязкой к P — привязка остаётся навсегда (была и при синхронном цикле).

## Решения

- **Задания политик, а не политики в цикле диспетчера.** Диспетчер не выполняет политики: для каждой политики, которой нужно событие, он ставит задание в `policy_jobs` в той же транзакции, что DELETE строки outbox, и отдаёт событие в SSE. Упавшая политика не держит ни SSE, ни другие политики. At-least-once сохраняется.
- **Политика сводит состояние к текущему.** Она согласует с WidgetType, прочитанным из БД при выполнении задания, а не с payload события. Порядок заданий неважен.
- **Слияние заданий.** `policy_jobs (policy text, job_key text, generation bigint, attempts int, next_attempt_at timestamptz, last_error text, PRIMARY KEY (policy, job_key))`. Ключ выдаёт политика (`JobKey(event)`), здесь — `widget_type_id`. Постановка: `INSERT … ON CONFLICT DO UPDATE SET generation = generation + 1, attempts = 0, next_attempt_at = now()`. Воркер запоминает `generation = g` до чтения WidgetType. Успех — `DELETE … WHERE generation = g`. Сбой — `UPDATE attempts, next_attempt_at, last_error … WHERE generation = g`. Событие, пришедшее во время выполнения, оставляет задание созревшим, и оно выполнится ещё раз. Payload в задании нет: событийные реакции (Alert, счётчики) — курсор по Journal, не `policy_jobs` (ADR 0008).
- **Повторы бесконечны**, backoff 1 с → ×2 → потолок 5 мин. Каждая ошибка — в `slog` и в `last_error`. Новое событие по ключу сбрасывает паузу.
- **Внутри запуска сбой одной Scene не останавливает остальные.** Политика согласует все Scene (каждую в своей транзакции, `retryOnRace`; удалённая Scene пропускается) и возвращает `errors.Join`. При ошибке задание повторяется целиком, и уже согласованные Scene проходят вхолостую. Если WidgetType удалён, задание выполнено (Widgets удалённого типа не бывает).
- **Политика слушает `widget_type_updated`, `widget_added` и `widget_updated`.** Ключ — `widget_type_id`. Это закрывает гонку из «Что не так»: после commit Widget задание сливается с уже стоящим, и в норме прогон холостой. Для этого `WidgetAddedEvent`/`WidgetUpdatedEvent` получают `WidgetTypeID`. Кодек outbox читает старые строки без поля (ключа нет → задание не ставится). SSE-контракт `contract/api/v0` не меняется.
- **Слои.** application: интерфейс `Policy { Name() string; JobKey(event.Event) (string, bool); Run(ctx, key string) error }` и политика согласования Widgets с WidgetType (репозитории WidgetType и Scene). infrastructure/postgres/outbox: миграция `policy_jobs`, постановка заданий в диспетчере, `PolicyRunner` — одна горутина, задания по очереди (один процесс на БД, `SKIP LOCKED` не нужен). `Run` будится сигналом диспетчера и таймером ближайшего `next_attempt_at`; `RunDueOnce(ctx)` нужен для детерминированных тестов. Реестр политик собирается в `main.go`. При остановке текущее задание прерывается и повторяется после старта, дочистки нет.
- **UI Project.** 409 на правке Widget/Scene: UI сам перечитывает Scenes и Widgets (не ждёт SSE) и показывает понятный тост («Scene изменена, повторите правку»). Правку не переприменяет.

## Что сделать

- Миграция `policy_jobs`; постановка заданий в диспетчере; `PolicyRunner` с `Run`/`RunDueOnce`; запуск в `main.go`.
- `WidgetTypeID` в `WidgetAddedEvent`/`WidgetUpdatedEvent` и в кодеке outbox (чтение старых строк без поля).
- Политика согласования в application; `UpdateWidgetType` сохраняет только WidgetType. Убрать `maxReconcileAttempts`, синхронный цикл и `reconcileScene` из сервиса.
- UI Project: перечитывание и тост при 409.
- `CHANGELOG.md`.

## Приёмка

- Тест: задание, на котором упала политика, выполняется повторно после паузы; SSE-события, пришедшие после него, доставлены, не дожидаясь.
- Тест: при ошибке сохранения одной Scene остальные согласованы в том же запуске; после повтора согласованы все, уже согласованные не изменились (нет новых событий).
- Тест: событие `widget_type_updated`, пришедшее, пока задание по тому же WidgetType выполняется (взят generation g), приводит к повторному выполнению с новым WidgetType.
- Тест: два `widget_type_updated` подряд до запуска воркера дают одно задание.
- Тест: Widget, добавленный с привязкой к порту, который удалён после чтения WidgetType, после `DrainOnce` + `RunDueOnce` теряет привязку.
- Тест: после удаления InputPort, `DrainOnce` и `RunDueOnce` в доставленных событиях есть каждая затронутая Scene.
- Тест кодека: строка `widget_added` без `WidgetTypeID` декодируется.
- В браузере: удалить InputPort в Library, затем передвинуть Widget этой Scene в Project. После прихода события 409 нет; если правка попала в окно — тост, Widgets перечитаны, UI не ломается.
- `make build` и `make test` проходят.

## Comments

- 2026-10-06 (DDD-ревью задачи 20): политика по `widget_type_updated` — переходная. По ADR 0007 Project видит только Library Release, и правка WidgetType ни одной Scene не меняет; согласование Widgets переезжает в DraftChange смены закреплённого релиза (задача 33), и тогда эта политика удаляется. Механизм `policy_jobs` остаётся.
- 2026-10-09 (grilling): блокировка очереди решена заданиями политик вместо политик в цикле диспетчера (отвергнуты: принять блокировку; позиция на подписчика в outbox). Слияние заданий по ключу с `generation` — ценой того, что `policy_jobs` годится только для сведения к состоянию; реакции на каждое событие (Alert — задачи 54/55, Computation — 56) пойдут курсором по Journal (задача 42). Повторы бесконечные с backoff. Сбой одной Scene не останавливает остальные. Найдена и закрыта гонка AddWidget/UpdateWidget против удаления порта: политика слушает и события Widget, в них добавлен `WidgetTypeID`. UI при 409 перечитывает, без переприменения правки.
