# Настройки пользователя на сервере: порядок библиотек

Status: ready-for-agent
Priority: 2

Первая задача пары 81/82 (грилинг 2026-11-12): страница выбора библиотек
получает ручной порядок, и он хранится на сервере под пользователя, а не в
таблице библиотек. Решение и его обоснование — ADR 0024, термин — «User
settings» в `GLOSSARY.md`. Задача 82 (UI страницы) опирается на этот API.

## Почему отдельный агрегат

- Порядок — факт про N библиотек сразу: колонка `position` в
  `engineering.libraries` сделала бы одну перестановку транзакцией над N
  агрегатами (ADR 0008), поднимала бы версию каждой библиотеки на каждый
  драг (конфликт с переименованием в другой вкладке) и требовала бы правила
  «не сбрасывать» в `growctl apply`.
- Пользователей ещё нет (задача 49), авторизация — задача 50. До неё все
  запросы действуют как один человек; форма хранения должна пережить
  появление настоящих личностей без переделки таблицы, сервиса и API.

## Что делается

- Миграция в цепочке `public`:
  `public.user_settings (user_id UUID, organization_id UUID REFERENCES
  organizations(id), key TEXT, payload JSONB, version INTEGER > 0,
  updated_at)`, первичный ключ `(user_id, organization_id, key)`.
  `user_id` без внешнего ключа до задачи 49; миграция пользователей
  бэкфиллит строки `SingleUser` на первого.
- Домен `internal/server/domain/settings`: агрегат `Settings` (владелец,
  организация, порядок, `version.Version[Settings]`), VO `Order` (без
  нулевых ID, без дублей, копия на выдаче), `Repository`
  (`Find`/`Save`), `ErrSettingsConflict`; `SingleUser()` — фиксированный
  `f0000000-0000-4000-8000-000000000001`.
- Репозиторий `postgres/repositories/user_settings_repository_postgres.go`
  с кодеком payload `{"library_ids": [...]}`; вставка при начальной версии
  (`ON CONFLICT DO NOTHING`), CAS при сохранённой. Без outbox и без
  событий: настройка — не контент, общий поток событий — не канал одного
  человека.
- Сервис `application.SettingsService` (`LibraryOrder`,
  `SetLibraryOrder`): владелец — параметр конструктора (шов под
  принципала запроса), организация — серверная; проверка заявленной
  версии до записи, гонку ловит CAS.
- API `contract/api/v0/settings.go`: `GET /api/v0/settings/library-order`
  → `{version, library_ids}` (200 и `{0, []}` без строки, не 404),
  `PUT` c `{version, library_ids}` → `{version, library_ids}`; 409
  `settings_conflict` при устаревшей версии. Дубли и нулевой ID
  нормализуются, ID несуществующей библиотеки терпим (порядок — взгляд
  на контент, не инвариант о нём).
- Слияние с живым списком — на клиенте (задача 82): сохранённые ID
  первыми, остальные по имени. Сервер библиотеки не читает,
  `GET /libraries` остаётся порядком создания, `growctl` не затронут.
- `apiclient`: `LibraryOrder`, `SetLibraryOrder`; проводка в `main.go`,
  `servertest` и в тестовые сервисы `restapi`.
- Контракт: MINOR `0.33 → 0.34` + `make schemas`; Bruno:
  `get_library_order`, `put_library_order` (+ `requestBodies`,
  `roles_test.go` — `domain/settings` в Engineering node).
- Тесты: домен (нормализация порядка, неизменность владельца и версии при
  `WithLibraryOrder`, стабильность `SingleUser`), репозиторий (вставка,
  чтение, CAS, конфликт, раздельность владельцев и организаций), API
  (пустое состояние, первая запись, 409, терпимость к удалённой
  библиотеке).

## Вне объёма

- UI страницы выбора (двухпанельная раскладка, инлайн-редактирование,
  перетаскивание) — задача 82.
- `project_order` и перенос «последней открытой» библиотеки на сервер —
  позже, тем же механизмом (новый ключ, без миграции).
- Авторизация и принципал запроса — задача 50.
