# Integer-значения больше 2^53 теряют точность в виджете
Status: ready-for-agent

Появилось в ревью задачи 16. Домен хранит Integer-тег как `int64` (`domain/tag/tag_value_integer.go`), а скрипт WidgetType получает его как JS `number`. `number` точно представляет целые только до 2^53 − 1 (`Number.MAX_SAFE_INTEGER` = 9 007 199 254 740 991). Всё, что больше по модулю, молча округляется.

## Где теряется

- REST API и событие `tag_updated` передают значение строкой (`"value": "9007199254740993"`), там точность не теряется.
- `uiutil.NewInput` (`interface/ui/uiutil/srcdoc.go`) разбирает строку в `int64`, `uiutil.InputsJSON` кодирует её JSON-числом, а в iframe `JSON.parse` превращает число в `number`, и значение округляется.
- Так происходит везде, где виджет получает `inputs`: в Operation (`livescene.View` → `postMessage`) и в превью Library и Project (`BuildSrcdoc`).

## Пример

Integer-тег счётчика со значением `9007199254740993` виджет показывает как `9007199254740992`. Нет ни ошибки, ни маркера Quality, Operator видит правдоподобное, но неверное число.

## Что решить

Исправление меняет то, что скрипт получает в `inputs.<port>.value`, то есть контракт `docs/widget_type_contract.md`. По нему поля входа только добавляются, а смысл и тип существующих не меняются. Варианты:

- **Отдельное поле с точным значением.** Например, `inputs.<port>.raw` — исходная строка значения для всех TagType. `value` остаётся `number`, а виджету, которому нужна точность, хватит `BigInt(inputs.n.raw)`. Контракт не ломается, это расширение.
- **Строка вместо числа для больших значений.** Простой фикс, но тип `value` начинает зависеть от величины числа, а контракт обещает `number` для Integer. Нарушает контракт.
- **`BigInt` для больших значений.** Точно, но `JSON.parse` не создаёт `BigInt` (нужен свой разбор в `liveWidgetTail` и в `BuildSrcdoc`), а смешивать `BigInt` с `number` в арифметике нельзя: `value + 1` бросит `TypeError`. Нарушает контракт.
- **Оставить как есть.** Записать ограничение в контракт: Integer точен до ±(2^53 − 1). Опционально: вне диапазона помечать порт как Uncertain.

## Решение (grilling 2026-10-21)

Выбран вариант «отдельное поле», и контракт скрипта WidgetType становится пятым версионируемым контрактом (ADR 0005, `CONTEXT.md` → SchemaVersion уже обновлены).

### Вход виджета

- `inputs.<port>` = `{ value, text }`. `value` не меняется (Integer → `number`, Boolean → `boolean`, String → `string`). `text` — значение Tag строкой, без потери точности, для **всех** TagType: Integer `"9007199254740993"`, Boolean `"true"`/`"false"`, String — сама строка.
- Имя `text`, а не `raw`: в SCADA raw — значение устройства до масштабирования (понадобится для Device); `string` совпадает с TagType String и type hint.
- `text` в канонической форме — как сервер хранит значение (`"+007"` → `"7"`).
- Порт без значения (нет PortBinding или Tag удалён): `text` отсутствует (`undefined`), `value` — значение по умолчанию type hint, как сейчас. Так виджет отличает «значения нет» от настоящего `0`/`false`/`""`.
- Превью Library и Project — как Operation: `text` есть, только если введённое Engineer'ом значение допустимо для типа порта (Integer — `ParseInt` int64, Boolean — только `"true"`/`"false"`), в канонической форме. Недопустимый или пустой ввод — порт без значения. Порт «any» в превью: непустой ввод → `value` и `text` — эта строка.
- Контракт пишет: для Integer `value` точен только в пределах ±(2^53 − 1); за пределами `value` округлён, точное значение — `BigInt(inputs.<port>.text)`.
- Маркер Quality за пределами безопасного диапазона не ставится: Quality — надёжность Tag, а не его отображение.

### Контракт `widgetscript`

- Новый пакет `contract/widgetscript/v0` (package `widgetscriptv0`): `SchemaVersion()` = `0.1`, типы `Inputs` и `Input` (`value`, `text`) переезжают из `uiutil`, вместе с `MarshalJSON` (отсутствие `value`/`text` → ключа нет). `uiutil` строит и кодирует входы через них.
- `schemas/widgetscript/0.1.json` генерирует `make schemas`; `TestSchemaIsCommitted` в пакете, как у остальных контрактов. Схемы 0.0 без `text` нет — контракт сразу начинается с 0.1.
- Скрипту версия не передаётся (ни глобальной, ни в `inputs`, ни аргументом `render`). Версия — в схеме и в `docs/widget_type_contract.md`. Когда впервые понадобится MAJOR, WidgetType объявит MAJOR своего скрипта (не в этой задаче).
- Обновить doc-комментарий пакета `contract` (список контрактов) и таблицу пакетов в `AGENTS.md`.

## Приёмка

- `docs/widget_type_contract.md`: SchemaVersion `widgetscript` 0.1 и путь к схеме; поле `text` (все TagType, каноническая форма, отсутствует у порта без значения); предел точности `value` для Integer и пример с `BigInt`.
- `contract/widgetscript/v0` + `schemas/widgetscript/0.1.json`, `make schemas` ничего не меняет.
- Юнит-тест в `uiutil` на значения на границе: `9007199254740991`, `9007199254740993`, `-9007199254740993`, `math.MaxInt64`, `math.MinInt64` — `text` точен, `value` как раньше.
- Юнит-тесты превью: недопустимый ввод в integer-порт (`"abc"`) и boolean-порт (`"yes"`) → `text` нет, `value` по умолчанию; `"+007"` → `text` `"7"`; порт без привязки → `text` нет.
- Проверка в браузере: виджет с Integer-тегом `9007199254740993` в Operation и в превью Project получает `text` `"9007199254740993"`.
- `make build` и `make test` проходят.
