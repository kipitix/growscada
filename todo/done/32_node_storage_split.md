# Разделение узлов и хранилищ, Tag definition / Tag state
Status: ready-for-human
Blocked by: 31

Слой A. Архитектура — ADR 0002, ADR 0011; термины — `CONTEXT.md` (Engineering node, Runtime node, Tag definition, Tag state).

- Одна БД на сервер, одна строка подключения, три схемы со своими цепочками goose: `public` (серверная, бывшая единая цепочка: organizations, projects, outbox, policy_jobs), `engineering.*` (scenes, widgets, widget_types, определения Tag), `runtime.*` (Tag state и копия определений Tag). Последняя миграция старой цепочки однократно переносит таблицы (`ALTER TABLE … SET SCHEMA`, разделение `tags`) и отмечает базовую версию новых цепочек; данные dev-БД сохраняются.
- Никаких запросов из схемы одной роли в схему другой; обе ссылаются на `public`. Подпакеты `runtime/` в application и infrastructure/postgres; Engineering обращается к Runtime только через порт `RuntimeNode` (in-process реализация в `main.go`, HTTP — задача 52). Тест импортов запрещает зависимости между ролями в обе стороны.
- Tag definition (имя, TagType, Version) — неизменяемый агрегат в engineering, события `tag_created`/`tag_deleted` через outbox. Tag state (значение, Quality, `seq`) — в runtime, запись без ожидаемой Version (последняя побеждает), без строки outbox: после commit Runtime сам публикует `tag_updated` в EventBus (at-most-once). `seq` — одна последовательность runtime-схемы, присваивается в UPDATE.
- Начальный Tag state — нулевое значение TagType и Quality `Bad`.
- Мост до задачи 35: политика по `tag_created`/`tag_deleted` сводит runtime-копию определений проекта к Draft; сервис создания сразу после commit вызывает тот же идемпотентный upsert через `RuntimeNode` — после 201 тег уже принимает значения. Удаление Tag в Draft сразу удаляет его Tag state. Уборщик удалённого Project удаляет и его Tag state через порт, строку проекта — последней.
- API (MINOR `contract/api/v0`): `GET /tags`, `/tags/{id}` — прежняя форма (сервис собирает определение и состояние через `RuntimeNode`), `version` — версия определения, новое поле `seq` (omitempty), оно же в `tag_updated`. `PATCH /tags/{id}/value` без `version`, без 409; ответ — `seq`. `POST /tags` без `value`/`quality`.
- `devicelink` больше не отслеживает Version и не повторяет запись после 409; симулятор отбрасывает повторы по `seq`.
- Манифест growctl (MINOR `contract/manifest/v0`): `spec.initialValue`/`spec.initialQuality` убираются; `tests/manifests`, документация.
- Operation до задачи 35 читает Scenes и Widgets из Draft (`engineering.*`).
- Приёмка: несколько записей значения подряд дают события с разными возрастающими `seq` (замечание 2026-10-07); тесты репозиториев (testcontainers) на все три схемы; тест импортов; `make schemas`; Bruno; `CHANGELOG.md`.
- Вынесено: Origin и уникальность имени Tag независимо от Origin — задача 48 (и 34 для тегов Device); отдельные БД — задача 52.

## Comments

- 2026-10-04: бывший тикет 01 задачи 36 (`36_project_undo_redo_history`, расформирована). Решения, на которых стоит: Q2 (runtime-сущности Tag/Widget создают Device/интеграции и Operator; у WidgetType нет Origin), Q9 (в Draft/Revision — только определение Tag, значение и Quality — runtime), Q20 (существующие таблицы становятся Draft), Q26–Q28 (один бинарник, роли Engineering/Runtime node, две схемы БД, связь только через API Runtime node).
- 2026-10-06 (DDD-ревью задачи 20): разделение Tag — не только хранилище, но и модель. Определение Tag и его значение с Quality — две границы согласованности: определение — агрегат Draft с ожидаемой Version и edit conflict, значение — состояние Runtime с единственным писателем (Device или людьми), без ожидаемой Version. `devicelink` перестаёт отслеживать Version и повторять запись после 409 (ADR 0004, контракт API). Запись значения не порождает строку outbox на каждое изменение; запись в историю — Journal (задача 42). До этой задачи сверку Version при записи значения делает сервис (задача 20 её в агрегат не переносит).
- 2026-10-07 (code review задачи 20, замечание 8): `Tag` пока изменяемый (в отличие от `Scene` и `WidgetType`): `SetValue` меняет сам тег и дописывает `tag_updated` с версией «текущая + 1». Два `SetValue` до `Save` дадут в outbox два `tag_updated` с одной Version и разными значениями; подписчик, отбрасывающий повторы по Version (симулятор), оставит первое, а в БД — последнее. Сейчас не проявляется: `SetTagValueByID` вызывает `SetValue` один раз. При разделении Tag: запись значения не должна давать нескольких событий с одной Version (или не давать строк outbox вовсе, как решено выше); определение Tag — неизменяемый агрегат, как Scene и WidgetType. В приёмку — тест: несколько записей значения подряд не дают двух событий, претендующих на одну Version.
- 2026-10-26 (grilling задачи 32, ADR 0011): решения выше. Серверная схема `public` и одна БД на сервер вместо «двух схем, отдельных строк подключения»; Origin перенесён в 48, отдельные БД — в 52; Tag state назван в `CONTEXT.md`; `value`/`quality` уходят из создания тега и из манифеста.
- 2026-10-26 (реализация). Решения, уточнившие описание:
  - In-process реализация `RuntimeNode` — пакет `internal/server/inprocess`, а не тип в `main.go`: та же проводка нужна `servertest`. Это единственный пакет, кроме `main.go`, `servertest` и интерфейсного слоя, который видит обе роли.
  - `PATCH /tags/{id}/value` обслуживает `application/runtime.TagStateService` напрямую: `restapi.NewRouter` принимает сервисы обеих ролей, горячий путь Device не идёт через Engineering. Чтения тегов собирает `TagService` через порт, как описано.
  - Политика-мост (`sync_runtime_tag_definitions`) ключуется по тегу (`project:<id>/tag:<id>`), а не по проекту: тег есть в Draft — upsert его определения, нет — удаление его состояния. Сведение всего проекта, прочитанного до чужого commit, могло бы стереть только что созданное состояние; по тегу гонки нет.
  - Копия определения в `runtime.tags` несёт и версию определения: `tag_updated` публикует Runtime, а форма события — форма `GET /tags/{id}` с `version`.
  - Состояния, перенесённые миграцией, получают `seq` в порядке создания тегов; ещё не записанное состояние — `seq` 0; поле `seq` в JSON всегда есть (без omitempty, вопреки описанию: форма ответа одна, 0 — «ещё не писали», меньше `seq` любой записи). Ждущие строки `tag_updated` миграция удаляет из outbox (клиенты перечитывают при переподключении).
  - Симулятор состояния не читает, поэтому «отбрасывает повторы по `seq`» — его e2e-тесты и UI (`tagstate`), где Version заменена на `seq`.
  - Манифест любой версии с `initialValue`/`initialQuality` — ошибка, называющая удалённое поле, а не «unknown field».
