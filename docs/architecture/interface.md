# Interface Layer (`internal/server/interface/`)

> Architecture reference for the GrowSCADA server. `AGENTS.md` links here: read this
> document before changing the layer it describes. Decisions are in `docs/adr/`; the
> vocabulary is in `GLOSSARY.md`.

**REST API** (`internal/server/interface/restapi/`, port `:9090`):
- Uses stdlib `http.ServeMux` with method-prefixed patterns (Go 1.22+).
- All endpoints live under `apiv0.PathPrefix` (`/api/v0`); every response carries the `GrowSCADA-Schema-Version` header.
- The content of a Project (Tags, Scenes, Widgets, Library Imports with their `impact` preview, the imported WidgetTypes, its event stream) lives under `apiv0.ProjectPath(id)`; `version` in a content DTO and every write of the content is the Version of the Project's Draft (ADR 0016), create bodies state it, and a DELETE states it in `?version=` (a stale one is 409 `draft.ErrDraftConflict`) (`/api/v0/projects/{project_id}/…`); Projects (`/projects`, `?name=`) and Libraries (`/libraries`, `?name=`) are the server's, a Library's Draft (`widget-types`, `GET …/draft` for its Version and unsaved-changes flag) and `discard` (200 `{version, has_unsaved_changes}`; to the last saved state) under `apiv0.LibraryPath(id)`; a create or delete of a WidgetType states the Draft's Version too. A `LibraryImportResponse` carries the provenance of its saved state (`saved_state_number`, `title`, `author`, `saved_at`, `labels`, `version`). A 409 of an import's switch names the Widgets in `orphaned_widgets`. A group move of Widgets is one change: `PATCH …/scenes/{scene_id}/widgets` with `{version, moves: [{widget_id, x, y}]}` answers 200 `{version}`, 400 for an empty or repeated `moves`, 404 for a Widget the body names and the Scene does not hold, 409 `nothing_to_move` when no position changes, and the Draft's 409 `draft_conflict` like every write.
- The per-user settings are the server's own (ADR 0024): `GET /api/v0/settings/library-order` (200 `{version, library_ids}`, `{0, []}` for a person who never reordered) and `PUT …/settings/library-order` `{version, library_ids}` (200; 409 `settings_conflict` on a stale Version), and the same pair for the projects under `…/settings/project-order` with `project_ids`. The person is never named by the path, and the client merges the stored IDs with the live list.
- The DraftChange stack is under the Project's and the Library's path: `GET …/draft-changes` (200 `{version, can_undo, can_redo, undo_description?, redo_description?}`, 404 for a Project or Library that is not live) and `POST …/draft-changes/undo` and `…/redo` with `{version}` (200 with the state after the operation; 409 `nothing_to_undo`/`nothing_to_redo` for an empty stack, 409 with `Problem.draft` for a stale Version). The state is read without a lock; the two commands are writes of the Draft like any other.
- The saved states are under the Project's and the Library's path (ADR 0021): `POST …/saved-states` `{version, title, author}` (201 `SavedStateResponse`; 409 `nothing_to_save`, `draft_not_saveable`, `draft_conflict`; 400 for an empty title or author), `GET …/saved-states` (200 `{saved_states}`, newest first, without content), `GET …/saved-states/{n}` (200, a Library's with `widget_types`; 404 `saved_state_not_found`), `PATCH …/saved-states/{n}` `{title}` (200, no Version stated), `POST …/saved-states/{n}/load` (200 `{version, has_unsaved_changes, warnings?}` — the Draft replaced by that saved state in one transaction, its stack cleared and its Version raised, with no Version stated: a reset, not a content write; 404 `saved_state_not_found`; a Project's answer names the saved states it could not restore) and `GET /projects/{id}/saved-states/{n}/projectfile` (a download, as a Deployment's document). The events `saved_state_created` and `saved_state_title_updated` name the Project (its stream) or the Library (the server's stream) and carry the number in `Event.saved_state`; `GET …/saved-states?label=<uuid>` filters a list by one label and every `SavedStateResponse` carries its `labels` .

- The Labels and their assignments are the server's own (ADR 0025): `GET/POST /api/v0/labels` (200 `{labels}`, ordered by name ignoring case; 201 `LabelResponse`) and `PATCH/DELETE /api/v0/labels/{id}` (`{name?, color?}` — an absent field keeps the current one, an empty color clears it; 200, 409 `label_name_taken`, 404 `label_not_found`, 400 for an empty name or a malformed color) manage the names and colors, while `PUT/DELETE /api/v0/projects/{id}/saved-states/{n}/labels/{label_id}` (and the same under a Library) place and remove one label on a saved state and answer 200 `{labels}` — every label it carries afterwards. Assignment states no Draft Version and is idempotent; 404 `saved_state_not_found`/`label_not_found`, 400 for a bad number. The events `label_created`, `label_updated`, `label_deleted`, `label_assigned` and `label_unassigned` go to the server's stream: a created, updated or deleted one names the label in `Event.id`, an assignment names it in `Event.label` and the saved state in `Event.saved_state` with the Project's or the Library's ID in `Event.id` . `apiclient`: `Labels`, `CreateLabel`, `UpdateLabel`, `DeleteLabel`, `AssignLabel`, `UnassignLabel`, `SavedStatesByLabel`.
- Deployment is under the Project's path : `GET …/deployment` (the Deployment it runs with its `saved_state_number`, 404 until the first Deploy), `GET …/tag-states` (the snapshot of its Tag states, 404 likewise), `POST …/saved-states/{n}/deploy` (201 `{number, deployed_at}`, 409 `nothing_to_deploy`, 404 `saved_state_not_found`), `POST …/discard` (200 `{version}`, 409 `nothing_to_discard` — the Draft reset to its last saved state in one transaction) and `POST …/revert-to-deployed` (200 `{version}`, 409 `nothing_to_revert` — the Draft reset to the running Deployment). The old `POST …/deploy` answers `410 Gone`; `GET …/deploy/preview` is removed. `GET …/draft` answers the state of the Draft (`{version, has_unsaved_changes}`), the Version every content write states and whether the Draft holds changes its last saved state does not — the Draft's own flag ; the same type is the answer of a Library's `discard` and of a Project's `projectfile` Open, and `Problem.draft` (409 `draft_conflict`) uses it for `version` alone. The Deployment and the Tag states are the Runtime node's; a Deploy is the Deploy service's, Discard and Revert are the Engineering node's. The Runtime node's history is `GET …/deployments` (200 `{deployments: [{number, deployed_at, cause, rolled_back_from?, saved_state_number?}]}`, newest first, `[]` for a Project never deployed, 404 for a deleted one), `GET …/deployments/{n}` (the running Deployment's shape plus `cause`/`rolled_back_from`/`saved_state_number` and `content`; 404 for a number the Project lacks, 400 for a non-numeric one) and `POST …/deployments/{n}/rollback` (201 with the new Deployment's summary, 404, 409 `nothing_to_rollback`) — no Draft is read (ADR 0014).

**Journal** is under the Project's path too (ADR 0019). `GET …/journal?from=<seq>&limit=<n>` reads a page: 200 `{entries: [Entry]}`, the entries of `contract/record/v0` as they are stored, in the order of their positions; `from` is exclusive and defaults to 0, `limit` defaults to 100 and never exceeds 1000; a non-numeric or out-of-range value is 400 `invalid_input`, a Project that is not live 404 `project_not_found`, and every answer carries `GrowSCADA-Schema-Version`. `GET …/journal/events` is the live stream: `Content-Type: text/event-stream`, a `: connected` comment, then `id: <seq>` and `data: <Entry>` per entry. Its start is `?from=` (which wins), else `Last-Event-ID`, else the Project's position (only new entries); a bad position is 400 and a Project that is not live 404, both before the stream opens. Delivery is at-most-once, while a reconnect with `Last-Event-ID` catches up exactly by reading the table (ADR 0019). The handler is the Runtime node's own, not `eventHub`: `maxSSEClients` does not cap it and it names no client. `/events` keeps `tag_updated` and `deployment_created` for the other modes and the Device Gateway (ADR 0020); removing them is a separate task.

**Operation** is the Runtime node's read model of the starting state of Operation (ADR 0020). `GET …/operation` answers 200 `{position, deployment, tag_states}`: the Project's current Journal position, the Deployment it runs as a `DeploymentResponse` with `content: ProjectFile` (`deployment` is `null`, not absent, until the first Deploy) and every Tag of that Deployment's `tag_states` by ID, an unwritten one as its TagType's zero value with Quality `bad` and `seq` 0 (`tag_states` is `{}`, never `null`, without a Deployment). A live Project answers 200 before its first Deploy, so Operation can subscribe and catch the first Deployment; a Project that is not live is 404 `project_not_found`. It reuses `DeploymentService`, `TagStateService` and `JournalService` and adds no repository, migration or outbox row; `apiclient.ProjectClient.Operation` reads it and `ui/player.Player` renders it . With `?at=<position>` (ADR 0023) the same body is answered from the nearest Checkpoint at or before the position (`OperationStateService.GetAt`): `position` is then the Checkpoint's `seq`, before the first Checkpoint the body is the empty state at 0, a future position is clamped, a non-numeric or negative one is 400 `invalid_input`, and `apiclient.ProjectClient.OperationAt` reads it for History.
- Project files are under the Project's path too (ADR 0018): `GET …/projectfile` (the Draft as the `ProjectFile` a Deploy would send; 409 `draft_not_deployable` with the builder's reason) and `GET …/deployments/{n}/projectfile` (the stored document of Deployment n; 404 without it) are downloads — `Content-Type: application/json` and `Content-Disposition: attachment; filename="<project>-draft.json"` / `"<project>-deployment-<n>.json"`, the Project's name reduced to safe characters or its ID when nothing is left — with the document as it is and the API's schema version staying a header; `POST …/projectfile?version=V` opens the document as the whole Draft (200 `{version}`, 409 `nothing_to_open`, the Version gate of every Draft write), `POST …/projectfile/deploy` makes it a Deployment without the Draft (201 `{number, deployed_at}`, 409 `nothing_to_deploy`); a document that does not validate is 400 with `Problem.file_issues: [{path, message}]`, every problem listed, and a Discard of a Deployment whose Library saved states this server lacks answers 200 with those saved states in `warnings` and the widgets of their WidgetTypes dropped .
- CORS middleware applied globally.
- Errors follow RFC 7807 Problem Details (`problems.go`).
- Each resource has its own handler file (`tags.go`, `widgets.go`, etc.). JSON shapes are `contract/api/v0`; the conversions to/from `appdto` are in `dto_mapping.go`.
- Request bodies are decoded strictly with `decodeRequest` (unknown field → 400); clients read responses tolerantly.
- `NewRouter` takes the services of both roles (`restapi.Services`): `PATCH …/tags/{id}/value` and the Deployment/Tag-states reads go to the Runtime node (`TagStateService`, `DeploymentService`) — a Tag write has no `version` and answers `seq` —, everything else, a Deploy of a saved state and Discard/Revert included, to the Engineering node's; `newAPIEvent` translates `tagstate.TagUpdatedEvent` (the Tag's full state, `seq` included) and `deployment_created` (the Project's ID, the Deployment's number and time and its `saved_state_number`).
- Devices, Environments and the pairs `(Environment, Device)` are content of a Project (`…/devices`, `…/environments`, `…/environments/{id}/devices/{device_id}`); the token routes (`…/devices/{device_id}/token`, `…/token/rotate`) are the Runtime node's and answer 404 on a server without it; issuing and rotating check that the Device exists in the Draft, while reading and revoking do not — an orphaned token stays visible and revocable . A Device Gateway authenticates with `Authorization: Bearer gsc_dev_…`: `GET /api/v0/device/config?environment=<id>` answers its configuration and `GET /api/v0/device/events` its Project's configuration events; `PATCH …/tags/{id}/value` with a token writes as that Device (a Tag it does not supply is 403, an unknown or revoked token 401, a token of another Project 403). A bearer without the `gsc_dev_` prefix is not a Device Token (user authentication).

SSE streams no longer name a client: `?client=` of an older tab is accepted and ignored (ADR 0022).

**EventBus** (`internal/server/interface/eventbus/`): in-process bus feeding the SSE streams: domain events handed over by the outbox dispatcher, the Runtime node's `tag_updated` and `deployment_created` (published by `TagStateService` and `DeploymentService` themselves through `AsyncPublisher`, ADR 0011), plus delivery's own events (`client_connected`/`client_disconnected`, `system_ready`). The `eventHub` routes a `ContentEvent` to the clients following its Project and everything else — Projects, Libraries with their WidgetTypes, labels with their assignments, connections — to those following the server's stream: `GET /api/v0/events` is the server's, joined by one Project's with `?project=<id>` (a Project not found adds nothing), `GET /api/v0/projects/{id}/events` one Project's alone. A Device Gateway's `GET /api/v0/device/events` follows its Project's stream with the configuration events alone (`device_*`, `environment_*`, `environment_device_*`), plus the events of that Project itself, which go to the server's stream. `event_bus_mqtt.go` is a stub.

**PWA UI** (`internal/server/interface/ui/`, port `:8080`):
- Built with [go-app v11](https://go-app.dev/) — compiled to WebAssembly, served by the same binary.
- Five top-level modes under one header, rendered by `root/root.go` and chosen in the main menu (`root/menu.go`):
  - **Library** — the **selection page** of the Libraries (`ui/picker`): two panes — the list of names, each with a dot of its state ("Unsaved changes" first, then `saved`, `never saved`) and, since the Libraries carry an order, a grip to arrange it — beside the details of the selected one: its name, its description, its state in words, the action **Open** and, below a line of its own, **Delete**. A desktop screen shows both panes; a phone shows one at a time (`← Libraries` goes back) and `data-screen` says which. The name and the description are edited in place — a double click on a desktop screen, the pencil of the field on a phone, which an open field replaces with a grey tick that saves and a grey cross that drops the change — and written on Enter (`Ctrl`/`Cmd+Enter` for the description), on the tick, on the blur of the field, with `Esc` or the cross to cancel, and the server's refusal under the field with the text kept (the server is the only validator); the pair goes in one update, and a field left as it was asks for nothing. **Create** ("+" in the list header) puts a draft row at the top and the name field in the details; Enter or the field's blur creates it (an empty name drops the draft), Cancel sends nothing, and a created entity opens at once. Delete opens a confirmation under its line that asks for the entity's name — typed exactly, so a slip removes nothing — and then shows the next entity. The order is the person's own (ADR 0024): the stored IDs first, then the rest by name; a drop starts on the grip — the browser's own drag on a desktop screen, a pointer gesture installed by `drag_touch_wasm.go` on a phone, because go-app v11 exposes no touch events — and stores the whole order at once, optimistically, putting it back when the write is refused; `Alt+↑/↓` moves the selected one, `↑/↓` step the selection, `Enter` opens it. The list is what selects, never opens. **Open** shows the editor: the WidgetTypes of the selected one's Draft (HTML template + JS script, live sandboxed preview via `<iframe srcdoc>`) under a panel of icons — the left column is gone — carrying the single way back to the selection page, the list that opens the saved states, **Undo** and **Redo** with the unsaved-changes mark after them (the panel names no saved state); the resets **Discard** and **Revert** are gone from the UI, which keeps Discard in the API, and there is no panel of publications: a Library publishes nothing . Its WidgetTypes, its Save and the load of a saved state are edited freely (ADR 0022). `Undo` and `Redo` of the Draft's DraftChange stack (ADR 0017): the hover text is the `undo_description`/`redo_description` of `GET …/draft-changes` ("Nothing to undo" for an empty stack), both are off while the stack offers no such step and while a command is in flight, `Ctrl+Z`/`Cmd+Z` and `Ctrl+Shift+Z`/`Cmd+Shift+Z` do the same (not in a field the user types in, not behind a dialog of the mode, and only while the mode is shown — Root keeps the hidden modes mounted); the state is read on mount, on `EventResync`, after each content event, after a command and after a load of a saved state, which clears the stack, and a `{version}` it states is what a command sends (a stale one is a 409, an empty stack is a 409 with the toast and a reread). **Save** lives on the saved-states screen, not in a dialog: `Ctrl+S`/`Cmd+S` opens that screen at its form too, even in a field, and takes the browser's Save Page away; a Save of a Draft at its Clean Version is refused (`nothing_to_save`, the form's floppy stays off with "Nothing to save since the last save"). The unsaved-changes mark is the server's `has_unsaved_changes` of `GET …/draft`, read on mount, on `EventResync`, after each content event and after each command (a load of a saved state follows it too, and a load of any saved state leaves the Draft clean — ADR 0016, amendment 2026-11-16). The panel's list opens **History** (`ui/savedstates`, shared with the Project mode) and pressing it again returns to the Draft: the Draft always the newest row at the top — its name field and a floppy that is enabled only while the Draft has changes — then the saved states of the selected library, newest first, in a list that scrolls in its own pane; each row carries the time it was saved, its name — edited in place —, its Author and its labels as colored chips with a tag icon (a saved state may carry any number of them; an empty label list opens the Labels page), and ends in a Load icon (the Draft becomes that saved state: `POST …/saved-states/{n}/load`, with a confirmation when the Draft holds unsaved changes, and the screen returns to the Draft); ADR 0025. A `saved_state_created`/`saved_state_title_updated` of another library is dropped; a `widget_type_*` rereads the Draft and the flag; a `label_*` rereads the chips, and `EventResync` rereads the panel, the history and the Draft .
  - **Project** — the **selection page** of the Projects (the same page as the Library's, with the project order: the rows are arranged by a drag as the Libraries' are; the Project dropdown is gone from this mode), then the editor — the Imported libraries panel (import a saved state of a Library, switch after a preview, remove; each import shows `saved state #N`, its title, its Author and its label chips) and the **Import libraries…** window behind it (the Libraries, each with its saved states narrowed by one label; Import/Switch/Imported, Remove with the impact preview — orphaned Widgets refuse the change, broken PortBindings are confirmed; ADR 0007, ADR 0012), configure Scenes and place Widget instances on them from the WidgetTypes of the imported saved states, grouped by Library. Scenes, Widgets, Tags, imports, Deploy (of a saved state) and the load of a saved state are edited freely (ADR 0022); a stale Version is a 409 that rereads the content and the stack. `Undo` and `Redo` of the Draft's DraftChange stack (ADR 0017): the hover text is the `undo_description`/`redo_description` of `GET …/draft-changes` ("Nothing to undo" for an empty stack), both are off while a dialog of the mode is open, `Ctrl+Z`/`Cmd+Z`, `Ctrl+Shift+Z`/`Cmd+Shift+Z` and `Ctrl+S`/`Cmd+S` (Save) do the same (not behind a dialog of the mode, and only while the mode is shown; the first two not in a field the user types in, Save even there because the browser's own Save Page is never meant), and a `{version}` it states is what a command sends (a stale one is a 409 that rereads the stack and the content, an empty stack is a 409 with the toast and a reread of the stack). The header names no saved state and no Deployment status: the list icon opens the saved states — pressing it again returns to the content — (the same screen as the Library's: the Draft always the newest row with the form that names it and fixes it as the next saved state — its Save is the floppy, the stored user name is the author, and it is enabled only while the Draft has changes —, then the saved states, newest first, each name renamed in place, each row carrying its labels as colored chips with a tag icon that opens the menu and a file-with-arrow icon that confirms **Load**, an empty label list opening the Labels page; the icons replace those words) — ADR 0025: a `label_*` rereads the chips, and nothing is published from a row any more — its unsaved-changes mark follows **Undo** and **Redo** (the server's `has_unsaved_changes` of `GET …/draft`, read on mount, on `EventResync`, after each content event and after each command; a load of a saved state follows it too and leaves the Draft clean, whichever saved state it is — ADR 0016, amendment 2026-11-16; a content event applies the flag alone, never the Version the shown content was read at) — Deploy (it opens the only list of saved states — titled "Deploy a saved state", its label filter `All labels`/one label served by `GET …/saved-states?label=`, with none it says to save the Draft first —: each saved state with its title, author, time and counts and a Deploy button unless it is running — "Running" — with the confirmation "Make saved state N the running one? Operation switches to it"; a Deployment with no saved state shows "Running Deployment N (no saved state)"; success shows a toast and rereads the saved states and `GET …/deployment`, a 409 `nothing_to_deploy` is the "This saved state is running already" toast, and `deployment_created` does the same in other tabs), and Deployments (always available: the list newest first with each number, time, cause — "Deployed", "Rolled back from #N" or "Deployed from file" — and the saved state it came from ("Saved state #N"), the running one marked, each row offering that Deployment's document as a download; selecting a row loads its document and shows the counts of its Scenes, Widgets, Tags, Devices and Environments; the Project mode offers no Rollback, which stays in the API and History). The Scene canvas selects an ordered set of Widgets whose last element is primary : a click replaces the selection, Shift/Ctrl/Cmd+click adds or removes one without dragging, a marquee dragged from the empty canvas selects by the axis-aligned box of each Widget's transformed corners (Shift adds; a drag shorter than 3 px on both axes is a click), `Ctrl/Cmd+A` selects the Scene's Widgets and `Esc` clears them (both, and the arrows, ignored in a field, behind a dialog of the mode and while another mode is shown). A body drag moves the whole selection by one delta and ends in one `PATCH …/widgets` with every moved position, a single Widget included; the arrows move it by 1 px (10 with Shift) and send one PATCH at the arrow's keyup, 500 ms without a press or a window blur, and any other write of the Draft waits for that PATCH before it states the Version (the same is true of a drag started mid-series). The canvas's dot grid does not follow the theme (a light core in a dark ring keeps at least one of the two visible on any Scene background; Operation has none), and a body drag — of one Widget or of the group — snaps its axis-aligned box, the group's common one included, to the edges and centres of the other Widgets and of the Scene within 6 px, nearest target first and the Scene's on a tie, drawing one `var(--accent)` line per snapped axis until mouseup; Alt frees the drag of snapping and guides, and the snapped positions go in the same one PATCH. The properties panel edits exactly one selected Widget — a group shows "N widgets selected" and no editors, and the anchor, rotation and resize handles belong to the single selection too. Next to Deployments is `Project file…`, one dialog (ADR 0018): `Download Draft` saves `GET …/projectfile` under the name the response gives it (a `draft_not_deployable` is a toast), `Open a file…` picks a `.json`, shows its name, schema, project and counts of Tags, Scenes, Widgets, Devices and Environments, warns that it replaces the whole Draft and can be undone, and confirms it with the Draft's Version and `Deploy a file…` picks one and confirms that Operation switches to a new Deployment while the Draft stays, naming the current Deployment; the server's `file_issues` are listed with their paths, not shown as one line, any other refusal is a toast, and after an open the content and the DraftChange stack are reread while after a file Deploy the Deployment and the Deployments list are; a picked file is a one-off and does not survive a reload.
  - **Operation** — runtime operator view: the Scenes of the running Deployment only, with live Tag values. Its picture is a `ui/player.Player` of its own (ADR 0020): the Player reads the starting state `GET …/operation`, then follows `GET …/journal/events?from=<position>`; Operation reads neither `GET …/deployment` nor `GET …/tag-states` and handles no `eventlog.ActionServerEvent`/`EventProjectResync` — the Bar's stream and Draft/Library changes reach it only through a `deployment` entry. A Project without a Deployment shows "Project is not deployed"; its first Deploy arrives as a `deployment` entry and switches the screen without a reload, and a Deployment without Scenes shows "No scenes to show". The selected Scene is kept by ID across a Deploy or Rollback when the new configuration has it, else the first Scene; a switch of Project reads that Project's Scene from LocalStorage.
  - **History** — event log viewer.
  - **Misc** — the Labels page and the User name page (see below), chosen in the menu.

- **The header and its main menu** (`root/root.go`, `root/menu.go`): one row above the modes — the burger, the navigation line naming what is shown (`Library · Greenhouse`, the mode alone while a selection page is shown or the name is not read yet), then the theme toggle every mode shares; Labels live in Misc. The navigation line is a chain of buttons — the mode, the entity and `Saved states` while the history is open — and each step above the last goes one level up: the entity closes the history screen, the mode shows the selection page; the step shown does nothing (task 91). The menu opens under the burger and lists the modes as an accordion: a row of a mode only expands its entities, the mode switches when one is chosen. Under the Library and the Project, `Choose a library…`/`Choose a project…` leads to the selection page; under Operation and History, the projects themselves and nothing else, since those modes have no page — their rows are off with `No projects yet` while the server has none; under Misc, its two pages, `Labels` and `User name`, with the page shown checked. A page of Misc is kept in `misc:page`, and the navigation line names it after the middle dot (`Misc · Labels`); its step goes back to the Misc contents. A row of an entity carries the badge of its state and comes in the order of the selection page (ADR 0024); a choice opens the editor at once, `Choose …` shows the page, either switches the mode, keeps `root:mode` and closes the menu. The menu reads both lists when it opens and rereads them while it is open on the events that change a row — of the projects and the libraries, a Save and a write of a Draft included — so it never depends on a mode having been opened; `Esc` and a click outside close it, giving the focus back to the burger. It is a disclosure — `aria-expanded`/`aria-haspopup` on the burger, `aria-expanded` on the mode rows, `role="menuitemradio"` with `aria-checked` on the entities and on the `Choose …` rows — only the mode shown is checked, so another mode's remembered page or entity is not marked (task 91) — and the header carries no tab list any more.
- **The Misc section** (`ui/misc`, `ui/labels`, `ui/username`) is the fifth mode: its contents list the two pages, `Labels` and `User name`, and each page opens on the whole screen under the same header as the Library's and the Project's panels — the back arrow and the page's name. Root chooses the page, keeps it in `misc:page` and follows `labels.ActionOpen` from History and Deploy; the User name page is reached from the menu alone and is not repeated in the Library's or the Project's panel. `Esc` and the menu work as everywhere; only the Labels page takes the keyboard, and only while it is shown.
  - **Labels** (`ui/labels`) lists the Organization's labels with a colored dot, the name, the optional color and `assigned_count`, renames and recolors in place (a palette of six presets or any `#RRGGBB`, "No color" included), creates at the bottom (`Ctrl`/`Cmd+Enter` from anywhere in the page, Enter in the name field) and deletes with a confirmation that names how many saved states lose the mark; the server's refusal stays under the field with the text kept. It never touches a Draft, a Version or the undo stack; the list is reread on mount, on `label_*` and on `EventResync` (ADR 0025).
  - **User name** (`ui/username`) stores the name the Save form fills in as the author under `author:name` — the key the Library and the Project share. Until Users and authentication exist it is a declaration, not an account: it blocks nobody. An empty name is refused; a save shows its toast and `username.ActionChanged` keeps the next Save form of both modes in step. Neither mode's panel shows the name; the form at the top of the saved states prefills it and takes no author field of its own (task 91).
- **The Operation Player** (`ui/player/`) is the operational model History will reuse: the running Deployment's `ProjectFile` and number, the Tag states by ID (including Tags the running configuration no longer names), the Journal position and the connection state. `player/model.go` maps a `ProjectFile` to the render shapes of `livescene` — Scenes, Widgets with their derived matrix, WidgetTypes and the Tags of the current configuration; a Tag without a state shows its type's zero value with Quality `bad` and `seq` 0. Entries of `contract/record/v0` apply immediately and in order: `tag_state` when its `seq` is above the known one (the state of a Tag outside the configuration is kept but not drawn), `deployment` by number — the document is read with `GET …/deployments/{n}`, the configuration is swapped and the states are kept by ID, so a new Tag is zero/bad and a removed one stops rendering — while an unknown type or a foreign MAJOR is ignored. The source is `player.Source` (`Open`/`Close` over `player.Events`), so the Player does not know whether the entries are live or replayed; `player.LiveSource` is the browser's EventSource over `apiclient.ProjectClient.JournalEventsURL(from)`, and `apiclient.ParseEntry` reads a message tolerantly. The Player redraws in batches: the entries apply at once, a burst costs one `Update`. A starting state is read before every explicit open — mounting, a switch of Project, a reconnect the browser gave up on — and the stream starts after its position; a native EventSource retry keeps the same `from` and catches up exactly from the table, and if the starting state moved ahead while the stream was opening the stream is reopened from the new position. A `deployment` document that fails to load is lost connectivity: the old configuration stays on screen, the view shows disconnected and the full resync retries with a backoff (2 s doubling to 30 s). `Connected` drives the same banner and Quality floor the Bar's state did. There is no periodic resync (ADR 0020).
- Operation and History show the Project chosen in the main menu for them, kept in LocalStorage under `<mode>:projectID`: Root restores it and its name on mount, drops it once the server no longer has it, and follows a rename and a `project_deleted` while mounted — leaving the mode with no project instead of the first one, and the navigation line with the mode alone; `uiutil.ActionProjectGone`, a 404 of a Project's Scene or Tag list (`uiutil.LoadOfProject`) or of the Player's `GET …/operation`, does the same. Operation shows its selected Project (`SetProject`). Project and Library instead open on their selection page (`ui/picker`): Root keeps a mode's screens — the page and the editor — mounted and switches them with visibility; the screen of a mode is kept in LocalStorage (`library:screen`, `project:screen`), so a switch of modes and a reload return to the page or the editor the person left, and `SetMode` recomputes nothing for a mode already opened; the mode opens the entity last shown (LocalStorage `project:projectID` / `library:selectedLibrary`) or the page when there is none, and the editor carries the single way back to the page in its own panel (`data-panel-back`, the arrow alone; the name is in the navigation line), which Root wires (`OnBack`, `OnHistory`) and which keeps the entity announced to the stream; `Project.SetProject` and `Library.SetLibrary` receive the announcement, and a Project or a Library deleted (or a read of it finding it gone — `uiutil.ActionProjectGone`, `uiutil.ActionLibraryGone`, both handled by `Root.entityGone`) leaves the mode with nothing selected and the page shown with its list reread . Project loads its content on the Bar's `EventProjectResync`. The event Bar keeps one SSE connection, `/events?project=<id>`, following the Project of the mode shown (Library leaves it as it is) and reopened when that changes; on open it fires `EventResync`, then `EventProjectResync` while it follows a Project. Content events and `EventProjectResync` carry the Project of their connection in the action tag `eventlog.ProjectTag`; a mode drops those of another Project (`eventlog.ForProject`), so a hidden mode showing another Project is stale until shown again. A mode whose Project the Bar already follows is resynced at once (`Bar.ResyncProject`). On a switch while connected the old connection stays (delivering only the server's events) until the new one opens, which then fires `EventProjectResync` alone: the server's data is not reloaded.
- All REST calls go through one `*apiclient.Client` created in `root` and handed to the modes (`Client.Project(id)` for a Project's content); components work on the `contract/api/v0` types directly (no UI copies) and keep IDs as `uuid.UUID` (`uuid.Nil` = none), parsing text only at LocalStorage/SSE/DOM boundaries (`uiutil.LoadID`, `StoreID`, `ParseID`).
- A call is wrapped by `uiutil.Call(compoCtx, call, onOK, onErr)`: Async → call → Dispatch; `onErr == nil` shows `toast.FromError(err)` (the server's Problem Details, a Bad Response, a Network Error, or a Client Error). `uiutil.Do` hands value and error to one callback; `uiutil.Load` reloads a list through its `Reloader`, `uiutil.LoadFor` a list that belongs to a key (the Widgets of the selected Scene: a response for another key is dropped and the load reruns). The version a write states comes from a `uiutil.Versions` (max of every response; forgotten on a 409 and on resync; a request takes a `Mark` when sent, and a response sent before a forget does not bring the old version back): each mode keeps the one Version of the Draft it shows (`draftVersions`), which every content response carries and which also says whether a reread state is newer than the one shown — there are no per-Scene or per-WidgetType versions (ADR 0016); the stack's own `{version}` is used by the undo and redo commands alone. Lookups by ID go through `uiutil.FindByID` / `IdxByID`.
- Root shows a non-dismissable banner while the server's `GrowSCADA-Schema-Version` differs from the UI's (`apiclient.OnServerVersion`).
- The PWA server (`pwaserve.Gzip`) compresses its textual answers with gzip when the browser accepts it — `app.wasm` above all, 27.6 MB down to 6.3 MB. `Content-Length` is the compressed body's, while `GrowSCADA-Wasm-Length` — stated on the wasm answer alone — carries the original: go-app's loader counts the bytes its reader yields, and the browser hands it the decompressed body, so it reads that header (the compressed `Content-Length` made its progress pass 100%). `Vary: Accept-Encoding` is stated on every answer, compressed or not, so a shared cache keeps the two forms apart; a HEAD and a refusal pass through uncompressed, since a HEAD has no body to compress. The middleware buffers an answer to know its exact length, which costs one copy of the body per answer in flight: the PWA is a development server for one person, not a CDN. The API server is not behind it, so the SSE streams are never buffered.
