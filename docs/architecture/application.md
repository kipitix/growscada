# Application Layer (`internal/server/application/`)

> Architecture reference for the GrowSCADA server. `AGENTS.md` links here: read this
> document before changing the layer it describes. Decisions are in `docs/adr/`; the
> vocabulary is in `GLOSSARY.md`.

Services (`ProjectService`, `TagService`, `LibraryService`, `WidgetTypeService`, `LibraryImportService`, `LabelService`, `SceneService`, `DeviceService`, `EnvironmentService`, `SavedStateService`, `DraftChangesService`, `DeployService`, `DiscardService`, `ProjectFileService`, `SettingsService`) accept repository interfaces injected from `main.go`. A mutation: parse input → load the aggregate → call its method → `Save`/`Delete` → `appdto`. Services publish no events (ADR 0008).

**Group move (ADR 0010, ADR 0017).** `SceneService.MoveWidgets(ctx, projectID, sceneID, version, moves)` moves a group of one Scene's Widgets in one `DraftChange` described "Move N widgets": it checks the live Project and Organization, the Draft's Version, then hands the moves to `draft.Session.MoveWidgets`, which loads the Scene once, calls `Scene.MoveWidgets` and records the before and after snapshot of each Widget that actually moved — an unchanged one is left out of the change, so undo restores every position of the group in one step. The request's input is validated before the Draft is read: an empty `moves` and a repeated `widget_id` are `invalidInput` (400), and `scene.ErrWidgetMovedTwice` from the domain is wrapped as invalid input too; an ID of another Scene is `scene.ErrWidgetNotFound` (404), `scene.ErrNothingToMove` is 409, and the Draft conflict is that of every Draft write.

**Undo and redo (ADR 0017).** `DraftChangesService` (`application/draft_changes_application_service.go`) serves the DraftChange stack of a Project's or a Library's Draft, named by a `draft.Scope`: `State` reads `{version, can_undo, can_redo, undo_description?, redo_description?}`, `Undo` and `Redo` state the Version the client saw and apply the change at the position (undo) or after it (redo). The stack's rows are internal: the repository reads the change at the position in the Draft's transaction, after the Version check, and writes the before (undo) or after (redo) snapshots, raising the Version and moving the position — no DraftChange is appended. The events are the change's inverse (a restored Tag is `tag_created`, a Widget whose binding returns `widget_updated`), so a stream and the UI see the restoration like the forward edit. An undo of a change whose rows were trimmed past the depth is not possible: `ErrNothingToUndo`/`ErrNothingToRedo` are 409; a stale Version is `ErrDraftConflict`. 

**Saved states (ADR 0021).** `SavedStateService` (`application/saved_state_application_service.go`) serves both a Project's and a Library's Draft by a `draft.Scope`: `Save` validates the title and author, reads the Draft's Version, assembles the snapshot with the same `ProjectFileBuilder` a Deploy uses (a Library's `WidgetTypes` through its read repositories) and hands it to `draft.Repository.SaveSavedState`, which locks the Draft's row, checks the stated Version (`draft.ConflictError`, 409 `draft_conflict`), refuses a Draft at its Clean Version (`draft.ErrNothingToSave`, 409 `nothing_to_save`), numbers the saved state after `last_saved_state_number`, writes it with the `saved_state_library_imports` of a Project's ProjectFile and raises `last_saved_state_number`/`last_saved_state_draft_version` and the Clean Version ; a builder refusal is `ErrDraftNotSaveable` (409 `draft_not_saveable` with the reason). The build is outside the transaction (the row lock plus the Version check give the same guarantee, as around Deploy), so `SaveSavedState` takes the assembled `draft.SavedStateContent`. `List` (`FindSavedStates`, newest first, reads content for the counts), `Find` (`FindSavedState`, a Library's with its WidgetTypes) and `Rename` (`RenameSavedState`, no Version — a title is not content) complete the service; `ProjectFile` downloads a Project's snapshot. `content_counts` is computed from the snapshot, and every saved state of a list carries the labels that mark it (one read through `LabelService.LabelsOf`; `FindSavedStates` filters by `label` in SQL), while no field says whether it was deployed or imported — a saved state is immutable and a Deploy or an Import changes nothing about it.

**Labels (ADR 0025).** `LabelService` (`application/label_application_service.go`) serves the Organization's labels: `List` (by name ignoring case, with `assigned_count`), `Create`, `Update` (a nil name or color keeps the current one; an empty color clears it) and `Delete` (its assignments go with it), then `Assign`/`Unassign` on a saved state of a `draft.Scope` (each idempotent, each locking the label and the saved state, each answering every label the saved state carries afterwards) and `LabelsOf` for a saved state list's chips. A name is trimmed, 1–100 runes on one line and unique in the Organization ignoring case (`label.ErrLabelNameTaken`, 409 `label_name_taken`); the color is `#RRGGBB` or empty, the theme's neutral one. A label is metadata, never content: no Version is stated, no DraftChange written, no undo entry made, and no ProjectFile, saved state or Deployment carries it — so a label change never conflicts with an edit of the Draft. `SavedStateService` attaches the labels to the history and filters with `SavedStateFilter`; a Project's or a Library's deletion removes its saved states' assignments through the database, the documented exception to ADR 0008, and `project_deleted`/`library_deleted` makes clients reread the history (no per-label event).

**User settings (ADR 0024).** `SettingsService` (`application/settings_application_service.go`) serves the settings of one person: `LibraryOrder` answers the IDs of the libraries the person placed (`{version: 0, library_ids: []}` for one who never reordered) and `SetLibraryOrder` stores the whole order, stating the Version it read (0: no row yet) — a stale one is `settings.ErrSettingsConflict` (409 `settings_conflict`), and two racing writes of one Version end with one conflict. The owner is `NewSettingsService`'s parameter — `settings.SingleUser` until authentication makes it the request's principal; the table, the key and the API do not change then. The order is weak references: duplicates and the zero ID are dropped, the ID of a deleted library is tolerated, and the client merges the stored IDs with the live list, so the service never reads the libraries and `GET /libraries` (and `growctl`) keeps creation order. A setting records no event and writes no outbox row: it is a view of the content, never content — no ProjectFile, saved state or Deployment carries it.

**Deploy, Rollback, Discard and Revert .** `ProjectFileBuilder` assembles the ProjectFile of a Draft over its `ProjectScope` and imports — the Tags with their supplier, the Devices, the Environments with their pairs, the Scenes with their Widgets, the WidgetTypes those Widgets use from the imported saved states, and the imports as provenance (`library_imports`, each naming its `saved_state`) — canonicalized (lists by ID, JSON keys sorted), so one Draft is always the same bytes; a dangling reference (a Widget of a type no imported saved state holds, a Tag supplied by a Device of another Project, a PortBinding naming a Tag the Draft lacks) fails the build. A Deploy takes a **saved state** (a `draft.SavedState`), not the Draft: `DeployService.Deploy` reads saved state `n` of the Project's Draft (a number the Project lacks is `draft.ErrSavedStateNotFound`, 404) and hands its ProjectFile to `RuntimeNode.DeploySavedState`, which stores it as a Deployment with `cause` `deploy` and `saved_state_number` `n`; a Deploy of the saved state the Project runs already is 409 `ErrNothingToDeploy` (the Runtime node's own sentinel, translated by `inprocess`), checked under the advisory lock that numbers the Deployment, so two racing Deploys of one saved state make one. The Engineering node keeps no copy of what it sent: the Deployment is the only truth (ADR 0014). The old `DeployService` of a Draft and its `Preview`/`DeployState` are gone, and so are `POST …/deploy` (410) and `GET …/deploy/preview`: the Project mode reads `GET …/deployment` (with `saved_state_number`) and the saved states. The Runtime node's `DeploymentService` serves `List` (newest first, no documents, empty for a Project never deployed), `Find` (by number, with the document; `ErrDeploymentNotFound`), `DeploySavedState`, `DeployFile` (a project file stored as a Deployment with `cause` `file` and no saved state, for a Runtime-only node, ADR 0018) and `Rollback` — a new Deployment with an earlier Deployment's document and `saved_state_number` copied (`cause` `rollback`, `rolled_back_from` the copied number), committed with the same derived-copy diff as a Deploy; a document equal to the running one is 409 `ErrNothingToRollback`. A Rollback publishes the same `deployment_created`. A Project that is not live is `project.ErrProjectNotFound`. `DiscardService` has two commands over the Draft, each one transaction (`draft.Repository.Replace`, clearing the stack, answering 200 with the Draft's `{version}` and `warnings`): `Discard` resets the Draft to its last saved state (409 `ErrNothingToDiscard` without one) and `Revert` to the running Deployment (409 `ErrNoDeploymentToDiscard` without one). A replacement whose content is a saved state's makes its Version the Clean Version — `Discard` and `Load` always, `Revert` when the Deployment it restores was made from a saved state and no import was dropped —, so the Draft reports no unsaved changes afterwards, whichever saved state it is (ADR 0016, amendment 2026-11-16). A Library Import the target names but this server cannot write — its Library is gone, or its saved state is — is dropped with the Widgets of that Library's WidgetTypes, so the Draft stays writable . The Tag states and the Device Tokens are the Runtime node's and stay.

**Project files (ADR 0018).** `ProjectFileService` (`application/project_file_application_service.go`) serves a Project's files: `Draft` answers the Draft as the `ProjectFile` the builder assembles (a Draft the builder refuses is `ErrDraftNotDeployable`, a 409 carrying its reason), `Deployment` the document the Runtime node stored (`RuntimeNode.FindDeployment`), `Open` replaces the whole Draft with a document as one DraftChange, "Open a project file" (the Version is the `draft.Repository.Update` gate, the redo tail is dropped and the stack stays; a document whose canonical form is the Draft is `ErrNothingToOpen`, and the comparison is skipped when the Draft cannot be built, so a valid file repairs it). A file deploy is `ProjectFileService.Deploy` : the same validator, then `RuntimeNode.DeployFile`, which stores the document with cause `file` and no saved state — nothing stands between, and a failed Deploy leaves nothing behind. `RuntimeNode.DeployFile` remains for a Runtime-only node. Both commands share one validator (`application/project_file_validator.go`): the schema version is read first — the same MAJOR, the MINOR not newer, a newer file answered as such — then the document is decoded strictly, its `project_id` must be the Project of the path, and the invariants and cross-references of the format are checked (names, types, protocols, sizes and script languages; unique IDs and natural keys, a Scene's ID among them; a Tag's supplier Device and its PortBindings, each on a port its WidgetType declares and with a hint that accepts the Tag's TagType; a pair's Environment and Device; each WidgetType the Widgets use and each Widget in one Scene); finally the ProjectFile is rebuilt from the would-be content and compared with the canonicalized input, so a document missing, extra or normalized differently is refused. Every problem is reported together as 400 with `Problem.file_issues: [{path, message}]`. Opening also checks every import against a live Library and its saved state (`lockLocalImports`) and locks those rows `FOR SHARE` inside the Draft's transaction; a file deploy does not, because the document carries its WidgetType copies. `draft.Session.Open` (`domain/draft/open.go`) records only the entities that differ, with the ordinary events, so an open is one DraftChange proportional to the difference and undo restores the previous Draft. A Discard and a Revert lock the imports they keep `FOR SHARE` in their transaction; an import that disappears between the check and that lock is still `DeploymentNotDiscardableError` (409 `deployment_not_discardable`); the third Deployment cause is `DeploymentCauseFile` (`file`).

**Tag definition and Tag state (ADR 0011).** `TagService` keeps the Tag definitions of the Draft (entities of it, ADR 0016) and reads each with its state through `RuntimeNode` (`FindTagStates`; a definition without a state shows the initial one, and so does every one when the Runtime node fails to answer). `application/runtime.TagStateService` is the Runtime node's: `SetTagValue` (the hot path, `PATCH …/value`: the state read with the check of its Project in one query, `IsProjectLive` only on a miss; no expected Version, the latest write wins; the writer's Device is checked against the Tag's supplier in the same query (`tag.ErrTagNotSuppliedByDevice`; a Tag people write has `tag.NoSupplier`); the Tag's row is locked, the stored value and Quality compared, and only a change appends a `tag_state` entry to `runtime.journal` — the state's `seq` is that entry's position, so `runtime.tag_state_seq` is gone; a repeat keeps the position and moves `last_write_at` alone (ADR 0019); the write runs apart from the request's cancellation, and after a change is stored it publishes `tag_updated` to the EventBus itself, through the queue of `eventbus.AsyncPublisher` (one goroutine does the SSE fan-out; a full queue makes the write wait) — no outbox row, at-most-once), `FindTagStates`, `RemoveTagStates`, `RemoveProjectTagStates`; its own `ErrInvalidInput`. The copies are the running Deployment's alone: `CreateTag` and `DeleteTagByID` write nothing to the Runtime node, and `UpsertDefinitions` and `Delete` take the advisory lock of `CreateDeployment` and check for a Deployment in the same transaction, so a Tag created in the Draft takes no value (404) until the next Deploy names it, and a Tag deleted in the Draft keeps its state until the next Deploy drops it (ADR 0011, amendment 2026-11-04; the bridge of the Draft is gone).

**Journal read and live stream (ADR 0019).** `application/runtime.JournalService` is the Runtime node's read side of the Journal, and is deliberately **not** in the Engineering node's `RuntimeNode` port (the Engineering node never reads it): `Read(ctx, projectID, from, limit)` returns the Project's entries after the position `from` (exclusive) in the order of their positions, at most `limit` of them, refusing a negative `from` or a `limit` outside `(0, JournalMaxPageSize]` with its `ErrInvalidInput`; `Position(ctx, projectID)` returns the Project's current position (`COALESCE(MAX(seq), 0)`, the start of a stream that names none). The page constants are `JournalPageSize = 100` and `JournalMaxPageSize = 1000`. `postgres/runtime.NewJournalRepositoryPostgres` implements `JournalRepository` (`FindAfter`, `Position`) over `runtime.journal`: `WHERE project_id = $1 AND seq > $2 ORDER BY seq LIMIT $3`, each row decoded by `journal_codec.go`; the Project's liveness is checked first (`liveProject`, as `FindAll` of the Deployments does), so a deleted Project is `project.ErrProjectNotFound`, never an empty page, and another Project's entries are never returned. The routes are `GET …/journal?from=<seq>&limit=<n>` (200 `JournalResponse{entries}`; `from` defaults to 0, `limit` to 100; a non-numeric or out-of-range value is 400) and `GET …/journal/events` (SSE). The stream subscribes to `tag_updated` and `deployment_created` **before** it reads its start position, then reads the table page by page until a page is empty and waits: a wake-up only makes it read again, so it needs neither the event's payload nor an outbox row. The start is `?from=` (which wins), else the SSE `Last-Event-ID` header, else `Position` (new entries alone); every message is `id: <seq>` and `data: <Entry>`, the record document as it is. Delivery is at-most-once and a reconnect with `Last-Event-ID` catches up exactly, because the stream reads the table; two racing commits may reach it out of order or one may be missed (ADR 0019). A safety ticker (5 s) rereads in case a signal is lost, and signals collapse into a channel of capacity 1. The stream is its own handler, not `eventHub`: `maxSSEClients` does not cap it, it names no client and holds no lock, and `/events` keeps `tag_updated` and `deployment_created` for the other modes and the Device Gateway (ADR 0020); removing them is a separate task.

**Operation read model (ADR 0020).** `application/runtime.OperationStateService` is the Runtime node's starting state of Operation: `Get(ctx, projectID)` answers `OperationState{Position, Deployment, Deployed, TagStates}`, and is **not** in the Engineering node's `RuntimeNode` port. It composes existing reads in one order — `JournalService.Position`, then `DeploymentService.FindCurrent`, then `TagStateService.FindTagStates` by the IDs of `Deployment.Content.Tags` — so a Deploy committed between the reads has a position above the snapshot and the Journal stream replays it (reading the position last could hide it from Operation; entries already in the states come again and are harmless, ADR 0020). A Project without a Deployment is `Deployed == false` with the position and no states, not an error; every Tag of the Deployment is present, and one the Runtime node holds no state of is filled in by `tag.NewTagType(definition.Type).InitialState` — its TagType's zero value, Quality `bad`, `seq` 0, no `written_at`; an unknown type in the document is an error. A Project that is not live is an error wrapping `project.ErrProjectNotFound`. The configuration is the Deployment's `projectv0.ProjectFile` as it is: the model builds no render shapes and imports neither `domain/scene` nor any Engineering schema (ADR 0011). No repository, migration or outbox row is added. The PWA renders it with `ui/player` over the Journal stream . `GetAt(ctx, projectID, at)` (ADR 0023) is History's starting state at a past position: it clamps `at` to `JournalService.Position`, asks `CheckpointRepository.Nearest` for the latest snapshot at or before it — none is the empty state at position 0, never an error — and answers `{Position: checkpoint.Seq, Deployment: DeploymentService.Find(number), TagStates: the snapshot's}` with `WrittenAt` nil and the Name and Type filled from the Deployment's document where it names the Tag. `at < 0` is `ErrInvalidInput`; a Project that is not live is `project.ErrProjectNotFound` through the position or the nearest read.

**Checkpoints (ADR 0023).** A Checkpoint is an immutable snapshot of a Project's operational state beside the Journal, not an entry of it: `runtime.checkpoints` is keyed by `(project_id, seq)` — the Journal position it describes — and its payload is the Deployment in force (`number`, `cause`, `rolled_back_from`, `saved_state_number`; the document stays in `runtime.deployments`) and every Tag state with its own position. The record is `contract/record/v0.Checkpoint` (0.7). The Runtime node writes one in the transaction of every Deployment — a Deploy of a saved state, a Deploy from a file and a Rollback — after `refreshCopies`, at the position of the `deployment` entry, so the snapshot includes the initial states of the Tags the document adds (`insertDeployment` returns that position). `application/runtime.CheckpointService` adds the periodic ones: `Run` scans every `CheckpointScanEvery` (a minute), and `RunOnce` (for tests) asks `CheckpointRepository.DueProjects` for the live Projects whose position has moved `CheckpointEveryEntries` (10 000) past their latest Checkpoint and takes one `CheckpointRepository.Snapshot` of each — one `REPEATABLE READ` transaction reading the position, the Deployment and every `runtime.tag_states` row, inserted with `ON CONFLICT DO NOTHING`. A failed pass is logged and retried; no outbox and no policy take part. `postgres/runtime/checkpoint_codec.go` encodes and decodes the record (`schema_version` as a string, payload `{deployment, tag_states}`), and `NewCheckpointRepositoryPostgres` serves `Nearest` (the latest Checkpoint at or before a position, refusing a Project that is not live), `DueProjects` and `Snapshot`. The Engineering node's `RuntimeNode` port does not change, and the service is wired in `main.go` beside the dispatcher and the policy runner (a one-shot run in tests; `servertest` starts no ticker). Reading a past state is `OperationStateService.GetAt` : `GET …/operation?at=<position>` answers the nearest Checkpoint at or before the position — before the first one the empty state at 0, a future one clamped — with its Deployment's document and its Tag states; `apiclient.ProjectClient.OperationAt` reads it and History starts from it, then reads `GET …/journal?from=<seq>`.

**Projects (ADR 0006).** `ProjectService` keeps a Project's name and description : `CreateProject` and `UpdateProject` parse them — a `Description` is trimmed and at most 500 characters, an absent one keeps the current one — and `UpdateProject` records one `project_updated`; reads also carry `has_unsaved_changes`, the read model of a Project's selection row: the Draft's own `HasUnsavedChanges` — its Version above its Clean Version —, read from the Draft's row alone (`draft.Repository.Read`), false for a Draft never saved and for one nothing was written to (ADR 0016, amendment 2026-11-10). The description is an attribute of the aggregate, never part of its ProjectFile. The repositories of a Project's content are opened per Project: `ProjectScopes.ForProject(p)` → `Tags`, `Scenes`, `LibraryImports`, `Devices`, `Environments`, `EnvironmentDevices`, every query scoped by `project_id`, and their writes are gone: the content is the Project's Draft. `ProjectContent` (the Tag, Scene, Device and Environment services) first checks that the Project is live and of the server's Organization (`ErrProjectNotFound` → 404 of the Project), then opens its scope; the hot path of Tag values (`TagStateService.SetTagValue`, the Runtime node's) checks it in the state's own query and reads the Project only on a miss, and so do the lists the UI reloads on every event (Tags, Scenes, Devices and Environments by `FindAllInLiveProject`, a Scene's Widgets by the Scene's `FindByIDInLiveProject`), the Project read only when nothing is found. Deleting a Project only marks it; `NewProjectCleanupPolicy` purges the whole Draft in one transaction over it (`draft.Repository.Purge`, ADR 0016) with the events of the removal, then its Tag states through `RuntimeNode`, and the Project's row last (its Device Tokens go with it by the foreign key, and `RuntimeNode` forgets the ones its cache resolved, or a token of the removed Project would keep authenticating; a state upserted late holds the row, and the next run removes it). A Draft's content is written through its repository, which locks the Draft's row, checks the Project is live and the Version the write states, and writes the touched rows in the same transaction; no separate row locks remain. Job keys of a Project's content start with `project:<id>`.

**Libraries (ADR 0007, ADR 0016, ADR 0021).** A Library's Draft is a `draft.Draft` too: its WidgetTypes are its entities and every write of them (`WidgetTypeService.CreateWidgetType`/`UpdateWidgetType`/`DeleteWidgetTypeByID`, each stating the Draft's Version) is one transaction over `engineering.drafts` and one DraftChange; reads stay on `WidgetTypeRepositories.ForLibrary`. A Project sees WidgetTypes only through its Library Imports: `ProjectScope.LibraryImports.FindImportedWidgetType` finds a Widget's WidgetType in the imported saved state, and a Scene's write checks the type in that saved state inside the Draft's transaction (`library.ErrWidgetTypeNotFound` is invalid input) for each Widget added or retyped; a switch or removal of an import (`LibraryImportService.PutLibraryImport`/`DeleteLibraryImport`, the presence of an import decides add or switch and `version` is the Draft's) runs `ImportImpactOf` on the Project's Widgets read in the Draft's transaction, in the same DraftChange that switches the import. An import locks the live Library's row `FOR SHARE`, so a Library is marked deleted only while no live Project imports it; `LibraryService.DeleteLibraryByID` also asks the Runtime node (`RuntimeNode.DeploymentNamesLibrary`) whether the running Deployment of any live Project names a saved state of the Library, and answers 409 `ErrLibraryInRunningDeployment` if it does — a Discard of that Deployment could not restore the import. Old saved states and Deployments do not block the deletion: their documents carry the WidgetType copies they need (ADR 0007). A Library publishes nothing: `Save` fixes its saved states and a Project imports one of them, so there is no note and no publication, and there is no path that turns a saved state into a public one . `Discard` is synchronous and one transaction of the Draft (`Replace` with `session.ReplaceWidgetTypes`): it names the WidgetTypes of the **last saved state** back (409 `ErrNothingToDiscard` without one), clears the stack, makes the new Version the Clean Version and answers 200 `{version, has_unsaved_changes}`. `DraftState` answers the Draft's own unsaved-changes flag, never a comparison of Versions. There is no mark, no `library_discard_started`, no `NewDiscardLibraryPolicy` and no `library_discarding`. `NewLibraryCleanupPolicy` removes a marked Library with its Draft and saved states once no Project imports it; it re-checks no Deployment, because a marked Library is already gone for the API and a Deployment made from a file afterwards degrades to a warning at Discard.

**Concurrency: the Draft's Version (ADR 0022).** There is no editing lock: a Draft is edited and saved freely, and the one token of a write is the Version of its content (ADR 0016). Every write of a Project's or a Library's Draft states that Version; `draftRepositoryPostgres.Update` reads the Draft's row `FOR UPDATE` and answers `draft.ConflictError` (409 `draft_conflict`, the current Version in `Problem.draft`) when the stated one is stale, so two Engineers on one Draft see each other's writes as a conflict and retry. Undo and redo are shared: the second Engineer may undo another's DraftChange. A Save builds the snapshot outside the transaction and `draft.Repository.SaveSavedState` checks the stated Version under the Draft row's lock (409 `draft_conflict`); a Deploy takes a saved state and reads no Draft, a Library's saved state is only imported, and Import is a Draft write like any other, so only the last of them states a Version. `CheckVersion` has no caller. The editing-lock routes of a Project and a Library answer `410 Gone`; `?client=` on an SSE stream is accepted and ignored.

**Events (ADR 0008).** One transaction changes one aggregate. The aggregate records its own events (`Create…` records Created, `Reconstitute…` — for repositories — nothing; changes and `Delete` record theirs; see `event.Recorder`). The repository's `Save`/`Delete` writes the state (CAS on the loaded Version) and the pending events into the `outbox` table in one transaction; `outbox.Dispatcher` delivers them after commit, in the order of their transactions (`tx_id`; a row waits for every older transaction to end, so writers take no lock), to the `EventBus` (SSE) and deletes each row — at-least-once. Changes spanning aggregates are **policies** (`application.Policy`: `Name`, `JobKey(event)`, `Run(ctx, key)`): in the transaction that deletes a delivered row the dispatcher enqueues a job per policy that keys the event into `policy_jobs`; jobs with the same key merge (`generation`), and the `outbox.PolicyRunner` runs them apart from delivery, retrying a failure forever with backoff (1 s ×2 → 5 min). A policy brings state into line with what it reads when it runs, never with the event's payload (`NewProjectCleanupPolicy`: see Projects; `NewLibraryCleanupPolicy`: see Libraries). `NewUnbindDeletedTagPolicy` and `NewWidgetReconciliationPolicy` are gone (ADR 0016): a Tag's bindings are removed by the DraftChange that deletes the Tag, and an import switch removes the bindings it breaks in its own change. A Draft's content is one aggregate, so its writes state the Draft's Version, and `retryOnRace` remains only for writes that are not DraftChanges (the cleanup of a Project, service operations). Writes of Tag states, of the per-user settings and of labels with their assignments are the exceptions to all of this: no aggregate of people, no outbox (ADR 0011, ADR 0024, ADR 0025).

`appdto/` structs are the boundary between the domain and the outside world — not the REST DTOs.

**Devices and Environments (ADR 0004, amendment 2026-11-01).** `DeviceService` and `EnvironmentService` are the Engineering node's: a Project's Devices (protocol and configuration), its Environments and the pairs `(Environment, Device)` with their connection parameters. `DeviceConfigService` (`application/runtime`, the Runtime node's) serves a Device Gateway the configuration of its Device in one Environment from the running Deployment: the copies `runtime.devices`, `runtime.environments`, `runtime.environment_devices` and `runtime.tags`, read in one REPEATABLE READ transaction, never the Draft — a Device outside the Deployment is 403, an Environment or a pair it lacks is 404 (Q5). The Device Token is the Runtime node's: `application/runtime.DeviceTokenService` issues, rotates and revokes the one token a Device has, resolves `Authorization: Bearer gsc_dev_…` to its Device and Project (hash looked up in `runtime.device_tokens`, result cached in memory until the token changes), and holds no secret: the token is stored as its SHA-256 hash and its fingerprint and shown once.
