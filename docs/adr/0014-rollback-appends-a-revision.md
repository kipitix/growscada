# Rollback appends a Revision; the Revision is the only truth

A Rollback makes an earlier Revision operational again on the Runtime node alone, without the Draft and without an Engineering node. It does not rewrite history: it copies the earlier Revision's ProjectFile into a new, numbered Revision (`cause` `rollback`, `rolled_back_from` the earlier number, `deployed_at` now) in the same transaction that rebuilds the Runtime node's derived copies by the same diff a Deploy uses, so unchanged Tags keep their values and `seq`, a Tag the document no longer names loses its state, a Tag it adds or whose TagType changed starts from its TagType's zero value with quality `bad`, and every Device Token survives. The new Revision's number is the greatest stored plus one, taken under the advisory lock a Deploy takes, and `revision_created` (the same event, no new fields) tells readers to reload. A Rollback whose document is the running Revision's unchanged is refused `409 nothing_to_rollback`, a target Revision the Project does not have is `404`, and a Project being discarded refuses it `409` like a Deploy: the Discard policy reads the running Revision when it runs, and a Rollback in the middle would change what the Draft is restored to.

The list of Revisions is the Runtime node's, newest first, with each Revision's number, time and cause, beside its full document at `GET /projects/{id}/revisions/{n}` and the Rollback at `POST /projects/{id}/revisions/{n}/rollback` (201 with the new Revision's summary). A Project without a Revision answers an empty list, not 404. The Project mode of the PWA is the only UI entry point for now: it opens the list from the Deploy bar and confirms a Rollback after showing a summary — counts of the Scenes, Widgets, Tags, Devices and Environments — of the selected Revision for comparison. A Runtime node without an Engineering node therefore exposes Rollback over its REST API alone; making it available to an operator on such a node belongs to Operation/Player (task 43) and the embedded-Revision build (task 51).

Rollback is also why the Engineering node keeps no copy of the last ProjectFile it sent. That copy could no longer mean "the Revision the Project runs" once a Rollback happens elsewhere, and its only remaining readers were a dead `State` and the repair path of a failed copy write; Project mode reads `deploy/preview`, which compares the Draft with the Revision through `RuntimeNode` already. The copy, its repository, `DeployService.State`, `ErrRevisionCopyNotSaved` and the 500 that carried it are removed: a Deploy of a Draft equal to the running Revision is always `409 nothing_to_deploy`. See the amendment to ADR 0013.

A Rollback is an operational act and belongs in the Journal, but the Journal does not exist yet: recording it is task 42, and this task only notes it. The Revision's `cause` and `rolled_back_from` are what task 42 will read.

## Considered Options

- A separate `revision_rolled_back` event: rejected. Consumers do one thing on `revision_created` — reload the running configuration — and the cause is available in the list, so a second type would only multiply the branches without a reader.
- Rewriting the Revision's number or deleting the Revisions in between: rejected. History is the operational record; a Rollback is a new act, not an erasure of the Deploys that followed.
- Allowing a Rollback whose content equals the running Revision: rejected. It would grow the history with a Revision that changes nothing; `nothing_to_deploy` already refuses the Deploy counterpart.
- Resetting every Tag state on Rollback: rejected. A Rollback is a configuration switch, not a process reset; Tags the earlier document kept keep their values, as after a Deploy.
- Keeping the Engineering node's copy of the last ProjectFile: rejected. After a Rollback the Engineering node did not send the running Revision, so the copy would silently disagree with Operation; keeping it correct would require the Runtime node to write the Engineering schema (forbidden by ADR 0011) or the Engineering node to follow every Revision event.
- Returning the running Revision on a duplicate Rollback with 200: rejected. It would make a write look successful while changing nothing and would hide a client that retried a lost answer; 409 says plainly that there is nothing to roll back.
- A `GET …/revisions/{n}` that returns only counts: rejected. The Revision document is already the shape the API serves for the running one; the UI can summarise it and a tool can inspect it without a second shape.
- Putting the Rollback UI in Operation: rejected for now. Operation is read-only and is rebuilt as the Player by task 43; Project mode already owns Deploy and Discard, and the Runtime-only entry point is the REST API until then.
