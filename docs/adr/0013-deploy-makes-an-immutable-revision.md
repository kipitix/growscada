# Deploy makes an immutable Revision; Discard resets the Draft to it

A Deploy takes the whole Draft of a Project — its Tag definitions, Devices, Environments with their pairs, Scenes with their Widgets and the copies of the WidgetTypes its pinned Library Releases hold — assembles one ProjectFile and hands it to the Runtime node. The Runtime node numbers it and stores it as a Revision (`runtime.revisions`, an immutable JSON document: the number, the deployment time and the document) in one transaction, rebuilding its copies of the Tag definitions, the Devices, the Environments and their pairs from the document by diff, so the Tag states and the Device Tokens survive. A Tag the document adds, or one whose TagType changed, starts from its TagType's zero value with quality bad; a Tag the document drops loses its state with its copy; any other state is left as it is, so a Deploy does not reset the process. Operation runs exactly one Revision and reads it through `GET /projects/{id}/revision`; the Tag states are its own snapshot (`GET …/tag-states`), continued by `tag_updated`. Nothing of the Draft is visible in Operation until a Deploy makes a new Revision, and the `revision_created` event (at-most-once, like `tag_updated`, published by the Runtime node after the commit) is the only signal that reloads it. The number is the Runtime node's, not the Engineering node's: a Runtime node may serve several Engineering nodes, and the Revision is the Runtime node's data.

The JSON document is the truth: everything the Runtime node derives from it — its copies of Tags, Devices, Environments, pairs and the ProjectFile a Runtime node serves to a Device Gateway — can be rebuilt. The Engineering node keeps its own copy of the last ProjectFile it sent (`engineering.project_files`), but it is only a cache: it shows Revision and "unreleased changes" in the Project mode, and a failure to save it does not undo the Deploy. "Nothing to deploy" compares the freshly assembled document, canonicalized (lists sorted by ID, JSON keys sorted), with the Revision the Runtime node holds — never with the Engineering node's copy, which may be missing; the copy is saved then, so the next Deploy of the same Draft is refused. No dirty flag exists: the Draft is compared byte for byte.

A Discard resets the Draft to the Revision the Project runs, dropping every change made since the Deploy. It touches many aggregates, so it is a policy (ADR 0008): the request marks the Project and answers `202` at once; the policy prunes what the Revision does not name in the reverse order of references (Scenes, Library Pins, Tags, Environment Devices, Environments, Devices), restores it in the forward order (Library Pins, Devices, Environments, pairs, Tags, Scenes with their Widgets), recreating the missing aggregates under their IDs, each aggregate in its own transaction, and clears the mark last. While the mark stands the Draft is read-only — every write of its content checks it in its transaction, and Deploy refuses — so the policy never overwrites an edit and a Deploy never captures a half-restored Draft. The Runtime node is not touched: the Tag states and the Device Tokens outlive a Discard, as they outlive a Deploy; only the next Deploy drops the state of a Tag the Revision lacks.

## Amendment 2026-11-04: the Engineering node keeps no copy; Rollback appends a Revision

A Rollback (task 36) makes an earlier Revision operational on the Runtime node alone, so the Engineering node's copy of the last ProjectFile it sent no longer names the Revision the Project runs. The copy was only a cache, and its remaining readers go with it: Project mode reads `deploy/preview`, which compares the Draft with the Revision through `RuntimeNode`; `DeployService.State` had no caller; and the repair path of a failed copy write protected a copy nothing needs. `engineering.project_files`, `ProjectFileCopies`, `DeployService.State`/`DeployState` and `ErrRevisionCopyNotSaved` are removed, and a Deploy of a Draft equal to the running Revision is always refused `409 nothing_to_deploy` — there is no copy to save or repair. Project mode learns the Revision and whether there are unreleased changes from the preview alone.

A Rollback is a second way a Revision comes to be: the Runtime node copies an earlier Revision's document into a new numbered one, rebuilds its derived copies by the same diff as a Deploy (Tag states of unchanged Tags and every Device Token survive), and publishes `revision_created`. History is never rewritten. The API, the guards and the UI are in ADR 0014.

## Amendment 2026-11-05: a third way a Revision comes to be

A Deploy of the Draft (ADR 0014's Rollback was the second) is no longer the only way a Revision is made: a ProjectFile can be validated and deployed as a Revision directly, without the Draft and without an EditLock, its `cause` being `file`. The document is the same one this ADR describes, self-contained with the WidgetType copies, and the Runtime node stores it and rebuilds its derived copies by the same diff. The Engineering node's Deploy — the whole Draft as a ProjectFile — is unchanged, and a Draft whose document equals the running Revision is still refused `409 nothing_to_deploy`. The rest of the decision — open, export and the local-Library check — is ADR 0018.

## Considered Options

- Live editing of the running configuration (a Draft and Operation sharing the aggregate): rejected. It gives no atomic switch of what Operation runs, no review before the plant changes, and no history of what was running.
- Deploying each aggregate as it changes: rejected. Operation would run a mix of old and new configuration, and the ProjectFile would stop being a portable snapshot.
- Storing the Revision as a relational tree instead of one JSON document: rejected. The Revision is read as a whole, never queried by parts, and a document is what makes it immutable and portable; the derived copies are relational because they are written to and joined.
- Deleting and reinserting the Runtime copies on Deploy: rejected. The foreign keys would cascade into `tag_states` and `device_tokens`, dropping the process state and the secrets the Deploy is not about; the copies are rebuilt by diff.
- Comparing the Draft with the Engineering node's copy to decide "nothing to deploy": rejected. A Deploy whose copy failed to save would pass for a change and make a Revision of identical content; the truth must be the Revision.
- A dirty flag kept by the Engineering node: rejected. Every path that edits the Draft would have to set it, and a missed one silently loses a Deploy.
- Discard as one transaction over the whole Draft: rejected as an exception to one aggregate per transaction (ADR 0008), for a mechanism the Draft aggregate (task 38) will replace.
- Keeping in a Revision the Tag states, the Device Tokens or the aggregate versions: rejected. None is configuration: states are process state, tokens are secrets, and a Revision is immutable while versions change.

## Amendment 2026-11-08: the Revision is a Deployment (task 72_9)

The runtime entity this ADR calls a Revision is called a **Deployment** now. Nothing of the decision changes — a Deploy still makes one immutable numbered document from the Draft, Operation still runs exactly one, and the document is still the truth — but the names follow: `runtime.revisions` is `runtime.deployments` (its `n` column is `number`), `RevisionResponse`/`RevisionCause` are `DeploymentResponse`/`DeploymentCause`, the event `revision_created` is `deployment_created`, and the routes `/projects/{id}/revision` and `/projects/{id}/revisions…` are `/deployment` and `/deployments…` (the old ones answer `410 Gone`). Read every "Revision" below as "Deployment".

## Amendment 2026-11-08: a Deploy takes a Release (task 72_4)

A Deploy no longer takes the Draft: it makes one **Project Release** the running Deployment (`POST …/projects/{id}/releases/{n}/deploy`), and the order of an Engineer's work is Save → Release → Deploy. The Runtime node's `DeploymentService.DeployRelease` stores the Release's ProjectFile with `cause` `deploy` and `release_number` of the Release; a Deploy of the Release the Project runs already is `409 nothing_to_deploy`, checked under the advisory lock that numbers the Deployment, so two racing Deploys of one Release make one. The Engineering node's `DeployService` and its `Preview`/`DeployState` are removed, the old `POST …/deploy` answers `410 Gone`, and `GET …/deploy/preview` is gone: the Project mode reads `GET …/deployment` (the Deployment and its `release_number`) and `GET …/releases` instead. Note and the rest of the Release are ADR 0021.

A **Discard** resets the Draft to its last **Commit** now — the saved state, dropping unsaved work — and answers `409 nothing_to_discard` when the Project has no Commit. Resetting the Draft to the running Deployment is the separate **Revert to deployed** (`POST …/projects/{id}/revert-to-deployed`, `409` when the Project runs no Deployment). Both are one transaction over the Draft and clear its stack; neither touches a Commit, a Release or a Deployment. A project file deploy is a Release with origin `file` (ADR 0018).
