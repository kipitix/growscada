# A Commit is an immutable snapshot of the Draft, fixed by Save

An Engineer needs a named point of history to return to, to release and to deploy, while the Draft stays editable without a lock (ADR 0022) and every edit is still written at once as a DraftChange (ADR 0016, ADR 0017). A DraftChange is a reversible intent, not a point of history: it holds the before and after state of what one write touched, is trimmed with the stack and is cleared by Deploy, Release and Discard. Something must therefore hold the whole Draft as it was when the Engineer decided it was worth keeping, and it must outlive the stack.

This ADR starts the model; task 72_8 gives it its final form together with Releases and the Deploy that runs one.

## Decision

- **Commit is an entity of the Draft**, like DraftChange, not an aggregate of its own. It belongs to exactly one Draft (`draft.Scope`), is numbered 1, 2, 3… within it, and is removed with it by the foreign key. A Save is one transaction over the Draft's row, so a Commit is written in the same transaction as the last Version it fixed, and no policy is needed.
- **Commit is immutable.** It holds its `ID`, number, title, Author, time, the Version of the Draft it fixed and its content. The content is the canonical ProjectFile of a Project's Draft — assembled by the same builder a Deploy uses — or the copies of a Library's Draft WidgetTypes, the same value object a Library Release holds. The encoding is internal, with a format version, like the outbox and DraftChanges (ADR 0005). Only the title changes, through `WithTitle`, which records `commit_title_updated`; the snapshot never does.
- **Save fixes the Draft; it does not save it.** The Draft's edits are still written at once, and Save writes no DraftChange, raises no Version and touches no undo/redo stack. The Draft remembers `last_commit_number` and `last_commit_draft_version`, so a Save of a Draft at the Version of its last Commit is refused as `nothing_to_save`. The UI shows unsaved changes as the Draft's Version above its last Commit's.
- **The snapshot is built before the transaction and checked against the Version.** The builder reads the Draft over several queries; the repository then locks the Draft's row, checks that the stated Version is still current (a write that landed meanwhile is 409 `draft_conflict`), refuses an unchanged Draft and inserts the Commit under the row lock. The row lock also makes the number unique without a retry loop. Building inside the transaction was rejected for the first version: it would hold the row lock for as long as the whole Draft is read, and the Version check gives the same guarantee.
- **Renaming a title states no Version.** A title is not content: `commit_title_updated` and the API's `PATCH …/commits/{n}` work after another Engineer's writes, and the snapshot is untouched.
- **The REST API and the events.** `POST …/commits` takes `{version, title, author}`, `GET …/commits` lists newest first without content, `GET …/commits/{n}` reads one (a Library's with its WidgetTypes), `PATCH …/commits/{n}` renames it and `GET …/projects/{id}/commits/{n}/projectfile` downloads a Project's snapshot. A Project's events go to its stream, a Library's to the server's; the modes reload the history on them and never the Draft's content. The API's MINOR rises.
- **A Project Release is made from a Commit and copies it (task 72_3).** It is an aggregate of its own, with its own table and repository, outside the Draft: a Release holds its number within the Project, the Commit's number and title at the moment of publication, a note, the Author, the time, its origin (`commit`; `file` comes with task 72_4) and a copy of the Commit's content. It therefore survives the Commit, the Draft, future Commit retention and the deletion of a Library whose content it copied; it writes nothing of them and needs no Draft Version. One Commit is published at most once. The content is immutable; the note is metadata and changes on its own (`release_note_updated`), as a title does. The Project's Release list is the Engineering node's read model: whether a Release is the one running is the Deployment's answer (task 72_4), not a flag on the Release.
- **Tasks 72_4…72_8 build on this.** A Release is deployed by task 72_4, Library Releases are made from Commits by task 72_5, and retention of Commits comes later. `CommitResponse.released` tells whether a Project's Commit is published; the history is kept whole.

## Considered Options

- **Commit as an aggregate with its own repository and policy**: rejected. It shares the Draft's transaction, its liveness and its CASCADE, and a policy between the two would only add a window in which a Commit names a Draft that has moved.
- **A full Draft snapshot per DraftChange**: rejected with ADR 0017: the volume is the Draft times the depth of the stack, and the stack is trimmed.
- **Tagging a DraftChange as a point of history**: rejected. The stack is cleared by Deploy and Release, so the tags would disappear exactly when the history matters, and undo after a Save would not be a Save.
- **Content fetched and hashed from the Draft on read instead of stored**: rejected. The builder and the whole content may change later; a Commit must keep the bytes it fixed.
- **Building the ProjectFile inside the Save transaction**: rejected for the first version. It would hold the Draft's row lock through every read of the builder; the Version check around a build outside it gives the same "the snapshot is the Draft at this Version" guarantee, and Deploy already works that way (ADR 0022).

## Consequences

- A Commit's storage is proportional to the Draft: the whole ProjectFile per Save. Retention is a later task; until then every Save is kept.
- The Draft gains two counters and the history gains a table (`engineering.commits`, `engineering.commit_library_pins` for a Project's pins). The pins of a Commit or a Project Release do not keep a Library from being deleted: the documents are self-contained, and only a running Deployment does (task 71, ADR 0007). A Project's Releases gain `engineering.project_releases` and `engineering.project_release_library_pins`, a copy of the ProjectFile and of its pins.
- A Save whose Draft the builder refuses is 409 `draft_not_saveable` with the builder's reason, exactly as a download of the Draft is 409 `draft_not_deployable`: an inconsistent Draft is neither deployable nor a point of history.
- Save does not require a Deployment: a Project that has never been deployed has Commits.
- The Author is a name in the request, stored with the Commit and shown to other Engineers; tasks 49/50 replace it with a User.
- The undo/redo stack is unaffected: Save neither clears it nor adds to it.

## Amendment 2026-11-08: a Library Release is a Commit's publication too

Task 72_5 gives a Library the same pair as a Project. A Library Release is made from a Library's Commit: the copies of the Commit's WidgetTypes go into `released_widget_types` in the same transaction as the Release row, the Release names the Commit (`commit_number`), its Author, its origin and its note, and one Commit is published at most once. The Release does not copy the Commit's title: the list reads it from the Commit, and a Release with `origin = legacy` has none. The content of a Library Commit and of its Release is the same value object, and the ProjectFile's pins are unaffected. `CommitResponse.released` is true for a Library's Commit a Release published, so the Library UI disables "Make Release" on it. The Release is never removed alone and outlives nothing of its Library; the Library's deletion is still kept only by a live pin or a running Deployment (task 71).

## Amendment 2026-11-09: the full model — Draft, Commit, Release, Deployment (task 72_8)

The closing part gives the model its final form and settles what the earlier parts left open.

- **The levels.** A Draft is edited at once as DraftChanges under the Version of its content (ADR 0016, ADR 0017, ADR 0022). A **Save** fixes the whole Draft as a numbered, immutable Commit. A **Release** publishes one Commit — a Project Release (task 72_3) or a Library Release (task 72_5) — as an immutable, numbered copy of the Commit's content, its title at that moment, a note, the Author and the time. A **Deploy** makes one Project Release the running Deployment on the Runtime node (task 72_4). Neither a Release nor a Deploy reads or states a Draft Version: both work from an immutable Commit.
- **One Commit, at most one Release.** A Project Release and a Library Release are both unique per Commit (`origin = 'commit'`). A Release outlives its Commit, its Draft and future retention because it copies the content.
- **A Deployment names the Release it runs.** `runtime.deployments.release_number` is nullable: a Deployment made from a file (task 72_4, ADR 0018) and one made before this model has none. A Rollback copies the target Deployment's Release. Operation and the Project mode read the number, show "Release N · running", and show "Deployment N (not a Release)" for a Deployment with none.
- **No backfill.** An existing running Deployment is not turned into a Release and no synthetic Commit is made from it: the Draft may differ from what runs, and a fabricated history would lie. The Engineer may Save → Release → Deploy whenever they want the current Draft to run. A Library Release made before Commits keeps `origin = 'legacy'`, names no Commit and has the Author `system`; its `released_widget_types` are unchanged.
- **Discard and Revert are different acts.** Discard resets the Draft to its last Commit; Revert to deployed resets a Project's Draft to the running Deployment, and Revert to latest Release resets a Library's to its latest Release. Each is one transaction and clears the undo stack; neither changes a Commit, a Release or a Deployment.
- **Save, Release and Deploy clear nothing.** The sentence in the introduction that a DraftChange "is cleared by Deploy, Release and Discard" described the model before Save, Release and Deploy stopped touching the Draft: after task 72_4 and task 72_5 none of the three writes the Draft, so only a Discard and a Revert clear the stack (ADR 0017's amendment). A Commit's `draft_version` and the Draft's `last_commit_draft_version` are how the editor shows unsaved changes without touching the stack.
- **The API's shape.** Commits are `…/commits`, Project Releases `…/releases`, the Deploy `…/releases/{n}/deploy`, and the running state `…/deployment`. `POST …/deploy` is gone (410), `GET …/deploy/preview` is removed, and the Library Release body is `{commit, note?, author}`. `api/v0` is 0.30 and `record/v0` 0.4; both are MINOR changes while MAJOR is 0, so an older client may fail — the CHANGELOG lists the breaks.
- **growctl** exposes the same order: `save`, `release --commit`, `deploy --release`, `commits`, `releases`; `apply` still edits only the Draft. See ADR 0022 for the Author.

## Amendment 2026-11-10: a Save is refused at the Draft's Clean Version (task 74)

`draft_version` and `last_commit_draft_version` stay as the provenance of a Commit — the Version of the Draft a Save fixed — but they no longer decide whether there is anything to save. ADR 0016 gives the Draft a Clean Version, and `SaveCommit` refuses `nothing_to_save` when the Draft is at it: after a Discard (whose target is the last Commit) a Save is refused, so a Commit of unchanged content is not made by it. The other direction is deliberate: a Draft whose content an undo, a redo or an Open brought back to its last Commit's is not at its Clean Version, so a Save of it is allowed and stores a Commit equal in content to the previous one. The editor's unsaved-changes flag is that same Clean Version read from the Draft, not a comparison of these two numbers.
