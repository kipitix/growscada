# A Checkpoint is a stored snapshot beside the Journal; History starts from one at a past position

ADR 0002 chose ordinary state tables plus a single ordered Journal of "fat" entries, and ADR 0019 made `seq` the Journal position a reader catches up by. ADR 0020 made Operation a client-side Player over a starting state and the Journal, and left History (task 45) and PlaybackFile (task 46) to start from a moment in the past. Replaying from position 0 for every seek is not viable: the Journal is kept forever, and a busy Project writes millions of entries a day. Something must hold the whole operational state at a position, and it must agree with the Journal by construction.

Task 44. The term is `GLOSSARY.md` (Checkpoint).

## Decision

- **A Checkpoint is an immutable record beside the Journal, not an entry of it.** `runtime.checkpoints` is keyed by `(project_id, seq)`: `seq` is the Journal position the snapshot describes — the state after the entry at that position. The record is `contract/record/v0.Checkpoint` (MINOR): the envelope (`schema_version`, `seq`, `project_id`, `timestamp`) and the payload: the Deployment in force and every Tag state. It is not an aggregate: it has no behaviour, no events and no Version, and the Engineering node never reads it.
- **The payload addresses the Deployment, never copies it.** The Deployment reference is the same `{number, cause, rolled_back_from?, release_number?}` a `deployment` entry carries; the document stays in `runtime.deployments` (ADR 0014, ADR 0019). Every Tag state carries `{tag_id, value, quality, seq}` — `seq` is the position of that Tag's latest change, so a Player merging the snapshot with later entries keeps the greater position (ADR 0020). Runtime-origin entities (task 48) join the record when they exist, as a MINOR.
- **Every Deployment writes a Checkpoint in its own transaction.** A Deploy of a Release, a Deploy of a file and a Rollback all insert a Deployment, its Journal entry and the rebuilt runtime copies in one transaction; the Checkpoint is inserted after the copies are rebuilt, at the deployment entry's `seq`, so the snapshot includes the initial states of the Tags the document adds and never disagrees with the Journal. A failed Deployment leaves no Checkpoint.
- **Periodic Checkpoints are counted in Journal entries.** A Runtime-node background service scans once a minute for Projects whose current position has moved at least `CheckpointEveryEntries` (10 000) past their last Checkpoint, and takes one snapshot per such Project in a single `REPEATABLE READ` transaction: the position (`MAX(seq)`), the Deployment in force and every `runtime.tag_states` row from one snapshot, inserted with `ON CONFLICT (project_id, seq) DO NOTHING`. Time-based snapshots were rejected: the cost of a replay is the number of entries, not the elapsed time, and a fast Project would replay hundreds of thousands of entries after five minutes. A failed scan is logged and retried on the next pass; no outbox, no policy.
- **History reads a starting state at a past position, not the record.** `GET …/operation?at=<position>` returns the same `OperationStateResponse` as the present read model: the nearest Checkpoint at or before `position`, its Deployment resolved to the document (the shape `GET …/deployments/{n}` serves) and its Tag states. `position` in the answer is the Checkpoint's `seq`; History then reads `GET …/journal?from=<seq>` up to the moment it wants. Before the first Checkpoint the answer is the empty state at position 0; a position beyond the Project's current one is clamped to it; a negative or non-numeric one is 400; a Project that is not live is 404. Without `at` the route is unchanged and reads the present state — a Checkpoint lags by up to the threshold and would delay Operation's first picture.
- **No server-side Player.** The server serves the snapshot at the Checkpoint's position; the entries up to the moment are applied by the client, as ADR 0020 requires. A route that returned "the state at T" would duplicate the Player on the server.
- **Retention stays deferred.** Every Checkpoint is kept and goes with its Project, as the Journal does. Correctness never depends on one: without a Checkpoint before a moment, History replays from 0. Pruning is a retention decision (ADR 0002, ADR 0019), and PlaybackFile (task 46) needs the snapshots of the periods it exports.

## Considered Options

- **A `checkpoint` entry type in the Journal**: rejected. The Journal is the record of changes, and a Checkpoint is a derived snapshot; a full state per periodic snapshot would bloat every replay and force the Player and History to skip entries they must otherwise read.
- **Embedding the Deployment's ProjectFile in the Checkpoint**: rejected. The document is immutable and addressed by number (ADR 0014, ADR 0019); duplicating it per snapshot adds megabytes and a second truth.
- **Time-based periodic snapshots**: rejected. Replay cost is proportional to entries, and a busy Project makes a fixed interval unbounded; counting entries bounds both the replay and the snapshot's share of storage.
- **A snapshot in the Tag-state write's transaction**: rejected. The hot path would read every state and write a large row whenever the threshold is crossed; the background service keeps it cheap.
- **A policy or outbox job for periodic snapshots**: rejected. Those coordinate aggregates (ADR 0008); a Checkpoint is derived data with no aggregate, and a missed pass costs a longer replay, not correctness.
- **`GET …/checkpoints?before=` returning the record and a client-side assembly**: rejected. History would glue two responses and depend on the record's internal shape; the Operation read model is the starting state ADR 0020 already designed, and only the moment differs.
- **A separate `GET …/starting-state?at=`**: rejected. It would duplicate `/operation` with the same shape; the optional `at` names the one difference.
- **Pruning Checkpoints now**: rejected and deferred. It complicates PlaybackFile for old periods and is a retention decision with its own requirements.

## Consequences

- `runtime.checkpoints` and `contract/record/v0.Checkpoint` (MINOR 0.4 → 0.5); `api/v0` gains the optional `at` (MINOR). `make schemas` regenerates the record schema.
- A Deploy or a Rollback writes one extra row whose size is proportional to the Project's Tag count. A periodic snapshot does the same once per 10 000 entries.
- History (task 45) starts from `GET …/operation?at=` and reads the Journal after it; PlaybackFile (task 46) reads Checkpoints from the store; Operation is unchanged.
- A Checkpoint's Tag states carry no `written_at`: the record is about value, Quality and position, and a past state has no "last written" the record keeps. `?at=` answers `written_at` absent.
- The Checkpoint record grows with task 48 (runtime-origin entities) as a MINOR; a Checkpoint written before it decodes with none, which is the correct state for a moment before those entities existed.
- The background service is the Runtime node's and is wired in `main.go`; a test calls its one-shot run instead of starting a ticker. The Engineering node's `RuntimeNode` port does not change.
