# Tag definition and Tag state are two aggregates in two roles; one database per server with a server schema

A Tag is split into its Tag definition (name, TagType — configuration of the Draft, held by the Engineering node, an immutable aggregate with an expected Version) and its Tag state (value, Quality — process state, held by the Runtime node). Tag state has a single writer, the Tag's supplier or people, so a write states no expected Version and the latest write wins: `PATCH /tags/{id}/value` takes no `version` and never answers 409, and `devicelink` no longer tracks Versions nor retries. Tag state writes are frequent and are not changes of an aggregate edited by people, so they bypass the outbox (ADR 0008): after commit the Runtime node publishes `tag_updated` to the EventBus itself, at-most-once — a client that misses one resyncs on reconnect. Every write takes the next number of one sequence of the runtime schema (`seq` in the API), by which a reader drops the older of two states of one Tag; the Journal (task 42) will take over that role with its own `seq`. A new Tag's state is its TagType's zero value with Quality `Bad`: creating a Tag (`POST /tags`, a growctl manifest) no longer carries a value.

Each server has one database with three schemas, each with its own goose migration chain: `public`, the server's (Organizations, Projects, the outbox and policy jobs — what belongs to the server process, not to a role; the former single chain), `engineering` (Scenes, Widgets, WidgetTypes, Tag definitions) and `runtime` (Tag states). Both roles reference `public`; neither queries the other's schema, and the code of one role never imports the other's (checked by a test): the Engineering node reaches the Runtime node only through the `RuntimeNode` port, implemented in-process today and over HTTP later (task 52). A server with one role (task 52) has `public` and that role's schema in its own database.

Until Deploy exists (task 35), the Runtime node learns Tag definitions from a temporary bridge: a policy on `tag_created`/`tag_deleted` brings the runtime copy of a Project's Tag definitions into line with the Draft, and the Tag creation calls the same idempotent upsert right after commit, so a Tag accepts values as soon as `POST /tags` answers (a failed call answers its error); the creation then rereads the Draft and removes the state of a Tag deleted meanwhile; a policy run fixes a failed call. Deleting a Tag in the Draft removes its state at once. Deploy replaces the bridge: the runtime copy then comes from the running Revision.

## Amendment 2026-11-01: the Runtime schema copies the Draft's tables; state lives apart from definition

The Runtime schema holds **copies** of the Draft's tables — `runtime.tags` (the Tag definition: name, TagType, Version and the supplying Device), `runtime.devices`, `runtime.environments`, `runtime.environment_devices` — each row of a copy referring to its original by ID, and the runtime-specific data in **separate tables** referring to the copies: `runtime.tag_states` (value, Quality, seq) and `runtime.device_tokens`. An Environment's copy keeps its name unique in the Project: a Gateway names the Environment it serves, and the name is resolved to a pair with a Device here, not in the Draft. The definition and the state of one Tag are therefore in two tables, where before the state shared a row with the definition. The copy is the Runtime node's own: it exists so that a write can check the TagType and the supplying Device without asking the Engineering node, and it is filled from the running Revision once Deploy exists (until then, by the temporary bridge above).

A Device's supplying relation is part of the Tag definition and is copied with it, because the Runtime node must refuse a write from a Device that does not supply the Tag. A Device Token stores the Project its Device belongs to beside the token's hash: a Gateway presents the token alone, and the Project must be resolved without the Engineering node even while the Device sleeps — its copy gone from the running Revision. Nothing changes in the roles: the Runtime node still reads only its own schema, and the Engineering node reaches it through the `RuntimeNode` port alone.

## Amendment 2026-11-02: the shared domain includes `domain/device`

The packages both roles build on include `internal/server/domain/device` — the Device, Environment and EnvironmentDevice aggregates, which are the Engineering node's — because the shared `domain/tag` names a Tag's supplier as `id.ID[device.Device]`, and the Runtime node compiles `domain/tag` together with it. The isolation stays where it matters: the Runtime node's code uses no Device aggregate, and a test checks that no package of a role imports one of the other role, the shared packages included.

## Amendment 2026-11-04: the Runtime copies belong to the running Revision

The Runtime node deploys a ProjectFile into a numbered Revision and rebuilds its copies — `runtime.tags` with the supplying Device, `runtime.devices`, `runtime.environments`, `runtime.environment_devices` — from that document in the Deploy's transaction, keeping the Tag states and the Device Tokens, and publishes `revision_created` after the commit, at-most-once, beside `tag_updated`. From the first Revision on the copies are the Revision's alone: the bridge's upsert and delete take the same advisory lock `CreateRevision` takes and check for a Revision in the same transaction, so they write nothing once one exists. A Tag created in the Draft meanwhile gets no copy, and its value is `404` until the next Deploy names it; a Draft deletion reaches the Runtime node the same way. So what is said above about a Tag accepting values as soon as `POST /tags` answers, and about deleting a Tag removing its state at once, holds only for a Project that has no Revision yet.

## Amendment 2026-11-04: the bridge is gone; the copies come from the Revision alone

The temporary bridge is removed (task 35, part 4): `CreateTag` no longer upserts a Tag definition, `DeleteTagByID` no longer removes a state, the `sync_runtime_tag_definitions` policy and the `UpsertTagDefinitions`/`RemoveTagStates` methods of the `RuntimeNode` port are gone. A Runtime copy exists only for what a Deploy put into the running Revision: a Tag created in the Draft takes a value only after the Deploy that names it, a Tag deleted in the Draft keeps its state until the Deploy that drops it, and a Project that was never deployed has no Tag states and no Device copies at all. The Deploy fills them by diff in its own transaction, and the first Revision comes from the whole Draft. `UpsertDefinitions` and `Delete` of the Runtime repository remain the Revision transaction's own steps, not a second writer.

## Considered Options

- Two schemas only, Projects and the outbox in `engineering`: rejected. The Runtime node needs to know the Projects too, and copying them into `runtime` would make every Project deletion a cleanup in two places.
- A separate database per role on one server: rejected. Both roles would need their own copy of the server's Projects; separate databases come with separate servers.
- An expected Version on Tag state writes, or a counter of its own checked on write: rejected. Nobody competes for a Tag's value, a Device would get 409s for an Engineer's edit of the Draft, and the hot path would pay a read and a retry.
- Tag state writes through the outbox until the Journal exists: rejected. One outbox row per value change, for an order the `seq` already gives.
- A per-Tag counter or a timestamp to order states: rejected. A timestamp is not monotonic across concurrent transactions; one sequence matches the Journal's `seq` that replaces it.
- An initial value as part of the Tag definition: rejected. A value is state, never configuration; until a supplier writes, `Bad` says so.
- Keeping `domain/device` of the Engineering role alone, with the supplier held as a bare `uuid.UUID` or as a second, shared marker identifier: rejected. The first breaks the typed-identifier convention of `domain/id`, the second adds a second identifier type for one relation and a conversion on every boundary; a typed `id.ID[device.Device]` in a shared package costs less than either.
- A Tag without a supplier modelled as a zero `id.ID` (no value object): rejected. "People write it" is a real state of the definition, and the zero ID leaked into `NULL`, the API and the Runtime copy; `tag.Supplier` names the state instead.
- Running task 35 (Deploy) before the split, without a bridge: rejected — the split is the ground Deploy stands on.
