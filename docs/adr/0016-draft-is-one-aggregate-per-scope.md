# The Draft is one aggregate per scope; its content is versioned as a whole

A Project's Draft and a Library's Draft were a set of aggregates — Scene, Tag definition, Device, Environment, Environment Device, Library Pin, WidgetType — each with its own Version and compare-and-swap, held together by transitional row locks: a Scene's write locked its Library Pin, a WidgetType's write locked its Library, every write read the EditLock row of another aggregate. ADR 0008 already noted that an atomic DraftChange touching several of them is not served by a multi-aggregate transaction and calls for the Draft as the aggregate, and ADR 0012 and ADR 0015 named the locks it would retire. This is that aggregate.

## Amendment 2026-11-08: the EditLock is not a field of the Draft (ADR 0022)

ADR 0022 removes the EditLock: `engineering.drafts` loses `holder_key`, `holder_name`, `held_since`, `last_seen` and `lock_version`, and `internal/server/domain/editlock` is gone; its `Scope` becomes `draft.Scope`. The Draft stays one aggregate per scope with one Version, and that Version is now the only concurrency token: a write states it, and `draftRepositoryPostgres.Update` answers `draft.ConflictError` when it is stale. There is no read-only Draft and no gate to check in a write's transaction. Save checks the Version under the Draft row's lock (ADR 0021); a Deploy takes a Release and reads no Draft (task 72_4, ADR 0022). Everything else below about the aggregate, its content and its transaction holds.

## Decision

- **One Draft aggregate per scope.** `engineering.drafts` holds one row per Project or per Library: two nullable foreign keys (`project_id`, `library_id`) with a CHECK that exactly one is set, both `ON DELETE CASCADE`, one unique index each. The row carries the Draft's content `version`, its EditLock (holder key and name, `since`, `last_seen`, and a separate `lock_version`), and the position of its DraftChange stack. The Draft's identity is the row's own ID; the scope columns say which Project or Library it belongs to.
- **Content stays in its tables.** Scene, Widget, Tag definition, Device, Environment, Environment Device, Library Pin and WidgetType keep their tables and their read repositories, but they are entities of the Draft, not aggregates: they lose their own `version` columns, their compare-and-swap, their `SceneRepository.Save`/`TagRepository.Save` write paths and the row locks that held their invariants across roots. A write opens one transaction over the Draft, loads only the entities it touches, checks the EditLock and the Draft Version in that transaction, writes the touched rows, the DraftChange and the outbox rows, and commits.
- **One Version for all content.** Every write of a Draft's content states and raises the Draft's `version`; the `version` field of a content DTO in `api/v0` is that number, the same in every entity of one response. Undo and redo raise it too. The EditLock keeps its own `lock_version`, which grows only when the holder changes, so a Take over remains possible while the holder edits.
- **The EditLock is a field of the Draft.** `engineering.edit_locks` is dropped; the lock check reads the Draft's row in the write's transaction, and the presence refcount and the reaper stay as they are (ADR 0015). A Project or Library created before this migration gets its Draft row from the migration; a new one gets it on first access.
- **The transitional locks go.** The Scene↔Library Pin lock and the WidgetType↔Library lock become invariants inside the Draft transaction: a pin switch removes the PortBindings it breaks in the same change, and a write of a Widget checks the pinned release it reads. Only the Library's deletion against a Project's pin stays across aggregates, because the Library is outside every Project's Draft.
- **Discard is one transaction.** A Project's Discard reads the running Revision from the Runtime node, then replaces the whole Draft's content from it, clears the stack and commits in one transaction; a Library's Discard does the same from its latest Release. The `discarding` and `discarding_to` marks, the `project_discard_started`/`library_discard_started` events, `DiscardProject`/`DiscardLibrary` policies and the 202 answer go; the EditLock is the gate, and Discard answers 200.
- **Policies that DraftChanges replace go.** `NewUnbindDeletedTagPolicy` (a deleted Tag's bindings are removed in the change that deletes it) and `NewWidgetReconciliationPolicy` (a pin switch removes the broken bindings in the change that switches it) are removed. `NewProjectCleanupPolicy` and `NewLibraryCleanupPolicy` stay: a deleted Project or Library is outside its Draft.

## Considered Options

- **The Draft as one JSONB document in a row**: atomic writes for free, but every query, index and repository over Scenes, Widgets and Tags would be rewritten, and the ProjectFile builder would read a blob. Rejected.
- **Keeping the content as separate aggregates and applying a DraftChange in one multi-aggregate transaction**: it contradicts ADR 0008 and gives no honest invariant — the transaction is the only thing holding the parts together, which is what an aggregate is for. Rejected.
- **Loading the whole Draft graph on every change**: purest aggregate, but moving one Widget would load every Scene and Widget of the Project. Selective loading inside the Draft's transaction keeps the boundary without the cost. Rejected.
- **Keeping per-entity Versions as the API's concurrency token and adding a Draft Version for undo and Deploy**: two version namespaces, and undo would have to invent versions for restored entities. One Draft Version is the single writer's token. Rejected.
- **Keeping Discard as a policy with a read-only mark**: ADR 0012 already planned to replace it once the Draft is an aggregate; a synchronous single transaction is simpler and has no observable half-reset state. Rejected.
- **Making Library Release an entity of the Library's Draft so Release and the stack clear share a transaction**: published snapshots would become Draft content. The stack clear after Release is a separate transaction instead (ADR 0017). Rejected.

## Consequences

- The `api/v0` contract changes in meaning: `version` on a content DTO is the Draft's Version, not the entity's. The Project and Library DTOs keep their own versions (rename and delete are lifecycle acts, not Draft edits), and the EditLock DTO keeps `lock_version`.
- Every application service of a Draft's content is rewritten around the Draft repository; `aggregateStore`, `ProjectScopes` and `LibraryContent` lose their write paths, `retryOnRace` remains only for operations that state no Version and are not Draft changes.
- A Project or Library deleted while its Draft is held still goes; the Draft row cascades and the holder learns from the deletion event.
- The Runtime node is untouched: Tag states, Device Tokens, Revisions and the Journal stay where they were (ADR 0011).
- `AGENTS.md` and `GLOSSARY.md` describe the Draft as the unit of consistency; the Project and Library modes' read-only behaviour is unchanged, but it now rests on one row instead of two.

## Amendment 2026-11-08: Discard goes to the last Commit, Revert to the published state

After task 72_4 (a Project) and task 72_5 (a Library) the two resets are distinct. **Discard** resets a Draft to its last Commit — the saved state, dropping the unsaved DraftChanges — and a Draft with no Commit is 409 `nothing_to_discard` instead of falling back to a Release. **Revert** resets it to the published state: the running Deployment of a Project (`revert-to-deployed`) or the latest Library Release (`revert-to-release`, task 72_5), and is 409 without one. Both are one transaction over the Draft, clear the undo stack and write no DraftChange; neither changes a Commit, a Release or a Deployment. The consequence for the flags: "unsaved changes" is the Draft's Version above the one its last Commit fixed, and "unpublished changes" is the last Commit's number above the Commit the latest Release published (0 for a legacy Release).

## Amendment 2026-11-10: "unsaved changes" is the Clean Version, not a Version above the last Commit's (task 74)

The rule above is wrong: `Replace` raises the Draft's Version, so a Discard that restored the last Commit's content left the Version above the one that Commit fixed and the flag said "unsaved changes" with nothing unsaved. The same held for a Library and for the row of a selection page.

- **The Draft keeps a Clean Version**: the last Version at which its content became equal to its last Commit's content. It is a field of the aggregate — `Draft.CleanVersion()` and `Draft.HasUnsavedChanges()` = `Version() > CleanVersion()` — stored in `engineering.drafts.clean_version` (`0` for a Draft whose content never equalled a Commit's, i.e. one never saved). The scope itself is not changed: the marker is written in the Draft's own row, in the Draft's own transaction, with no event and no Version of its own.
- **Who sets it.** A Save sets it to the Version it fixes. A whole-Draft replacement (`Repository.Replace`, a Discard or a Revert) sets it to the new Version only when the content it wrote equals the last Commit's content: a Discard of a Project or a Library always does, unless it dropped Library Pins with their Widgets (task 71), and a Revert does only when its target equals that content — a Project's Deployment document compared with the Commit's by the same canonical form a ProjectFile is built and validated with, a Library's Release copies compared with the Commit's. A content write (`Update`), an undo, a redo and an Open of a file leave it as it was, so the flag turns on by itself.
- **One definition for the Save.** `SaveCommit` refuses with `nothing_to_save` when the Draft is at its Clean Version, not when its Version matches the last Commit's: after a Discard a Save is refused, and no Commit of unchanged content is made by it.
- **The read model is the aggregate's.** `GET /projects`, `GET /libraries` and `GET …/draft` carry the flag the Draft answers; a Draft with no row is clean, so a Project or a Library never written has no unsaved changes. The UI draws the flag and computes nothing of its own (the per-tab "clean version" of tasks 72_6 and 72_7 goes).
- **Known limitation, accepted.** The flag is an approximation of "the content differs from the last Commit" in exactly one direction: an undo, a redo or an Open that brings the content back to the last Commit's leaves it saying "unsaved changes" until a Discard (which is then clean) or a Save. This is accepted because the alternative — building the whole Draft (a Project: its Tags, Devices, Environments, pairs, Scenes with their Widgets and the pinned WidgetTypes) on every read of the flag — would run on every content event of an editor and on every row of a selection page. The Save does not pay it either, and refuses nothing it should have accepted.

Considered and rejected: comparing content on every read of the flag (exact, including the undo case, but a full build per read while the Draft is off its saved Version, and a Draft that cannot be built has to be reported as changed); a boolean `dirty` on the Draft set by every command (the same as the Clean Version without an answer to "at which Version", and any command that forgets it is a silent lie); computing the flag in the client from the Version and the last Commit (the tab that performed a Discard is the only one that knows, so a reload, another tab and a selection page see the lie, and the selection page would have to read each entity's Commits).
