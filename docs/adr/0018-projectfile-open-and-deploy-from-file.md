# A ProjectFile opens as one DraftChange; a file deploys as a Revision

A ProjectFile is portable (ADR 0005, ADR 0006): one project configuration, the Project named by its global UUID, no operational state, every WidgetType a Widget uses carried as a copy, so it does not depend on the Libraries of the server that reads it. Until now the format only travelled one way — the Engineering node assembled it and the Runtime node stored it as a Revision — and no client could take one out or put one back. Engineers need both: export a Draft or any Revision for inspection, backup and hand-off; restore a file into a Draft and undo that if it was the wrong file; and make a file operational on a Runtime node directly, for a plant that has no Engineering node, or to restore a known-good configuration without editing the Draft first.

## Decision

- **The file is the document itself.** `GET …/projectfile` answers the ProjectFile of the Draft, assembled by the same `ProjectFileBuilder` a Deploy uses, so the file is exactly what a Deploy would send. `GET …/revisions/{n}/projectfile` answers the document the Runtime node stored for Revision `n`. Both are `application/json` attachments named `<project>-draft.json` and `<project>-revision-<n>.json`; the project's name is local to the server (ADR 0006) and only names the download. A Draft the builder refuses is `409 draft_not_deployable`: the file format promises a configuration that can be deployed, and an inconsistent Draft is a state to repair, not to export.
- **Opening a file replaces the Draft as one DraftChange.** `POST …/projectfile?version=V` takes the document, requires the EditLock and the Version of the Draft the client saw, and calls the Draft repository's `Update` with `Session.Replace` — the same operation a Discard uses — so the whole content is replaced in one transaction of the Draft (ADR 0016) and recorded as one DraftChange, "Open a project file" (ADR 0017). The stack is not cleared, the redo tail is dropped as by any new change, and undo restores the previous Draft through the change's snapshots. The snapshots hold only the entities whose state actually differs, so the row is proportional to the difference, not to two Drafts; this is the one DraftChange that may legitimately touch every entity. The ordinary per-entity events are recorded, so the stream, the UI and undo behave as for a hand edit. Tag states and Device Tokens are untouched: they are the Runtime node's and change only with the next Deploy (ADR 0011). A file whose canonical form equals the current Draft is `409 nothing_to_open`; the comparison is skipped if the current Draft cannot be built, so a valid file can repair an inconsistent Draft.
- **Opening validates against the local Libraries.** The Draft stores pins, not WidgetType copies, so a file can be opened only where its pins exist: every `library_pins` entry must name a live Library with that Release, and every `widget_types` copy must match the Release's `ReleasedWidgetType` in identity and content. The check runs before the write and again inside the Draft's transaction, with the Library rows locked `FOR SHARE` as `PutLibraryPin` does, so a concurrent deletion cannot leave a pin to a deleted Library.
- **Deploying a file creates a Revision and does not touch the Draft.** `POST …/projectfile/deploy` validates the document and hands it to the Runtime node through the existing port, which stores it as a new numbered Revision, rebuilds its derived copies by the same diff as a Deploy, and publishes `revision_created`. The Revision's `cause` is `file` — a third cause beside `deploy` and `rollback` — and `rolled_back_from` stays empty. It needs no EditLock, like a Rollback: it writes no DraftChange, leaves the stack as it is, and the Project mode honestly reports "unreleased changes" afterwards, with Discard able to reset the Draft to that Revision. Because the document is self-contained (the WidgetType copies are in it), this path does not check the local Libraries: a file from another server runs on a Runtime node that has none of its Libraries.
- **One validation, ending in canonical equality.** Both commands decode strictly (unknown fields are rejected, ADR 0005), check `schema_version` — same MAJOR, MINOR not newer than the server's — and require `header.project_id` to equal the Project of the path (ADR 0006). They then build the domain entities, enforce the invariants and cross-references of the format, rebuild the ProjectFile from the would-be content with the builder's canonicalization and compare it byte for byte with the canonicalized input. A document that differs from its own rebuild, or that the builder would refuse, is not applied. Problems are reported together: `400` with `Problem.file_issues: [{path, message}]`, a MINOR addition to the API contract. There is no rewriting of `project_id`: a file configures exactly the Project it names.
- **Discard refuses a Revision whose pins are absent locally.** A Revision deployed from a foreign file may name Library Releases this server does not have. Discarding it would write pins the Draft cannot hold, so `POST …/discard` answers `409 revision_not_discardable` with the missing pins in `file_issues` and leaves the Draft untouched. A Revision whose pins are local discards as before.

## Considered Options

- **Only export and import into the Draft; deploy the Draft afterwards**: rejected. It cannot restore a configuration on a Runtime node that has no Engineering node, and it makes a file restore depend on a second act; the Draft-based Deploy stays the ordinary path and the file path is its explicit counterpart.
- **Deploying a file by opening it into the Draft and deploying**: rejected for the same reason, and because it silently rewrites the Draft of a Project someone may be editing. The file deploy is Runtime-only, like a Rollback.
- **Rewriting `project_id` on import**: rejected. ADR 0006 makes the Project's UUID global precisely so a file cannot be mistaken for another Project; rewriting it would let a configuration be merged into an unrelated Project and would make its entities' IDs ambiguous.
- **Accepting any older MINOR**: rejected as a promise. While MAJOR is 0 no compatibility between MINORs is promised (ADR 0005); accepting exactly the same MAJOR up to the server's MINOR, with a clear refusal for a newer file, is the most a v0 reader can honestly do.
- **Lenient validation — only schema and references**: rejected. The Draft would then hold a configuration a Deploy refuses, and the file would stop meaning "what Operation runs". Rebuilding the document is the cheapest proof that the file is deployable and exactly what the Draft will become.
- **Clearing the DraftChange stack on open**: rejected. Opening is an edit an Engineer must be able to undo like any other; the diff-only snapshot keeps the log's volume bounded by the actual change.
- **Storing WidgetType copies in the Draft**: rejected for the same reason pins exist: a Draft references a Library Release, and a ReleasedWidgetType is immutable.
- **Requiring local Libraries for a file deploy**: rejected. The Runtime node runs the copies in the document and never reads a Library; requiring them would block exactly the disaster-recovery and cross-server cases the format is for. The price is a Revision the Draft cannot be discarded to, which the Discard guard answers plainly.
- **Silently dropping pins a Discard cannot restore**: rejected. It would reset the Draft to something other than the Revision, without saying so.
- **Reporting only the first validation problem**: rejected. A hand-edited file usually has several, and a client fixing them one round trip at a time is the worse experience; the list costs one optional field.
- **A new `upload` event**: rejected. `revision_created` already tells every reader to reload the running configuration, and the cause is in the Revision's summary; a second type would only add branches (ADR 0014 makes the same argument for Rollback).

## Consequences

- The API contract grows by four routes, `file_issues` and the `file` cause — a MINOR while MAJOR is 0 — and `runtime.revisions`'s cause check gains the value by a migration. `project/v0` does not change: the validation has no new fields to carry.
- The Engineering node validates a ProjectFile, because the invariants live in its domains; the Runtime node only stores the document and its derived copies, as for a Deploy. A future Runtime-only node serving this command must take the validation with it.
- Project mode gains one dialog: download the Draft, open a file, deploy a file — the latter available to a read-only viewer, the two Draft writes gated by the EditLock.
- A `file` Revision behaves like any other for Operation, Rollback and the history; only a Discard needs its pins to be local.
- The Deploy of a Draft is unchanged; ADR 0013's "Deploy takes the Draft" now names one of three ways a Revision comes to be, beside Rollback (ADR 0014) and a file deploy.
