# One aggregate per transaction; an aggregate's events are stored with it in an outbox

Every transaction changes exactly one aggregate. The aggregate records its own domain events (Created on `Create`, never on `Reconstitute`; Deleted on `Delete()`, a Scene also recording one per Widget), and the repository's `Save`/`Delete` writes the new state (compare-and-swap on the Version it was loaded with) and those events into an `outbox` table in one transaction. A single dispatcher delivers outbox rows after commit, in the order of the transactions that wrote them (a row waits until every older transaction has ended, so a change is delivered after every change it was made on top of, and writers never wait for one another): to the in-process EventBus (SSE), and deletes the row in the same transaction that enqueues a policy job for every policy subscribed to the event — at-least-once. A policy job is keyed by the policy and a key the policy derives from the event (the aggregate it brings into line, e.g. the WidgetType): a further event for the same key merges into the waiting job and raises its generation, so a job taken before that event runs again. Policy workers run jobs apart from the dispatcher and retry a failed one with a pause, so a failing policy never holds back SSE or other policies. Changes spanning aggregates, such as reconciling Widgets with a changed WidgetType, are idempotent policies triggered by events, each Scene in its own transaction: eventual consistency, not a multi-aggregate transaction. A policy brings state into line with the current state of what the event names, read when the job runs, never with the event's payload: merged jobs and jobs run out of order then give the same result. For policies an event is thus an Event Notification ("something about this aggregate changed"), whereas Journal entries, carrying the full new state (ADR 0002), are Event-Carried State Transfer; neither is event sourcing, since state tables stay the source of truth. Operations that state no expected Version (removal, policies) reread and retry on a write race instead of reporting an edit conflict. We chose this so that "rolled back ⇒ nothing published" and "committed ⇒ eventually delivered" hold by construction, and events cannot be forgotten by a service. We assume one server process per database. Tag state writes are the exception: they bypass the outbox (ADR 0011).

## Considered Options

- A unit of work spanning several repositories (`uow.Do`, events raised by the service, published after commit): rejected. It makes multi-aggregate transactions the easy path and keeps event publication a service-side duty that can be forgotten (task 21).
- Publishing events from memory right after commit, without an outbox: rejected. A crash between commit and a policy loses the reconciliation for good.
- Policies run by the dispatcher before SSE, the row kept until they succeed: rejected. One persistently failing policy would stop the delivery of every later event, Operation's live Tag values included.
- A delivery position (cursor) per reliable subscriber in the outbox: rejected. Rows are deleted once delivered and held back by older transactions, so per-subscriber positions over them are harder to get right than a job table.
- One policy job per event, without merging: rejected. Every edit of a WidgetType would run the policy over all its Scenes again, though only the latest state matters.
- The Journal (ADR 0002) as the outbox: rejected. The Journal is the permanent operational record of the Runtime node with its own contract; Draft edits are not journaled, yet their events (e.g. `widget_type_updated`) still need reliable delivery. The Journal will be written in the same `Save` transaction, beside the outbox.

## Consequences

- An atomic DraftChange touching several aggregates (task 38) is not served by a multi-aggregate transaction; it calls for the Draft as the aggregate. EditLock makes it a single-writer boundary, so its size costs no contention.
- The outbox payload is an internal codec, not a contract (ADR 0005): rows live seconds, and a format change must keep reading the previous one until the outbox has drained.
- A long transaction anywhere in the database holds back the delivery of every younger one until it ends.
- With a second server process on the same database both dispatchers would deliver every event and SSE clients of one would miss the other's events; that needs a different design.
- Removing a container of aggregates is a policy too: a deleted Project is emptied Scene by Scene and Tag by Tag (ADR 0006), its content briefly outliving it.
- Policy jobs carry no event payload and merge, so they serve only policies that bring state into line. A reaction to each operational event (a notification per Alert raised, a Computation counting pulses) must not merge; it reads the Journal (ADR 0002) with a position of its own instead.
