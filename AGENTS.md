## Project Overview

GrowSCADA is a web-based SCADA system built in Go, following Domain-Driven Design (DDD). The backend and PWA frontend are compiled from the same Go codebase into a single binary — the server handles the API and serves the WASM frontend.

## Makefile Reference

All primary workflows go through `make`. **Always prefer `make <target>` over running raw commands directly.**

| Target | What it does |
|--------|-------------|
| `make install_tools` | Installs `goose` migration tool via `go install` |
| `make build` | Builds everything: `build_server` + `build_growctl` + `build_simulator` |
| `make build_server` | Compiles WASM frontend (`app.wasm`) and server binary to `bin/growscada_combined_server/` |
| `make build_growctl` | Compiles the `growctl` CLI (declarative project and tag manifests, kubectl-style) to `bin/growctl/` |
| `make build_simulator` | Compiles the device simulator to `bin/growscada_device_simulator/` |
| `make run_simulator` | `build_simulator` + runs it with `tests/device_simulator/example.yaml`: the seeded Device `sim`, its Environment `bench` and its token drive the seeded `device.speed` tag (needs a running server **with its Project deployed**: a Device and its Tags exist on the Runtime node only from a Deployment) |
| `make run_simulator_dashboard` | `build_simulator` + runs it with `tests/device_simulator/seed_dashboard.yaml`: drives the seeded tags bound to the "Main Dashboard" scene, visible in Operation after a Deploy of the Project (Project mode; `make db_up` alone creates no Deployment) |
| `make run` | `build_server` + starts server + opens Chromium at `localhost:8080` |
| `make db_up` | Starts the dev PostgreSQL container via Docker Compose; applies migrations and seeds automatically |
| `make db_down` | Stops the container and **deletes** the data volume |
| `make test` | Runs all tests with coverage under the race detector (`go test -race --cover ./...`) |
| `make bruno_test` | Builds the server and simulator images (`Dockerfile`), starts them on a fresh seeded database (`tests/api/docker-compose.yaml`, ports 9090/9191 on the host), runs both Bruno collections with a pinned `@usebruno/cli` via `npx` (`--env localhost --exclude-tags=manual`) and removes the containers; needs Docker and Node |
| `make bench` | Runs benchmarks only (`go test -run=^$ -bench=. -benchmem ./...`) |
| `make schemas` | Regenerates the committed JSON schemas `schemas/<contract>/<MAJOR.MINOR>.json` from the `contract/` types; run it after raising a contract's SchemaVersion. Refuses to rewrite a version already on `path`, freezes older versions in `schemas/<contract>/frozen.sha256`, and while MAJOR is 0 prints a NOTE for what in a new MINOR would need a MAJOR after 1.0 |
| `make full_restart` | Clean-slate restart: `db_down` → `db_up` → `run` (use when the DB state is stale or corrupted) |

`build_server` runs two compilations of the same `cmd/combined_server/main.go`: `GOARCH=wasm GOOS=js` for `app.wasm`, then host-arch for the server binary.

## Architecture

### Package Layout

`internal/` is split by application. The server's DDD layers live under `internal/server/`; the tools that talk to the server from outside sit next to it and talk to it over the REST API only. The shapes of everything that crosses a process or time boundary live in the public `contract/` package (ADR 0005), which every side may import. What else they may import depends on their role:

- **Engineer tools** (`growctl`) may also import value objects from `internal/server/domain/` (tag name, type, quality, name matchers, project name) to validate input the same way the server does. Never `application/`, `infrastructure/` or `interface/`.
- **The roles of the server** (ADR 0011): the Engineering node (`domain/scene`, `domain/library`, `domain/librarypin`, `domain/draft`, `application`, `application/appdto`, `postgres/repositories`, `postgres/outbox`) and the Runtime node (`domain/tagstate`, `application/runtime`, `postgres/runtime`) never import each other; the Runtime node builds only on the shared domain (`domain/tag`, `project`, `organization`, `id`, `event`, `version`). The Engineering node reaches the Runtime node only through its port `application.RuntimeNode`, implemented in-process by `internal/server/inprocess` (wired in `main.go` and `servertest`; HTTP — task 52). `internal/server/roles_test.go` checks the imports and that no SQL string of a role names the other role's schema.
- **The Device side** (`devicelink`, `devicesim`, future protocol adapters) depends only on the REST contract (`apiclient` → `contract/api/v0`), never on `internal/server/domain/`: its own enums (`devicelink.TagType`, `devicelink.Quality`) mirror the API's strings, so adapters stay independent of the server's internals (ADR 0004).

```
contract/           # Versioned contracts, public (ADR 0005): SchemaVersion + one package per contract and MAJOR
  api/v0/           # Server API: REST bodies and live events (package apiv0)
  project/v0/       # Project format: ProjectFile, the document a Deployment stores
  record/v0/        # Operational record format: Journal, Checkpoint, PlaybackFile (not modelled yet)
  manifest/v0/      # growctl manifests
  widgetscript/v0/  # WidgetType script contract: the `inputs` of render(inputs) (docs/widget_type_contract.md)
schemas/            # Generated JSON schemas, schemas/<contract>/<MAJOR.MINOR>.json (make schemas)
internal/
  server/           # GrowSCADA server + WASM UI (DDD layers below)
    domain/         # Core business logic — no external dependencies
    application/    # Use-case services, orchestrate domain objects (runtime/: the Runtime node's)
    infrastructure/ # Concrete implementations (Postgres repositories, outbox; postgres/runtime/: the Runtime node's)
    interface/      # Delivery mechanisms (REST API + SSE, EventBus, PWA UI)
    inprocess/      # The roles wired in one process: RuntimeNode over the Runtime node's services
  apiclient/        # Go client of the REST API, apiv0 types as they are; used by growctl, devicelink and the PWA UI
  growctl/          # growctl CLI: manifests, planner
  devicelink/       # Contract by which a Device delivers Tag values to the server (ADR 0004)
  devicesim/        # Lower-level device simulator: patterns, virtual Device, control API
cmd/
  combined_server/  # Entry point — wires everything together
  growctl/          # CLI entry point; logic in internal/growctl
  device_simulator/ # Simulator entry point; logic in internal/devicesim
```

### Domain Layer (`internal/server/domain/`)

Each subdomain owns its aggregate, value objects, and repository **interface**:

| Package    | Aggregate / Concept |
|------------|---------------------|
| `project/` | `Project` — unit of isolation (ADR 0006): name unique among the live Projects of its Organization; immutable (`Rename`, `Delete` marks it deleted); `ProjectUpdatedEvent`; `ProjectEvent` (its own events) and `ContentEvent` (events of its Tags, Scenes, Widgets, which name the Project by embedding `project.Content`; no event is both) |
| `organization/` | `Organization` — identity marker of the tenant; the server runs with the one the migrations create |
| `tag/`     | `Tag` — the Tag definition (name, TagType, supplier) of one Project (`ProjectID`), an entity of its Draft, the Engineering node's; immutable (`Delete` returns a new Tag); `TagCreatedEvent`, `TagDeletedEvent`; the value objects both roles share (`TagName`, `TagType` with `ZeroValue`, `TagValue`, `TagQuality` — `Good/Bad/Uncertain`) |
| `tagstate/` | `TagState` — the Tag state (value, Quality, `Seq`) with its `Definition`'s copy, the Runtime node's (ADR 0011); immutable (`Write` returns a new one); `Initial` = the TagType's zero value with Quality `Bad`; `TagUpdatedEvent` (a `tag.TagEvent`, never stored in the outbox); `Repository` |
| `draft/`   | `Draft` — the working state of one Project or one Library, the unit of consistency of its content (ADR 0016, ADR 0017): its `Scope` (a Project's or a Library's, in this package), the one `Version` of its content, its `StackPosition`, and the operations over the content (`CreateTag`, `DeleteTag` unbinding Scenes, Scenes, Widgets, Devices, Environments, pairs, pins, `Replace`, `Open`, `Purge`); `Draft.Undo`/`Draft.Redo` raise the Version and move the position, `draft.Session` is one write in the Draft's transaction (`Undo`/`Redo` apply a change's snapshots, never replay its operation), `draft.Snapshot` the before/after state of one touched entity, `draft.StackState` the two changes a client would undo and redo; `DraftChange` rows live in `engineering.draft_changes`. `draft.Commit` is the Draft's other entity (task 72_2, ADR 0021): an immutable, numbered snapshot of the whole Draft (the canonical ProjectFile or the Library's `ReleasedWidgetType` copies) with `CommitTitle` and `Author` VOs, its time and the Version it fixed; `WithTitle` records `commit_title_updated`, `NewCommit` `commit_created`; a Save writes no DraftChange and raises no Version, and `ErrNothingToSave` refuses an unchanged Draft |
| `scene/`   | `Scene` — named canvas (mnemonic screen) of one Project, binding only Tags of it (`TagTypes` are read through the Project's scope, `ProjectScope.ProjectID()`; TagTypes of another Project are `ErrTagTypesOfAnotherProject`, never taken for missing Tags); immutable aggregate whose methods (`AddWidget`, `UpdateWidget`, `MoveWidgets`, `RemoveWidget`, `Update`, `ReconcileWith`, `Delete`) return a new Scene; Scene and Widget events. `MoveWidgets` takes `WidgetMove` values (a Widget's ID and its new x/y), keeps every other field including z, reads neither the WidgetType nor the Tags (a broken binding never refuses a move, ADR 0010), records one `WidgetUpdatedEvent` per widget that actually moved and refuses a repeated ID (`ErrWidgetMovedTwice`), an unknown one (`ErrWidgetNotFound`) or a move that changes nothing (`ErrNothingToMove`) |
| `scene/`   | `Widget` — entity of the Scene aggregate: instance of a WidgetType placed on a Scene, with position/size/rotation/transform matrix |
| `library/` | `Library` — reusable collection of WidgetTypes of an Organization, outside every Project (ADR 0007): name unique among its live Libraries; immutable (`Rename`, `Delete` marks it deleted, refused while a live Project pins it); `LibraryEvent` (its own events and `library_released`); its Draft is the `draft.Draft` of the Library (ADR 0016) |
| `library/` | `WidgetType` — entity of one Library's Draft (`LibraryID`, name unique in it): HTML template + JavaScript script, InputPorts; immutable, carries no Version of its own (`Update`, `Delete` — touches no Scene; `RecreateWidgetType` rebuilds the released copies a Discard restores); its events name the Library. The reads are opened per Library (`WidgetTypeRepositories.ForLibrary`), the writes are the Draft's |
| `library/` | `LibraryRelease` — immutable snapshot of a Draft, never removed but with its Library: number (latest + 1), time, note, copies `ReleasedWidgetType` (value object, no Version — what Projects see and Widgets are checked against); `CreateRelease` refuses an unchanged Draft (`DraftDiffers`, also the "unreleased changes" flag); the Release states and checks the Draft's Version |
| `librarypin/` | `LibraryPin` — the Library Release of one Library a Project's Draft uses, one per pair (`ContentEvent`); `Switch` with an expected Version, `Delete`; `ImpactOf` — the one function computing what a switch or removal does to the Project's Widgets (orphaned → refused, `OrphansError`; broken PortBindings → removed by a policy), used by the preview and the check |
| `release/` | `Release` — the immutable publication of a Commit (task 72_3; ADR 0021), an aggregate of its own: its number within its scope, the Commit's number and title at publication, an optional `Note` (metadata: `WithNote` records `release_note_updated`), `Author`, time, `Origin` (`commit`; `file` in task 72_4) and a copy of the Commit's content, so it outlives the Commit, the Draft and the Library. One Commit is published at most once (`ErrCommitAlreadyReleased`); `CreateRelease(scope, commit, number, note, author, at)` is a pure constructor; `Repository` |
| `event/`   | Base of domain events: `Event`, `Base`, `EventType` (every event name), `EventTimestamp`, `Recorder`. Imports no aggregate |
| `id/`      | Generic `ID[T]` UUID value object; type parameter prevents mixing IDs of different aggregates |
| `version/` | Optimistic-concurrency version value object; Generic `Version[T]` |

### Application Layer (`internal/server/application/`)

Services (`ProjectService`, `TagService`, `LibraryService`, `WidgetTypeService`, `LibraryPinService`, `SceneService`, `DeviceService`, `EnvironmentService`, `DiscardService`, `ProjectFileService`, `ReleaseService`) accept repository interfaces injected from `main.go`. A mutation: parse input → load the aggregate → call its method → `Save`/`Delete` → `appdto`. Services publish no events (ADR 0008).

**Group move (task 40, part 1; ADR 0010, ADR 0017).** `SceneService.MoveWidgets(ctx, projectID, sceneID, version, moves)` moves a group of one Scene's Widgets in one `DraftChange` described "Move N widgets": it checks the live Project and Organization, the Draft's Version, then hands the moves to `draft.Session.MoveWidgets`, which loads the Scene once, calls `Scene.MoveWidgets` and records the before and after snapshot of each Widget that actually moved — an unchanged one is left out of the change, so undo restores every position of the group in one step. The request's input is validated before the Draft is read: an empty `moves` and a repeated `widget_id` are `invalidInput` (400), and `scene.ErrWidgetMovedTwice` from the domain is wrapped as invalid input too; an ID of another Scene is `scene.ErrWidgetNotFound` (404), `scene.ErrNothingToMove` is 409, and the Draft conflict is that of every Draft write.

**Undo and redo (task 38, part 3; ADR 0017).** `DraftChangesService` (`application/draft_changes_application_service.go`) serves the DraftChange stack of a Project's or a Library's Draft, named by a `draft.Scope`: `State` reads `{version, can_undo, can_redo, undo_description?, redo_description?}`, `Undo` and `Redo` state the Version the client saw and apply the change at the position (undo) or after it (redo). The stack's rows are internal: the repository reads the change at the position in the Draft's transaction, after the Version check, and writes the before (undo) or after (redo) snapshots, raising the Version and moving the position — no DraftChange is appended. The events are the change's inverse (a restored Tag is `tag_created`, a Widget whose binding returns `widget_updated`), so a stream and the UI see the restoration like the forward edit. An undo of a change whose rows were trimmed past the depth is not possible: `ErrNothingToUndo`/`ErrNothingToRedo` are 409; a stale Version is `ErrDraftConflict`. 

**Commits (task 72_2; ADR 0021).** `CommitService` (`application/commit_application_service.go`) serves both a Project's and a Library's Draft by a `draft.Scope`: `Save` validates the title and author, reads the Draft's Version, assembles the snapshot with the same `ProjectFileBuilder` a Deploy uses (a Library's `WidgetTypes` through its read repositories) and hands it to `draft.Repository.SaveCommit`, which locks the Draft's row, checks the stated Version (`draft.ConflictError`, 409 `draft_conflict`), refuses a Draft at its last Commit's Version (`draft.ErrNothingToSave`, 409 `nothing_to_save`), numbers the Commit after `last_commit_number`, writes it with the `commit_library_pins` of a Project's ProjectFile and raises `last_commit_number`/`last_commit_draft_version`; a builder refusal is `ErrDraftNotSaveable` (409 `draft_not_saveable` with the reason). The build is outside the transaction (the row lock plus the Version check give the same guarantee, as around Deploy), so `SaveCommit` takes the assembled `draft.CommitContent`. `List` (`FindCommits`, newest first, reads content for the counts), `Find` (`FindCommit`, a Library's with its WidgetTypes) and `Rename` (`RenameCommit`, no Version — a title is not content) complete the service; `ProjectFile` downloads a Project's snapshot. `content_counts` is computed from the snapshot, and `released` is true when a Release published the Commit (`ReleasedCommits` of the Release repository, only for a Project's scope until task 72_5).

**Releases (task 72_3; ADR 0021).** `ReleaseService` (`application/release_application_service.go`) publishes a Project's Commit and reads its Releases: `Create` checks the live Project and Organization, parses the note (optional, ≤2000 characters) and the Author, reads the Commit from the Draft's repository (a Commit the Project lacks is `draft.ErrCommitNotFound`, answered 404 with its number) and hands it to `release.Repository.Create`, which locks the Project (`pg_advisory_xact_lock`), numbers the Release `max(number)+1`, refuses a second Release of the Commit (`release.ErrCommitAlreadyReleased`, 409 `commit_already_released`) and writes the copy of the Commit's content with the pins of its ProjectFile in one transaction. No Draft Version is read or stated: a Commit is immutable and a Release changes no Draft. `List` (newest first), `Find`, `UpdateNote` (a note is metadata: `PATCH …/releases/{n}`, no Version, `release_note_updated`) and `ProjectFile` (the copied document as a download, `<project>-release-<n>.json`) complete it.

**Deploy Release, Rollback, Discard and Revert (task 35, part 4; task 36; task 72_4).** `ProjectFileBuilder` assembles the ProjectFile of a Draft over its `ProjectScope` and pins — the Tags with their supplier, the Devices, the Environments with their pairs, the Scenes with their Widgets, the WidgetTypes those Widgets use from the pinned Releases and the pins as provenance — canonicalized (lists by ID, JSON keys sorted), so one Draft is always the same bytes; a dangling reference (a Widget of a type no pinned release holds, a Tag supplied by a Device of another Project, a PortBinding naming a Tag the Draft lacks) fails the build. A Deploy takes a **Release**, not the Draft: `ReleaseService.Deploy` reads the Release's copied ProjectFile and hands it to `RuntimeNode.DeployRelease`, which stores it as a Deployment with `cause` `deploy` and `release_number`; a Deploy of the Release the Project runs already is 409 `ErrNothingToDeploy` (the Runtime node's own sentinel, translated by `inprocess`), checked under the advisory lock that numbers the Deployment, so two racing Deploys of one Release make one. The Engineering node keeps no copy of what it sent: the Deployment is the only truth (ADR 0014). The old `DeployService` and its `Preview`/`DeployState` are gone, and so are `POST …/deploy` (410) and `GET …/deploy/preview`: the Project mode reads `GET …/deployment` (with `release_number`) and the Release list. The Runtime node's `DeploymentService` serves `List` (newest first, no documents, empty for a Project never deployed), `Find` (by number, with the document; `ErrDeploymentNotFound`), `DeployFile` (a project file stored as a Deployment with `cause` `file` and no Release, for a Runtime-only node, ADR 0018) and `Rollback` — a new Deployment with an earlier Deployment's document and Release untouched (`cause` `rollback`, `rolled_back_from` the copied number), committed with the same derived-copy diff as a Deploy; a document equal to the running one is 409 `ErrNothingToRollback`. A Rollback publishes the same `deployment_created`. A Project that is not live is `project.ErrProjectNotFound`. `DiscardService` has two commands over the Draft, each one transaction (`draft.Repository.Replace`, clearing the stack, answering 200 with the Draft's `{version}` and `warnings`): `Discard` resets the Draft to its last Commit (409 `ErrNothingToDiscard` without one) and `Revert` to the running Deployment (409 `ErrNoDeploymentToDiscard` without one). A Library Pin the target names but this server cannot write — its Library is gone, or the Release is — is dropped with the Widgets of that Library's WidgetTypes, so the Draft stays writable (task 71). The Tag states and the Device Tokens are the Runtime node's and stay.

**Project files (task 39, ADR 0018).** `ProjectFileService` (`application/project_file_application_service.go`) serves a Project's files: `Draft` answers the Draft as the `ProjectFile` the builder assembles (a Draft the builder refuses is `ErrDraftNotDeployable`, a 409 carrying its reason), `Deployment` the document the Runtime node stored (`RuntimeNode.FindDeployment`), `Open` replaces the whole Draft with a document as one DraftChange, "Open a project file" (the Version is the `draft.Repository.Update` gate, the redo tail is dropped and the stack stays; a document whose canonical form is the Draft is `ErrNothingToOpen`, and the comparison is skipped when the Draft cannot be built, so a valid file repairs it). A file deploy is `ReleaseService.CreateFromFile` (task 72_4): the same validator, a Release with origin `file` (title `?title=`, default "File"; author `?author=`, default "file") and then that Release deployed; a failed Deploy leaves the immutable Release for a retry, and every file deploy makes a new Release. `RuntimeNode.DeployFile` remains for a Runtime-only node. Both commands share one validator (`application/project_file_validator.go`): the schema version is read first — the same MAJOR, the MINOR not newer, a newer file answered as such — then the document is decoded strictly, its `project_id` must be the Project of the path, and the invariants and cross-references of the format are checked (names, types, protocols, sizes and script languages; unique IDs and natural keys, a Scene's ID among them; a Tag's supplier Device and its PortBindings, each on a port its WidgetType declares and with a hint that accepts the Tag's TagType; a pair's Environment and Device; each WidgetType the Widgets use and each Widget in one Scene); finally the ProjectFile is rebuilt from the would-be content and compared with the canonicalized input, so a document missing, extra or normalized differently is refused. Every problem is reported together as 400 with `Problem.file_issues: [{path, message}]`. Opening also checks every pin against a live Library and its Release and locks those rows `FOR SHARE` inside the Draft's transaction; a file deploy does not, because the document carries its WidgetType copies. `draft.Session.Open` (`domain/draft/open.go`) records only the entities that differ, with the ordinary events, so an open is one DraftChange proportional to the difference and undo restores the previous Draft. A Discard and a Revert lock the pins they keep `FOR SHARE` in their transaction; a pin that disappears between the check and that lock is still `DeploymentNotDiscardableError` (409 `deployment_not_discardable`); the third Deployment cause is `DeploymentCauseFile` (`file`).

**Tag definition and Tag state (ADR 0011).** `TagService` keeps the Tag definitions of the Draft (entities of it, ADR 0016) and reads each with its state through `RuntimeNode` (`FindTagStates`; a definition without a state shows the initial one, and so does every one when the Runtime node fails to answer). `application/runtime.TagStateService` is the Runtime node's: `SetTagValue` (the hot path, `PATCH …/value`: the state read with the check of its Project in one query, `IsProjectLive` only on a miss; no expected Version, the latest write wins; the writer's Device is checked against the Tag's supplier in the same query (`tag.ErrTagNotSuppliedByDevice`; a Tag people write has `tag.NoSupplier`); the Tag's row is locked, the stored value and Quality compared, and only a change appends a `tag_state` entry to `runtime.journal` — the state's `seq` is that entry's position, so `runtime.tag_state_seq` is gone; a repeat keeps the position and moves `last_write_at` alone (ADR 0019); the write runs apart from the request's cancellation, and after a change is stored it publishes `tag_updated` to the EventBus itself, through the queue of `eventbus.AsyncPublisher` (one goroutine does the SSE fan-out; a full queue makes the write wait) — no outbox row, at-most-once), `FindTagStates`, `UpsertTagDefinitions` (idempotent: a Tag without a state gets its initial one; a state of another Project or TagType is an error), `RemoveTagStates`, `RemoveProjectTagStates`; its own `ErrInvalidInput`. The copies are the running Deployment's alone: `CreateTag` and `DeleteTagByID` write nothing to the Runtime node, and `UpsertDefinitions` and `Delete` take the advisory lock of `CreateDeployment` and check for a Deployment in the same transaction, so a Tag created in the Draft takes no value (404) until the next Deploy names it, and a Tag deleted in the Draft keeps its state until the next Deploy drops it (ADR 0011, amendment 2026-11-04; the bridge of the Draft is gone, task 35, part 4).

**Journal read and live stream (task 42, part 2; ADR 0019).** `application/runtime.JournalService` is the Runtime node's read side of the Journal, and is deliberately **not** in the Engineering node's `RuntimeNode` port (the Engineering node never reads it): `Read(ctx, projectID, from, limit)` returns the Project's entries after the position `from` (exclusive) in the order of their positions, at most `limit` of them, refusing a negative `from` or a `limit` outside `(0, JournalMaxPageSize]` with its `ErrInvalidInput`; `Position(ctx, projectID)` returns the Project's current position (`COALESCE(MAX(seq), 0)`, the start of a stream that names none). The page constants are `JournalPageSize = 100` and `JournalMaxPageSize = 1000`. `postgres/runtime.NewJournalRepositoryPostgres` implements `JournalRepository` (`FindAfter`, `Position`) over `runtime.journal`: `WHERE project_id = $1 AND seq > $2 ORDER BY seq LIMIT $3`, each row decoded by `journal_codec.go`; the Project's liveness is checked first (`liveProject`, as `FindAll` of the Deployments does), so a deleted Project is `project.ErrProjectNotFound`, never an empty page, and another Project's entries are never returned. The routes are `GET …/journal?from=<seq>&limit=<n>` (200 `JournalResponse{entries}`; `from` defaults to 0, `limit` to 100; a non-numeric or out-of-range value is 400) and `GET …/journal/events` (SSE). The stream subscribes to `tag_updated` and `deployment_created` **before** it reads its start position, then reads the table page by page until a page is empty and waits: a wake-up only makes it read again, so it needs neither the event's payload nor an outbox row. The start is `?from=` (which wins), else the SSE `Last-Event-ID` header, else `Position` (new entries alone); every message is `id: <seq>` and `data: <Entry>`, the record document as it is. Delivery is at-most-once and a reconnect with `Last-Event-ID` catches up exactly, because the stream reads the table; two racing commits may reach it out of order or one may be missed (ADR 0019). A safety ticker (5 s) rereads in case a signal is lost, and signals collapse into a channel of capacity 1. The stream is its own handler, not `eventHub`: `maxSSEClients` does not cap it, it names no client and holds no lock, and `/events` keeps `tag_updated` and `deployment_created` for the other modes and the Device Gateway (ADR 0020); removing them is a separate task.

**Operation read model (task 43, part 1; ADR 0020).** `application/runtime.OperationStateService` is the Runtime node's starting state of Operation: `Get(ctx, projectID)` answers `OperationState{Position, Deployment, Deployed, TagStates}`, and is **not** in the Engineering node's `RuntimeNode` port. It composes existing reads in one order — `JournalService.Position`, then `DeploymentService.FindCurrent`, then `TagStateService.FindTagStates` by the IDs of `Deployment.Content.Tags` — so a Deploy committed between the reads has a position above the snapshot and the Journal stream replays it (reading the position last could hide it from Operation; entries already in the states come again and are harmless, ADR 0020). A Project without a Deployment is `Deployed == false` with the position and no states, not an error; every Tag of the Deployment is present, and one the Runtime node holds no state of is filled in by `tag.NewTagType(definition.Type).InitialState()` — its TagType's zero value, Quality `bad`, `seq` 0, no `written_at`; an unknown type in the document is an error. A Project that is not live is an error wrapping `project.ErrProjectNotFound`. The configuration is the Deployment's `projectv0.ProjectFile` as it is: the model builds no render shapes and imports neither `domain/scene` nor any Engineering schema (ADR 0011). No repository, migration or outbox row is added. The PWA renders it with `ui/player` over the Journal stream (task 43, part 2).

**Projects (ADR 0006).** The repositories of a Project's content are opened per Project: `ProjectScopes.ForProject(p)` → `Tags()`, `Scenes()`, `LibraryPins()`, `Devices()`, `Environments()`, `EnvironmentDevices()`, every query scoped by `project_id`, and their writes are gone: the content is the Project's Draft. `ProjectContent` (the Tag, Scene, Device and Environment services) first checks that the Project is live and of the server's Organization (`ErrProjectNotFound` → 404 of the Project), then opens its scope; the hot path of Tag values (`TagStateService.SetTagValue`, the Runtime node's) checks it in the state's own query and reads the Project only on a miss, and so do the lists the UI reloads on every event (Tags, Scenes, Devices and Environments by `FindAllInLiveProject`, a Scene's Widgets by the Scene's `FindByIDInLiveProject`), the Project read only when nothing is found. Deleting a Project only marks it; `NewProjectCleanupPolicy` purges the whole Draft in one transaction over it (`draft.Repository.Purge`, ADR 0016) with the events of the removal, then its Tag states through `RuntimeNode`, and the Project's row last (its Device Tokens go with it by the foreign key, and `RuntimeNode` forgets the ones its cache resolved, or a token of the removed Project would keep authenticating; a state upserted late holds the row, and the next run removes it). A Draft's content is written through its repository, which locks the Draft's row, checks the Project is live and the Version the write states, and writes the touched rows in the same transaction; no separate row locks remain. Job keys of a Project's content start with `project:<id>`.

**Libraries (ADR 0007, ADR 0016).** A Library's Draft is a `draft.Draft` too: its WidgetTypes are its entities and every write of them (`WidgetTypeService.CreateWidgetType`/`UpdateWidgetType`/`DeleteWidgetTypeByID`, each stating the Draft's Version) is one transaction over `engineering.drafts` and one DraftChange; reads stay on `WidgetTypeRepositories.ForLibrary`. A Project sees WidgetTypes only through its Library Pins: `SceneService` finds a Widget's WidgetType among the releases the Project pins (`ProjectScope.LibraryPins().FindPinnedWidgetType`), and a Scene's write checks the type in the pinned release in the Draft's transaction (`checkPinned`) for each Widget added or retyped; a switch or removal of a pin (`LibraryPinService.PutLibraryPin`/`DeleteLibraryPin`, the presence of a pin decides add or switch and `version` is the Draft's) runs `ImpactOf` on the Project's Widgets read in the Draft's transaction, in the same DraftChange that switches the pin. A pin locks the live Library's row `FOR SHARE`, so a Library is marked deleted only while no live Project pins it; `LibraryService.DeleteLibraryByID` also asks the Runtime node (`RuntimeNode.DeploymentNamesLibrary`) whether the running Deployment of any live Project names a Release of the Library, and answers 409 `ErrLibraryInRunningDeployment` if it does — a Discard of that Deployment could not restore the pin. Old Commits and Project Releases do not block the deletion: their documents carry the WidgetType copies they need (task 71, ADR 0007). `LibraryService.Release` reads the latest release and the Draft, takes the next number, retries on `ErrReleaseNumberTaken` and checks the Draft's Version under the Draft row's lock (an unchanged Draft is `ErrNothingToRelease`); the stack is cleared in a transaction of its own after the release rows are committed, a failure to clear being 500 while the release stands. `Discard` is synchronous and one transaction of the Draft (`Replace` with `session.ReplaceWidgetTypes`): it names the released WidgetTypes back, clears the stack and answers 200 `{version}`; there is no mark, no `library_discard_started`, no `NewDiscardLibraryPolicy` and no `library_discarding`. `NewLibraryCleanupPolicy` removes a marked Library with its Draft and releases once no Project pins it; it re-checks no Deployment, because a marked Library is already gone for the API and a Deployment made from a file afterwards degrades to a warning at Discard.

**Concurrency: the Draft's Version (ADR 0022).** There is no editing lock: a Draft is edited and saved freely, and the one token of a write is the Version of its content (ADR 0016). Every write of a Project's or a Library's Draft states that Version; `draftRepositoryPostgres.Update` reads the Draft's row `FOR UPDATE` and answers `draft.ConflictError` (409 `draft_conflict`, the current Version in `Problem.draft`) when the stated one is stale, so two Engineers on one Draft see each other's writes as a conflict and retry. Undo and redo are shared: the second Engineer may undo another's DraftChange. Deploy reads the Draft's Version, builds the ProjectFile, then checks the same Version again in a short transaction (`draft.Repository.CheckVersion`) before sending it to the Runtime node: a write that landed during the build is 409 and nothing mixed is deployed; Rollback, Release and Discard read no Draft that way and need no such check. The `/edit-lock` routes of a Project and a Library answer `410 Gone` (removed with API 1.0); `?client=` on an SSE stream and `X-GrowSCADA-Client` are accepted and ignored.

**Events (ADR 0008).** One transaction changes one aggregate. The aggregate records its own events (`Create…` records Created, `Reconstitute…` — for repositories — nothing; changes and `Delete()` record theirs; see `event.Recorder`). The repository's `Save`/`Delete` writes the state (CAS on the loaded Version) and the pending events into the `outbox` table in one transaction; `outbox.Dispatcher` delivers them after commit, in the order of their transactions (`tx_id`; a row waits for every older transaction to end, so writers take no lock), to the `EventBus` (SSE) and deletes each row — at-least-once. Changes spanning aggregates are **policies** (`application.Policy`: `Name`, `JobKey(event)`, `Run(ctx, key)`): in the transaction that deletes a delivered row the dispatcher enqueues a job per policy that keys the event into `policy_jobs`; jobs with the same key merge (`generation`), and the `outbox.PolicyRunner` runs them apart from delivery, retrying a failure forever with backoff (1 s ×2 → 5 min). A policy brings state into line with what it reads when it runs, never with the event's payload (`NewProjectCleanupPolicy`: see Projects; `NewLibraryCleanupPolicy`: see Libraries). `NewUnbindDeletedTagPolicy` and `NewWidgetReconciliationPolicy` are gone (ADR 0016): a Tag's bindings are removed by the DraftChange that deletes the Tag, and a pin switch removes the bindings it breaks in its own change. A Draft's content is one aggregate, so its writes state the Draft's Version, and `retryOnRace` remains only for writes that are not DraftChanges (the cleanup of a Project, service operations). Writes of Tag states are the exception to all of this: no aggregate of people, no outbox (ADR 0011).

`appdto/` structs are the boundary between the domain and the outside world — not the REST DTOs.

**Devices and Environments (ADR 0004, amendment 2026-11-01).** `DeviceService` and `EnvironmentService` are the Engineering node's: a Project's Devices (protocol and configuration), its Environments and the pairs `(Environment, Device)` with their connection parameters. `DeviceConfigService` (`application/runtime`, the Runtime node's) serves a Device Gateway the configuration of its Device in one Environment from the running Deployment: the copies `runtime.devices`, `runtime.environments`, `runtime.environment_devices` and `runtime.tags`, read in one REPEATABLE READ transaction, never the Draft — a Device outside the Deployment is 403, an Environment or a pair it lacks is 404 (task 35, Q5). The Device Token is the Runtime node's: `application/runtime.DeviceTokenService` issues, rotates and revokes the one token a Device has, resolves `Authorization: Bearer gsc_dev_…` to its Device and Project (hash looked up in `runtime.device_tokens`, result cached in memory until the token changes), and holds no secret: the token is stored as its SHA-256 hash and its fingerprint and shown once.

The Engineering node keeps no copy (ADR 0014).
- **The Drafts** (`postgres/repositories/draft_repository_postgres.go`): `engineering.drafts` and `engineering.draft_changes` — `Read`, `Update` (locks the Draft's row, checks the stated Version, runs a `draft.Session`, writes the touched rows from its snapshots, one DraftChange and the outbox, raises the Version and moves the stack), `Replace` (Discard: same, clearing the stack, no DraftChange), `Purge` (the cleanup of a deleted Project), `ClearStack` (after Deploy/Release), and `CheckVersion` (the check around Deploy's build, ADR 0022); the loader reads only the entities an operation touches (`draft_repository_snapshots.go`), and the snapshots are encoded by `postgres/draftchange`.
- **The Project Releases** (`postgres/repositories/project_release_repository_postgres.go`): `engineering.project_releases` and `engineering.project_release_library_pins` — `Create` (locks the Project with `pg_advisory_xact_lock` and its row `FOR SHARE`, numbers the Release `max(number)+1`, writes the copy of the Commit's `draft.CommitContent` and the pins of its ProjectFile, and maps the partial unique key of `(project_id, commit_number)` to `release.ErrCommitAlreadyReleased`), `List` (newest first), `Find`, `UpdateNote` (one transaction and `release_note_updated`; no Version) and `ReleasedCommits` (the numbers a Commit list marks `released`). The content is the internal encoding a Commit uses, not a contract.

- **Outbox** (`postgres/outbox/`): `Append` (called by the repositories' shared `aggregateStore` template), the internal event codec (not a contract; the payload carries the `project_id` of a content event) and the `Dispatcher` (`Run`, `Notify` — wired to repositories via `repositories.NotifyOnCommit`, `DrainOnce` for deterministic tests; `WithPolicyRunner` makes it enqueue policy jobs) and the `PolicyRunner` (`Run` — woken by the dispatcher and by the timer of the next due job, `RunDueOnce` for deterministic tests); the policy registry is assembled in `main.go`. One dispatcher and one runner per database.

### Interface Layer (`internal/server/interface/`)

**REST API** (`internal/server/interface/restapi/`, port `:9090`):
- Uses stdlib `http.ServeMux` with method-prefixed patterns (Go 1.22+).
- All endpoints live under `apiv0.PathPrefix` (`/api/v0`); every response carries the `GrowSCADA-Schema-Version` header.
- The content of a Project (Tags, Scenes, Widgets, Library Pins with their `impact` preview, the pinned WidgetTypes, its event stream) lives under `apiv0.ProjectPath(id)`; `version` in a content DTO and every write of the content is the Version of the Project's Draft (ADR 0016), create bodies state it, and a DELETE states it in `?version=` (a stale one is 409 `draft.ErrDraftConflict`) (`/api/v0/projects/{project_id}/…`); Projects (`/projects`, `?name=`) and Libraries (`/libraries`, `?name=`) are the server's, a Library's Draft (`widget-types`, `GET …/draft` for its Version), `releases` (the body's `version` is the Draft's) and `discard` (200 `{version}`) under `apiv0.LibraryPath(id)`; a create or delete of a WidgetType states the Draft's Version too. A 409 of a pin's switch names the Widgets in `orphaned_widgets`. A group move of Widgets is one change: `PATCH …/scenes/{scene_id}/widgets` with `{version, moves: [{widget_id, x, y}]}` answers 200 `{version}`, 400 for an empty or repeated `moves`, 404 for a Widget the body names and the Scene does not hold, 409 `nothing_to_move` when no position changes, and the Draft's 409 `draft_conflict` like every write.
- The DraftChange stack is under the Project's and the Library's path: `GET …/draft-changes` (200 `{version, can_undo, can_redo, undo_description?, redo_description?}`, 404 for a Project or Library that is not live) and `POST …/draft-changes/undo` and `…/redo` with `{version}` (200 with the state after the operation; 409 `nothing_to_undo`/`nothing_to_redo` for an empty stack, 409 with `Problem.draft` for a stale Version). The state is read without a lock; the two commands are writes of the Draft like any other.
- The Commits are under the Project's and the Library's path (task 72_2; ADR 0021): `POST …/commits` `{version, title, author}` (201 `CommitResponse`; 409 `nothing_to_save`, `draft_not_saveable`, `draft_conflict`; 400 for an empty title or author), `GET …/commits` (200 `{commits}`, newest first, without content), `GET …/commits/{n}` (200, a Library's with `widget_types`; 404 `commit_not_found`), `PATCH …/commits/{n}` `{title}` (200, no Version stated) and `GET /projects/{id}/commits/{n}/projectfile` (a download, as a Deployment's document). The events `commit_created` and `commit_title_updated` name the Project (its stream) or the Library (the server's stream) and carry the number in `Event.commit`.

- The Project Releases are under the Project's path (task 72_3; ADR 0021): `POST …/releases` `{commit, note?, author}` (201 `ReleaseResponse`; 409 `commit_already_released`; 404 for the Project or the Commit, answered with the number the body names; 400 for a missing Commit number, an empty author or an over-long note), `GET …/releases` (200 `{releases}`, newest first, without content), `GET …/releases/{n}` (200 with `content_counts`; 404 `release_not_found`), `PATCH …/releases/{n}` `{note}` (200; no Version stated; 404) and `GET …/projects/{id}/releases/{n}/projectfile` (a download, `<project>-release-<n>.json`). The events `release_created` and `release_note_updated` go to the Project's stream and carry the number in `Event.release`; the history reloads them because `CommitResponse.released` changes with them. `apiclient`: `CreateRelease`, `Releases`, `Release`, `UpdateReleaseNote`, `ReleaseProjectFile`.
- Deployment is under the Project's path (task 72_4): `GET …/deployment` (the Deployment it runs with its `release_number`, 404 until the first Deploy), `GET …/tag-states` (the snapshot of its Tag states, 404 likewise), `POST …/releases/{n}/deploy` (201 `{number, deployed_at}`, 409 `nothing_to_deploy`, 404), `POST …/discard` (200 `{version}`, 409 `nothing_to_discard` — the Draft reset to its last Commit in one transaction) and `POST …/revert-to-deployed` (200 `{version}`, 409 `nothing_to_revert` — the Draft reset to the running Deployment). The old `POST …/deploy` answers `410 Gone`; `GET …/deploy/preview` is removed. `GET …/draft` answers the state of the Draft (`{version}`), the Version every content write states. The Deployment and the Tag states are the Runtime node's; a Deploy is the Release service's, Discard and Revert are the Engineering node's. The Runtime node's history is `GET …/deployments` (200 `{deployments: [{number, deployed_at, cause, rolled_back_from?, release_number?}]}`, newest first, `[]` for a Project never deployed, 404 for a deleted one), `GET …/deployments/{n}` (the running Deployment's shape plus `cause`/`rolled_back_from`/`release_number` and `content`; 404 for a number the Project lacks, 400 for a non-numeric one) and `POST …/deployments/{n}/rollback` (201 with the new Deployment's summary, 404, 409 `nothing_to_rollback`) — no Draft is read (ADR 0014).

**Journal** is under the Project's path too (task 42, part 2; ADR 0019). `GET …/journal?from=<seq>&limit=<n>` reads a page: 200 `{entries: [Entry]}`, the entries of `contract/record/v0` as they are stored, in the order of their positions; `from` is exclusive and defaults to 0, `limit` defaults to 100 and never exceeds 1000; a non-numeric or out-of-range value is 400 `invalid_input`, a Project that is not live 404 `project_not_found`, and every answer carries `GrowSCADA-Schema-Version`. `GET …/journal/events` is the live stream: `Content-Type: text/event-stream`, a `: connected` comment, then `id: <seq>` and `data: <Entry>` per entry. Its start is `?from=` (which wins), else `Last-Event-ID`, else the Project's position (only new entries); a bad position is 400 and a Project that is not live 404, both before the stream opens. Delivery is at-most-once, while a reconnect with `Last-Event-ID` catches up exactly by reading the table (ADR 0019). The handler is the Runtime node's own, not `eventHub`: `maxSSEClients` does not cap it and it names no client. `/events` keeps `tag_updated` and `deployment_created` for the other modes and the Device Gateway (ADR 0020); removing them is a separate task.

**Operation** is the Runtime node's read model of the starting state of Operation (task 43, part 1; ADR 0020). `GET …/operation` answers 200 `{position, deployment, tag_states}`: the Project's current Journal position, the Deployment it runs as a `DeploymentResponse` with `content: ProjectFile` (`deployment` is `null`, not absent, until the first Deploy) and every Tag of that Deployment's `tag_states` by ID, an unwritten one as its TagType's zero value with Quality `bad` and `seq` 0 (`tag_states` is `{}`, never `null`, without a Deployment). A live Project answers 200 before its first Deploy, so Operation can subscribe and catch the first Deployment; a Project that is not live is 404 `project_not_found`. It reuses `DeploymentService`, `TagStateService` and `JournalService` and adds no repository, migration or outbox row; `apiclient.ProjectClient.Operation` reads it and `ui/player.Player` renders it (task 43, part 2).
- Project files are under the Project's path too (task 39, ADR 0018): `GET …/projectfile` (the Draft as the `ProjectFile` a Deploy would send; 409 `draft_not_deployable` with the builder's reason) and `GET …/deployments/{n}/projectfile` (the stored document of Deployment n; 404 without it) are downloads — `Content-Type: application/json` and `Content-Disposition: attachment; filename="<project>-draft.json"` / `"<project>-deployment-<n>.json"`, the Project's name reduced to safe characters or its ID when nothing is left — with the document as it is and the API's schema version staying a header; `POST …/projectfile?version=V` opens the document as the whole Draft (200 `{version}`, 409 `nothing_to_open`, the Version gate of every Draft write), `POST …/projectfile/deploy` makes it a Deployment without the Draft (201 `{number, deployed_at}`, 409 `nothing_to_deploy`); a document that does not validate is 400 with `Problem.file_issues: [{path, message}]`, every problem listed, and a Discard of a Deployment whose pins this server lacks answers 200 with those pins in `warnings` and the widgets of their WidgetTypes dropped (task 71).
- CORS middleware applied globally.
- Errors follow RFC 7807 Problem Details (`problems.go`).
- Each resource has its own handler file (`tags.go`, `widgets.go`, etc.). JSON shapes are `contract/api/v0`; the conversions to/from `appdto` are in `dto_mapping.go`.
- Request bodies are decoded strictly with `decodeRequest` (unknown field → 400); clients read responses tolerantly.
- `NewRouter` takes the services of both roles (`restapi.Services`): `PATCH …/tags/{id}/value` and the Deployment/Tag-states reads go to the Runtime node (`TagStateService`, `DeploymentService`) — a Tag write has no `version` and answers `seq` —, everything else, a Deploy of a Release and Discard/Revert included, to the Engineering node's; `newAPIEvent` translates `tagstate.TagUpdatedEvent` (the Tag's full state, `seq` included) and `deployment_created` (the Project's ID, the Deployment's number and time and its `release_number`).
- Devices, Environments and the pairs `(Environment, Device)` are content of a Project (`…/devices`, `…/environments`, `…/environments/{id}/devices/{device_id}`); the token routes (`…/devices/{device_id}/token`, `…/token/rotate`) are the Runtime node's and answer 404 on a server without it; issuing and rotating check that the Device exists in the Draft, while reading and revoking do not — an orphaned token stays visible and revocable (task 66). A Device Gateway authenticates with `Authorization: Bearer gsc_dev_…`: `GET /api/v0/device/config?environment=<id>` answers its configuration and `GET /api/v0/device/events` its Project's configuration events; `PATCH …/tags/{id}/value` with a token writes as that Device (a Tag it does not supply is 403, an unknown or revoked token 401, a token of another Project 403). A bearer without the `gsc_dev_` prefix is not a Device Token (user authentication — task 50).

SSE streams no longer name a client: `?client=` of an older tab is accepted and ignored (ADR 0022).

**EventBus** (`internal/server/interface/eventbus/`): in-process bus feeding the SSE streams: domain events handed over by the outbox dispatcher, the Runtime node's `tag_updated` and `deployment_created` (published by `TagStateService` and `DeploymentService` themselves through `AsyncPublisher`, ADR 0011), plus delivery's own events (`client_connected`/`client_disconnected`, `system_ready`). The `eventHub` routes a `ContentEvent` to the clients following its Project and everything else — Projects, Libraries with their WidgetTypes and releases, connections — to those following the server's stream: `GET /api/v0/events` is the server's, joined by one Project's with `?project=<id>` (a Project not found adds nothing), `GET /api/v0/projects/{id}/events` one Project's alone. A Device Gateway's `GET /api/v0/device/events` follows its Project's stream with the configuration events alone (`device_*`, `environment_*`, `environment_device_*`), plus the events of that Project itself, which go to the server's stream. `event_bus_mqtt.go` is a stub.

**PWA UI** (`internal/server/interface/ui/`, port `:8080`):
- Built with [go-app v11](https://go-app.dev/) — compiled to WebAssembly, served by the same binary.
- Four top-level modes rendered by `root/root.go`:
  - **Library** — the Libraries (create, rename, delete), the WidgetTypes of the selected one's Draft (HTML template + JS script, live sandboxed preview via `<iframe srcdoc>`), its release state, Release (with a note), Discard (synchronous, one transaction) and its releases, viewed read-only. Its WidgetTypes, Release and Discard are edited freely (ADR 0022); a release shown read-only is the only read-only view. `Undo` and `Redo` of the Draft's DraftChange stack (ADR 0017): the hover text is the `undo_description`/`redo_description` of `GET …/draft-changes` ("Nothing to undo" for an empty stack), both are off while a release is shown, `Ctrl+Z`/`Cmd+Z` and `Ctrl+Shift+Z`/`Cmd+Shift+Z` do the same (not in a field the user types in, not behind a dialog of the mode, and only while the mode is shown — Root keeps the hidden modes mounted); the state is read on mount, on `EventResync`, after each content event, after a command and after a Release or a Discard that clears the stack, and a `{version}` it states is what a command sends (a stale one is a 409, an empty stack is a 409 with the toast and a reread). The column also carries **Save** and the unsaved-changes indicator of the Draft against its last Commit, and **History**: the Commits of the selected library, newest first, with their titles renamed in place (task 72_2; ADR 0021); a `commit_created`/`commit_title_updated` of another library is dropped.
  - **Project** — the Library Pins (pin, switch after a preview, unpin), configure Scenes and place Widget instances on them from the WidgetTypes of the pinned releases, grouped by Library. Scenes, Widgets, Tags, pins, Deploy (of a Release), Discard and Revert are edited freely (ADR 0022); a stale Version is a 409 that rereads the content and the stack. `Undo` and `Redo` of the Draft's DraftChange stack (ADR 0017): the hover text is the `undo_description`/`redo_description` of `GET …/draft-changes` ("Nothing to undo" for an empty stack), both are off while a dialog of the mode is open, `Ctrl+Z`/`Cmd+Z` and `Ctrl+Shift+Z`/`Cmd+Shift+Z` do the same (not in a field the user types in, not behind a dialog of the mode, and only while the mode is shown); the state is read on mount, on a resync, after each content event, after a command and after a Deploy or a Discard that clears the stack, and a `{version}` it states is what a command sends (a stale one is a 409 that rereads the stack and the content, an empty stack is a 409 with the toast and a reread of the stack). The header also shows the Deployment the Project runs and its Release (or "Not deployed"), Save (a dialog with a title and the stored author, or 409 `nothing_to_save`), its unsaved-changes indicator against the last Commit's `draft_version`, History (the Commits, newest first, each title renamed in place) — task 72_2, ADR 0021 —, Releases (task 72_3, ADR 0021: the publication of a Commit from its history row — a note and the stored author —, the list of Releases newest first with the Commit's title, note, author, time and counts, each note edited in place and each ProjectFile downloaded; a Commit published already has its button disabled with the reason in its tooltip; a successful publication shows a toast; `release_created` and `release_note_updated` reread both the list and the history), Deploy (it opens the Release list: each Release has a Deploy button unless it is running — "Running" — with the confirmation "Make Release N the running one? Operation switches to it"; a Deployment with no Release shows "Running Deployment N (not a Release)"; success shows a toast and rereads the Releases and `GET …/deployment`, and `deployment_created` does the same in other tabs), Discard (confirmation; it resets to the last Commit, and `nothing_to_discard` is a toast), Revert (confirmation; it resets to the running Deployment) and Deployments (always available: the list newest first with each number, time, cause — "Deployed", "Rolled back from #N" or "Deployed from file" — and Release, the running one marked, each row offering that Deployment's document as a download; selecting a row loads its document and shows the counts of its Scenes, Widgets, Tags, Devices and Environments; the Project mode offers no Rollback, which stays in the API and History). The Scene canvas selects an ordered set of Widgets whose last element is primary (task 40): a click replaces the selection, Shift/Ctrl/Cmd+click adds or removes one without dragging, a marquee dragged from the empty canvas selects by the axis-aligned box of each Widget's transformed corners (Shift adds; a drag shorter than 3 px on both axes is a click), `Ctrl/Cmd+A` selects the Scene's Widgets and `Esc` clears them (both, and the arrows, ignored in a field, behind a dialog of the mode and while another mode is shown). A body drag moves the whole selection by one delta and ends in one `PATCH …/widgets` with every moved position, a single Widget included; the arrows move it by 1 px (10 with Shift) and send one PATCH at the arrow's keyup, 500 ms without a press or a window blur, and any other write of the Draft waits for that PATCH before it states the Version (the same is true of a drag started mid-series). The canvas's dot grid does not follow the theme (a light core in a dark ring keeps at least one of the two visible on any Scene background; Operation has none), and a body drag — of one Widget or of the group — snaps its axis-aligned box, the group's common one included, to the edges and centres of the other Widgets and of the Scene within 6 px, nearest target first and the Scene's on a tie, drawing one `var(--accent)` line per snapped axis until mouseup; Alt frees the drag of snapping and guides, and the snapped positions go in the same one PATCH. The properties panel edits exactly one selected Widget — a group shows "N widgets selected" and no editors, and the anchor, rotation and resize handles belong to the single selection too. Next to Deployments is `Project file…`, one dialog (task 39, ADR 0018): `Download Draft` saves `GET …/projectfile` under the name the response gives it (a `draft_not_deployable` is a toast), `Open a file…` picks a `.json`, shows its name, schema, project and counts of Tags, Scenes, Widgets, Devices and Environments, warns that it replaces the whole Draft and can be undone, and confirms it with the Draft's Version and `Deploy a file…` picks one and confirms that Operation switches to a new Deployment while the Draft stays, naming the current Deployment; the server's `file_issues` are listed with their paths, not shown as one line, any other refusal is a toast, and after an open the content and the DraftChange stack are reread while after a file Deploy the Deployment, the Releases and the Deployments list are; a picked file is a one-off and does not survive a reload.
  - **Operation** — runtime operator view: the Scenes of the running Deployment only, with live Tag values. Its picture is a `ui/player.Player` of its own (task 43, part 2; ADR 0020): the Player reads the starting state `GET …/operation`, then follows `GET …/journal/events?from=<position>`; Operation reads neither `GET …/deployment` nor `GET …/tag-states` and handles no `eventlog.ActionServerEvent`/`EventProjectResync` — the Bar's stream and Draft/Library changes reach it only through a `deployment` entry. A Project without a Deployment shows "Project is not deployed"; its first Deploy arrives as a `deployment` entry and switches the screen without a reload, and a Deployment without Scenes shows "No scenes to show". The selected Scene is kept by ID across a Deploy or Rollback when the new configuration has it, else the first Scene; a switch of Project reads that Project's Scene from LocalStorage.
  - **History** — event log viewer.
- **The Operation Player** (`ui/player/`) is the operational model History will reuse (task 45): the running Deployment's `ProjectFile` and number, the Tag states by ID (including Tags the running configuration no longer names), the Journal position and the connection state. `player/model.go` maps a `ProjectFile` to the render shapes of `livescene` — Scenes, Widgets with their derived matrix, WidgetTypes and the Tags of the current configuration; a Tag without a state shows its type's zero value with Quality `bad` and `seq` 0. Entries of `contract/record/v0` apply immediately and in order: `tag_state` when its `seq` is above the known one (the state of a Tag outside the configuration is kept but not drawn), `deployment` by number — the document is read with `GET …/deployments/{n}`, the configuration is swapped and the states are kept by ID, so a new Tag is zero/bad and a removed one stops rendering — while an unknown type or a foreign MAJOR is ignored. The source is `player.Source` (`Open`/`Close` over `player.Events`), so the Player does not know whether the entries are live or replayed; `player.LiveSource` is the browser's EventSource over `apiclient.ProjectClient.JournalEventsURL(from)`, and `apiclient.ParseEntry` reads a message tolerantly. The Player redraws in batches: the entries apply at once, a burst costs one `Update`. A starting state is read before every explicit open — mounting, a switch of Project, a reconnect the browser gave up on — and the stream starts after its position; a native EventSource retry keeps the same `from` and catches up exactly from the table, and if the starting state moved ahead while the stream was opening the stream is reopened from the new position. A `deployment` document that fails to load is lost connectivity: the old configuration stays on screen, the view shows disconnected and the full resync retries with a backoff (2 s doubling to 30 s). `Connected` drives the same banner and Quality floor the Bar's state did. There is no periodic resync (ADR 0020).
- Project, Operation and History each have their own project switcher at their top (`ui/projects.Switcher`, one per mode: list, create, rename, delete with confirmation; the selection in LocalStorage under `<mode>:projectID`, the first Project when it is gone — left at once on `project_deleted` or `uiutil.ActionProjectGone`, which a 404 of a Project's Scene or Tag list (`uiutil.LoadOfProject`) fires instead of a toast, and a 404 of the Player's `GET …/operation` too). Project and Operation show their selected Project (`SetProject`, its `*apiclient.ProjectClient`); Project loads its content on the Bar's `EventProjectResync`, Operation resyncs its own Player and reads nothing of the Bar; Library has no switcher. The event Bar keeps one SSE connection, `/events?project=<id>`, following the Project of the mode shown (Library leaves it as it is) and reopened when that changes; on open it fires `EventResync`, then `EventProjectResync` while it follows a Project. Content events and `EventProjectResync` carry the Project of their connection in the action tag `eventlog.ProjectTag`; a mode drops those of another Project (`eventlog.ForProject`), so a hidden mode showing another Project is stale until shown again. A mode whose Project the Bar already follows is resynced at once (`Bar.ResyncProject`). On a switch while connected the old connection stays (delivering only the server's events) until the new one opens, which then fires `EventProjectResync` alone: the server's data is not reloaded.
- All REST calls go through one `*apiclient.Client` created in `root` and handed to the modes (`Client.Project(id)` for a Project's content); components work on the `contract/api/v0` types directly (no UI copies) and keep IDs as `uuid.UUID` (`uuid.Nil` = none), parsing text only at LocalStorage/SSE/DOM boundaries (`uiutil.LoadID`, `StoreID`, `ParseID`).
- A call is wrapped by `uiutil.Call(compoCtx, call, onOK, onErr)`: Async → call → Dispatch; `onErr == nil` shows `toast.FromError(err)` (the server's Problem Details, a Bad Response, a Network Error, or a Client Error). `uiutil.Do` hands value and error to one callback; `uiutil.Load` reloads a list through its `Reloader`, `uiutil.LoadFor` a list that belongs to a key (the Widgets of the selected Scene: a response for another key is dropped and the load reruns). The version a write states comes from a `uiutil.Versions` (max of every response; forgotten on a 409 and on resync; a request takes a `Mark` when sent, and a response sent before a forget does not bring the old version back): each mode keeps the one Version of the Draft it shows (`draftVersions`), which every content response carries and which also says whether a reread state is newer than the one shown — there are no per-Scene or per-WidgetType versions (ADR 0016); the stack's own `{version}` is used by the undo and redo commands alone. Lookups by ID go through `uiutil.FindByID` / `IdxByID`.
- Root shows a non-dismissable banner while the server's `GrowSCADA-Schema-Version` differs from the UI's (`apiclient.OnServerVersion`).
- UI tests mount components in go-app's `TestEngine` (`ui/uitest`; on the host go-app calls `OnPreRender`, not `OnMount`, so tests mount a `mountOnHost` wrapper) against the real API from `servertest.StartAPI`.

### Single Binary / Dual Compilation

`cmd/combined_server/main.go` calls `app.RunWhenOnBrowser()` near the top — when compiled to WASM this call takes over and runs the PWA; when compiled for the server it is a no-op, and the rest of `main` starts the HTTP servers. Both compilation targets share the same source file.

### Repository Integration Tests

Tests in `internal/server/infrastructure/postgres/repositories/` use **testcontainers-go** to spin up a real Postgres container, apply migrations via Goose, and run assertions. No manual database setup is needed for `go test`.

Tests of the tools that talk to the server (`internal/devicelink`, `internal/devicesim` end-to-end) run the real REST API over Postgres via `internal/server/servertest`: the container starts lazily on first use, so the unit tests of those packages don't need Docker.

## API Collections

Manual/exploratory API tests are maintained as [Bruno](https://www.usebruno.com/) collections in `tests/api/bruno_collections/`: `growscada_server/` for the server REST API (the `localhost` environment points to `http://localhost:9090`) and `device_simulator/` for the simulator's control API (`localhost:9191`, `TAG_NAME` is the seed tag `max_connections` driven by `tests/device_simulator/seed_dashboard.yaml`). The main automated tests are Go tests; two checks keep the collections from falling behind the API:

- **Static check** (`TestBrunoCollection` in `restapi` and `devicesim`, part of `make test`, no Docker): via `internal/brunotest`, every request must hit a route of the `routes()` table, every route must be covered by a request, and every body must decode strictly into the type that `requestBodies` (in the test) maps to its route.
- **Run** (`make bruno_test`, outside `make test`: GitHub CI and the end of every task, rule 9): both collections against the application in containers on a fresh seeded database, in `seq` order. Each request asserts its status, the `GrowSCADA-Schema-Version` header (server), `application/problem+json` on errors and one or two key fields on reads.

A request that needs an ID the server generates (the group move's Scene and Widgets) takes it from the answer in an `after-response` script with `bru.setVar`; the `localhost` environment declares the name with a placeholder UUID, which the static check substitutes and a run overwrites.

Bruno tags: `manual` — left out of the run (`get_events`, `get_project_events`: the SSE streams never end); `invalid-body` — a body meant to be rejected, skipped by the body check (it still has to cover its route).

## MCP Servers

Three MCP servers are available (via `opencode.json`) and should be used during development. Keep `opencode.json` plain JSON with no comments and no trailing commas: the `rtk` OpenCode plugin parses it strictly to honour `permissions`, and a JSONC comment only earns a `failed to parse permissions` warning on every shell call.

### codegraph

**Use codegraph BEFORE grep/find or reading files** when you need to understand or locate code. The index is a pre-built SQLite knowledge graph of every symbol, call edge, and file in the workspace — sub-millisecond reads, updated within ~1s of file changes. It lives in `.codegraph/` and is **gitignored**: a new dev host has none until `codegraph init -y` runs there (rule 10).

- `codegraph_explore` — PRIMARY tool. Pass a natural-language question or a bag of symbol/file names; returns the verbatim source of all relevant symbols grouped by file, plus call paths between them. Equivalent to running Read on multiple files at once — treat returned source as already read. Most questions need only this one call.
- `codegraph_node` — Read a single file (pass `file` only) or look up one named symbol (pass `symbol`). Returns source with line numbers + caller/callee trail so you see the blast radius before editing.
- `codegraph_search` — Quick symbol lookup by name. Returns locations only (no code). Use `codegraph_explore` to get the actual source.

**When to use it:**
- Before any edit — run `codegraph_node` on the symbol you're about to change to see who calls it.
- When exploring an unfamiliar area — one `codegraph_explore` call replaces a grep + multi-file Read loop.
- When asking "how does X work" or "where is Y defined" — answer directly from codegraph, no file reading needed.

### gopls
Go language server. Use it for accurate code intelligence instead of plain-text grep:
- `go_diagnostics` — compiler and vet errors for a file
- `go_file_context` — symbols, imports, and structure of a file
- `go_package_api` — exported API of any package
- `go_search` — workspace-wide symbol search
- `go_symbol_references` — find all usages of a symbol
- `go_rename_symbol` — safe rename across the workspace
- `go_vulncheck` — check dependencies for known vulnerabilities

### chrome-devtools
Browser automation. Use for verifying UI changes in the running PWA (port 8080):
- `navigate_page`, `take_screenshot` — open pages and capture state
- `click`, `fill`, `press_key`, `type_text` — interact with the UI
- `evaluate_script` — run JavaScript in the page context
- `list_console_messages`, `list_network_requests` — inspect runtime behavior
- `lighthouse_audit` — performance and accessibility audit

## Development Rules

1. **Work in a separate branch.** Never make changes directly on the `path` branch. If the current branch is `path`, stop and ask the user to create or switch to a feature branch before proceeding.

2. **Never commit without explicit user request.** Do not run `git commit` on your own initiative. Only commit when the user explicitly asks ("commit this", "make a commit", etc.). Preparing and staging changes is fine; committing is not.

3. **Always verify build and tests.** After any code change, run `make build` to confirm the build succeeds and `make test` to confirm all tests pass. Do not report a task as done until both commands exit cleanly.

4. **Raise the SchemaVersion when a contract changes.** Any change to a type in `contract/` changes a contract (ADR 0005): raise that contract's `SchemaVersion` — MINOR if old readers can ignore the change (an `omitempty` field, a new event type), MAJOR otherwise (removed/renamed/retyped field, new enum value) — and run `make schemas`. While MAJOR is 0 every change only bumps MINOR. `make test` fails if the types and the committed schema disagree.

5. **Keep Bruno collections in sync.** When any REST API endpoint is added, removed, or modified (URL, method, request/response shape), update the corresponding Bruno collection in `tests/api/bruno_collections/` to reflect the change: every new request has assertions (status, schema header, error content type, key fields), the `seq` order holds (reads, then changes, deletes last; IDs and versions in the bodies follow that order on the seed data), and a new route that takes a body needs an entry in the test's `requestBodies`.

6. **Start the test environment before debugging.** Before any debugging session or manual API testing, ensure the dev database is running with `make db_up`. If the database state looks stale or you hit unexpected data errors, use `make full_restart` to get a clean slate. Never run the server or hit the API endpoints without first confirming the DB container is up.

7. **Ask questions one at a time, interactively.** When interviewing the user (grilling, design sessions, clarifications), ask exactly one question per turn via the interactive question tool (`AskUserQuestion`), with a recommended option first. This overrides any skill instruction to batch several questions into one round.

8. **Audit grilling decisions against DDD.** When a grilling round ends, check every decision it produced against the domain model: aggregate boundaries and invariants, one transaction per aggregate with policies across aggregates (ADR 0008), the layer and role dependencies above (ADR 0011), and the terms of `GLOSSARY.md` and `docs/adr/`. Each mismatch opens another grilling round on that decision (rule 7 applies). The grilling is done when an audit finds no mismatch.

9. **Verify a finished task in the browser and with Bruno.** Once `make build` and `make test` pass (rule 3), bring up the environment (rule 6), run the server and walk every UI flow the task touches in the PWA through `chrome-devtools` (screenshots, console free of errors), then run `make bruno_test`. A task is done when both checks pass; report what each one showed.

10. **Rebuild the codegraph index on a new dev host.** `.codegraph/` is gitignored, so a fresh clone or a new machine has no index: the MCP server starts without a default project and every codegraph call returns nothing until you index. Check once, early in the work — `test -d .codegraph`, or `codegraph status` (`⚠ Not initialized`) — and if it is missing, tell the user plainly that codegraph is not indexed here and that you will fall back to grep/Read until it is, then offer to run `codegraph init -y` in the repository root (about a second; it creates only the gitignored `.codegraph/`). Keep the index current with `codegraph sync` after a pull or a branch switch, and rebuild with `codegraph index` when results look stale.

11. **Notify the user when a turn ends.** There is no notification hook: the agent sends the push itself through [ntfy](https://ntfy.sh) to the topic `kipitix_growscada`, just before the final message of a turn:

```bash
curl -sS -X POST https://ntfy.sh/kipitix_growscada \
  -H "Title: GrowSCADA: <что сделано>" \
  -H "Tags: white_check_mark" \
  -d "<одна-две строки: что сделано и что осталось>"
```

The title and the message are short and in Russian. The topic is public: anyone who knows its name can read it, so put no secrets, tokens, credentials or file contents in the message. A failed request (offline, ntfy unavailable) is not a failure of the task — report it in one line and finish. When the user names another topic, use it for the rest of the session.
